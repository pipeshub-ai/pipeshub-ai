# Org context

Every request, consumed message and job runs inside an **org context**: the org (and user) the work acts for, held in a `ContextVar` (Python, `backend/python/app/core/org_context.py`) or `AsyncLocalStorage` (Node, `backend/nodejs/apps/src/libs/context/orgContext.ts`). The two modules mirror each other: `current()` / `currentOrgContext()`, `bind` / `runWithOrgContext`, `for_org` / `forOrg`, `system`, `spawn_detached` / `spawnDetached`.

## Where it is set

Only from a verified source, never from a body, query string or header other than `Authorization`. The one exception is a broker message without a `ctx` (an older producer, or signing switched off): the org then comes from `payload.orgId`, which is a claim, not a verified value, and is logged and counted (see Signed broker envelope):

| Entry point | Binds |
| --- | --- |
| Python `authMiddleware` (`api/middlewares/auth.py`) | the verified token's `orgId` and `userId`. A service token without `orgId` stays unbound; org-scoped routes refuse it (`service_token_org`, 401). |
| Node `AuthMiddleware.authenticate` and `scopedTokenValidator` | the verified token's `orgId` and `userId`. Pre-org scoped tokens (no `orgId`) stay unbound. |
| Broker consumers (Python Kafka/Redis Streams, Node Kafka/Redis Streams) | the org from the signed envelope (below). |
| Crawling worker | `forOrg(job.orgId, "crawl")` per job, after checking the org id is a valid id and the org exists and is active (otherwise the job is dropped, not failed). |
| Periodic loops and start-up migrations (trash purge, storage release, flat storage migration, record label repair, code edge build reconcile, named-entity sweep and completion, sync resume, stale sync-state reset, queued-sync drain, connector token refresh, connector registry sync, connector config migrations, code graph backfill, All-team migration, query service start-up and its builtin skill seeding, Node metrics refresh) | enumeration under `system(reason)`, each org's work under `for_org` / `forOrg` so nothing leaks between iterations. Per-org settings (for example the trash purge's `softDeletePurge`) are read inside the org they apply to. `app/core/org_jobs.for_each_org` runs a job's work this way for every internal org and returns the orgs whose work failed, so a one-time job stays pending until each has run. Arango and Neo4j ignore the bound org, so a read inside it still filters on `orgId` (or `of_org`). The queued-sync drain reads each active org's queue this way, then publishes oldest first across orgs within one budget, each resync under its own org, in one pass. |

Outside these, no context is bound and `current()` raises `MissingOrgContext`. It is a bug in the caller, not a user error.

## Long-lived work

`asyncio.create_task` copies the creating request's context, and Node's `AsyncLocalStorage` follows timers, emitters and sockets created inside a request. A consumer loop, refresher or client created lazily inside request A would then serve every later event as org A. Start such work with `spawn_detached(coro)` / `spawnDetached(fn)` (empty context); use `spawn_in_request` when a child task should keep the caller's context. CI ratchets (below) block new bare task creation.

## Signed broker envelope (v2)

Wire shape: `{"eventType": "...", "ctx": {v, eventId, orgId, userId, requestId, issuedAt, sig}, "payload": "<JSON string>"}`. `sig` is HMAC-SHA256 over the topic, the message `eventType`, the ctx fields and the SHA-256 of the payload string as transmitted, keyed by HKDF-SHA256 of `scopedJwtSecret`. Re-sending a signed message with a different `eventType`, a different payload, another topic or another org fails verification. `ctx.requestId` (a trace id) is signed but not acted on. Consumers dead-letter a bad signature, a future `issuedAt` (more than 300 s) and a `payload.orgId` that differs from `ctx.orgId`. A `ctx` of any other shape, and a top-level `org_ctx` key (which is stripped), never reach a handler.

- **Producers.** They sign only when `ENVELOPE_SIGN=true`. A message that cannot be signed (no org bound, or a payload naming another org) is sent unchanged and counted in `pipeshub_envelope_unsigned_total{topic,reason}`; with no key it raises in enforce mode and is counted and logged in shadow mode. Retries re-publish under the message's own org, so they are signed like the original. Enable `ENVELOPE_SIGN` only once every consumer of the topic reads v2.
- **Unsigned messages.** While `ENVELOPE_SIGN` is off, a message with no `ctx` is v1: it binds from `payload.orgId` (logged, counted in `pipeshub_envelope_ctx_missing_total{topic}`). While it is on, a message with no `ctx` is a stripped message, counted in `pipeshub_envelope_stripped_total{topic}` and logged; `enforce` mode rejects it, shadow mode accepts it through the same fallback. A v2 message that lost its `ctx` is delivered in the v1 shape (decoded payload), or rejected as malformed. With `ENVELOPE_CTX_REQUIRED=true` any message without `ctx` is dead-lettered. A consumer that writes org-scoped tables must call `assert_may_start` / `assertMayStart`, which refuses to start while that flag is false.
- **Signature age.** A validly signed message older than `ENVELOPE_MAX_AGE_SECONDS` (default 900) is stale: counted in `pipeshub_envelope_stale_total{topic}` and logged in shadow mode, rejected in enforce mode. The window must exceed the longest legitimate time between signing and the last open of a message. A retry is re-signed when it is re-published, and its backoff (at most 300 s) is waited after the message is opened, so retries are inside the window. A message redelivered unchanged (consumer crash, rebalance, a pending Redis entry claimed after `claim_min_idle_ms`) keeps its original signature time, and so does a message that waits in a long backlog. Watch `pipeshub_envelope_stale_total` in shadow mode and raise the window above the observed lag, and above `RECORD_PROCESSING_TIMEOUT` (default 1800 s) if crash redelivery of long records matters, before switching to enforce. A dropped message is never silent: every rejection is counted in `pipeshub_envelope_rejected_total{topic,reason,event_type}` (the event type is filled only once the signature verified, so a forged claim never becomes a label), `pipeshub_envelope_stale_by_type_total{topic,event_type}` counts the stale ones by type, and the consumer's log line (or its `message.end` line) names the reason, the event type and the record, so a lost self-scheduled message (a re-purge hop, a seal) can be traced and its record repaired.
- **Admissions (PostgreSQL queue).** The PostgreSQL queue consumer writes, once it has opened a delivery's message with the signature and age verified (and again at every hand-back or retry), an admission on the delivery row: a keyed MAC, made with the envelope key, over the message's event id, org, event type, topic and payload hash, the consumer group, the message id and the stamp. A delivery whose admission verifies is not judged by age again, so a message handed back through an outage, a handler that outlives the window, or a claim that lapses is still processed; the signature, shape, org and future checks always run. A missing, edited, copied or expired admission (older than `ENVELOPE_ADMITTED_MAX_AGE_SECONDS`, default 86400, counted in `pipeshub_envelope_admission_refused_total{topic}`) means the age check applies as to any message. A writer without the key cannot make one, but any message a consumer opened can be replayed by a writer who copied its row, for as long as the cap. A message nobody claimed within the window is still stale on its first claim, as on every transport. A delivery claimed but not yet opened when its process dies has no admission yet. A delivery whose claim is lost before it is opened (another consumer holds the row) is neither run nor reported by the consumer that lost it; the claim is checked when the message is first opened, so one lost after that, before the handler starts or while it runs, is not noticed and the delivery stays at-least-once. A stale message is dead-lettered before the record's disposition is reported, so a consumer that lost the row reports nothing. An outage longer than `ENVELOPE_MAX_AGE_SECONDS` (default 900) in enforce mode dead-letters the messages nobody had claimed yet as stale: the age is read for that one purpose and the record the message names, if it is still waiting, is marked FAILED (a record that has moved on is left alone); the message is never processed and is kept as a dead row for seven days, not redriven, because signing an old message again would defeat the age bound. A record that ends FAILED this way is indexed again by reindexing it (the per-record reindex, or the index-wide reindex, which republishes every record that is not being processed). Size `ENVELOPE_MAX_AGE_SECONDS` above the longest outage you accept, or run in shadow mode. The 24 hour admission cap bounds the same outcome for a message that was opened and then waited unclaimed for more than a day.
- **Replay (Python consumers).** The simple consumers that `MessagingFactory` builds (entity, sync, code graph, AI configuration, record titles) on every broker are given the durable consumer inbox, `platform.consumer_inbox` (`app/services/messaging/inbox.py`), when PostgreSQL is one of the process's stores (`MESSAGE_BROKER=postgres`, `DATA_STORE=postgres`, `KV_STORE_TYPE=postgres`, `VECTOR_DB_TYPE=pgvector` or `REDIS_MODE=postgres`) and both `PG_CORE_URL` and `PG_JOBS_URL` are set. A message whose event id (`ctx.eventId`, or the top-level `eventId` of an unsigned message) its consumer group already finished for that org is acknowledged without running the handler, whether it came back from the broker or was written to it again. The id is recorded only after the handler succeeded, so a failed handler is retried; on the PostgreSQL broker the record and the acknowledgement are one transaction. A handler that finished but whose record was lost (the process stopped in between) runs again on redelivery: no handler commits its effect in one PostgreSQL transaction, so this is at-least-once with redeliveries skipped, not exactly-once. Ids are kept for the replay window (`max(ENVELOPE_MAX_AGE_SECONDS, ENVELOPE_ADMITTED_MAX_AGE_SECONDS)` plus the 300 s future skew, 86,700 s by default) and then deleted by the jobs role, once a minute per process. In enforce mode (`ORG_CONTEXT_MODE=enforce`) every copy of a signed envelope is refused as stale by then, so a replay is refused whenever it comes. In shadow mode (the default) a stale signature is logged and accepted, so a copy replayed after its id was deleted runs again (it shows in `pipeshub_envelope_stale_total{topic}`); an unsigned message has no age in either mode, so the same holds for it. Past the window the inbox skips redeliveries, not every replay: refusing replays for good takes enforce mode, because keeping ids for as long as shadow mode accepts a copy would mean keeping them for ever. An inbox that cannot be read or written is counted in `pipeshub_consumer_inbox_errors_total{op}` and the message runs as if new, so the inbox never stops delivery. Without PostgreSQL as a store there is no inbox (logged once at start): redeliveries may run again, as before, and a signed replay is refused once stale only in enforce mode. No Redis seen-ids are kept: an eviction would let a replay through, and under `noeviction` they fill the server. The indexing consumers do not use the inbox; a record's own state (and the replay set, `docs/indexing-service.md` section 4.1) says what was indexed. The Node consumers use the same table (next item).
- **Replay (Node consumers).** The notification and mail consumers, on every broker (`MESSAGE_BROKER` kafka, redis or postgres), skip an event their consumer group already finished for that org, through the same `platform.consumer_inbox` rows (`backend/nodejs/apps/src/libs/services/consumer-inbox.ts`, the same row id as Python). The inbox exists when the document store is PostgreSQL (`DOC_STORE=postgres`) and `PG_JOBS_URL` is set; otherwise the API logs once at start that it has none, and a redelivered event may run again, as before. The event id is the signed `ctx.eventId`, else the top-level `eventId` every producer stamps; the org is the signed one, else the `orgId` the handler itself acts on; a message without both (a mail sent before sign-in has no org) is never matched. The notification consumer writes its notifications and the record in one PostgreSQL transaction, so a redelivery, a replay or two deliveries of the event running at once store it once. An installation-wide alert (`audience: platformAdmins`) has no org of its own: it is recorded per org it reaches, so a delivery that failed partway stores only the orgs still missing when it comes back, and a redelivery that finds every org done stores nothing and queues no email. The mail consumer records after the send: a mail is sent again only when the process stops between the send and the record, or when two deliveries of the event run at the same time (an SMTP send cannot be rolled back). An inbox that cannot be read or written is counted in `pipeshub_consumer_inbox_errors_total{op}` and the message runs as if new; skipped copies are counted in `pipeshub_consumer_inbox_skipped_total{consumer}` and logged at INFO. The API's TTL sweeper deletes rows past the same replay window as the Python consumers (`ENVELOPE_MAX_AGE_SECONDS`, `ENVELOPE_ADMITTED_MAX_AGE_SECONDS`, 300 s skew), once a minute, as the jobs role.
- **Key.** Each service calls `configure_from_config` / `configureEnvelopeFromSecret` at startup (key derived from `scopedJwtSecret`). A Python service whose key cannot be read retries (briefly at startup, then in the background with backoff) and is never silent. While there is no key and signing or `ENVELOPE_CTX_REQUIRED` is on, a message carrying a `ctx` is rejected in enforce mode and processed through the counted, loudly logged fallback (`pipeshub_envelope_unverified_total{topic}`) in shadow mode. With neither flag on, it is processed through the counted fallback with a warning. With a key, a bad signature is always rejected.
- A shared test vector pins the Python and Node implementations to one canonical string.

## Shadow and enforce

`ORG_CONTEXT_MODE` is `shadow` (default) or `enforce`; any other value stops the service at startup. At org-scoped choke points, an access with no ambient org (`missing`) or an explicit org differing from the ambient one (`mismatch`) is, in `shadow`, counted (`pipeshub_org_context_violations_total{kind,site}`) and logged once per site with the call site, then allowed. A call made with the org-less bootstrap org `system` is counted as `system_token`, not `mismatch`, and is refused in `enforce` like a mismatch, so such a call must bind the org it acts for. In `enforce` it raises `MissingOrgContext` / `OrgMismatch`. Python: every `org_id` argument of every `IGraphDBProvider` implementation method (wrapped by `instrument_org_methods`). Node: `ambientOrg(orgId, site)`, currently at the crawling worker. Flip to `enforce` once the counters are zero over the simulator sites and the scale matrix.

## Service tokens without an org

A service token with no `orgId` stays unbound. Python answers 401 ("Token missing orgId") on every route except the pre-org allowlist `PRE_ORG_SERVICE_ROUTES` (`api/middlewares/auth.py`):

| Route | Why |
| --- | --- |
| `GET /api/v1/parse/providers` | lists parser providers; no org data |

Adding a route is a security decision; a test pins the list. Node scoped tokens without an org (pre-org login and mail flows) stay unbound and are not yet gated by an allowlist.

## Guards

- Python: `backend/python/tests/unit/core/test_org_context_guards.py` (baseline `org_context_baseline.json`).
- Node: `backend/nodejs/apps/tests/libs/context/org-context-guards.test.ts` (baseline `org-context-baseline.json`).

Both fail when a file gains a bare task/timer/worker creation (detached_work) or a new direct read of `orgId` off claims or the request user (direct_org_reads). Counts may only go down; re-record with `ORG_CONTEXT_UPDATE_BASELINE=1` after an intentional change.
