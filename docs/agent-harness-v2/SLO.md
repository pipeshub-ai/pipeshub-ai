# Agent harness v2 — SLOs

Status: P0.9. Owner: platform / deploy (perf and profile suites), execution track (fault suites),
intelligence track (parity cases).

This is the list of numbers the harness is held to, how each one is measured, which suite measures
it and which phase gate fails when it is missed. The thresholds come from TEST-STRATEGY §8.3 and
the design's robustness and deployment budgets (G20). Rows
marked **new** had no threshold before P0.9; they are proposals with a rationale, and the first
measured run on the harness path confirms or revises them in this file (never silently in a
workflow).

Baselines behind the relative thresholds:

| Footprint | `docs/agent-harness-v2/footprint-baseline.md` (measured by `deployment/docker-compose/tests/footprint.sh`) | per-container and per-process memory of the `eval` stack, harness off and on |

**Gates in CI (QA-22).** Every row has either a measured gate or a written reason with its owner in
`integration-tests/perf/slo_gates.py`. The latency rows run on the fault-stack rig (the production Node harness
composition and worker, a scripted model at a fixed token rate, `harness_profiles.py`) through
`bench_harness.py --profile rig --fail-on-gate`, weekly and on a published release (`perf-harness.yml`,
`harness-latency`). Thresholds have headroom over the measured value and are never looser than the target; a run
measured above the host's core count is `rerun`, not a result; a missed SLO carries its finding as a waiver and a
regression bound. Since PERF-B, SLO #1 is met and unwaived on one long session
(`code-mode-5k`) and on 16 sessions out of step at the capacity model's N = 16 commit rate (`commits-n16`).

**Decision (2026-10-12, PERF-C): in step and overload are measured apart.** PERF-C ended PERFB-F1 (the
transactions of one org aborting each other at its quota window and audit chain head: 13.5–14.7 aborted
transactions per committed one, now 0.1). The closed-loop profile that showed it, 16 sessions back to back with no
think time, then runs at about 62 commits/s, 3.4 times the capacity model's N = 16 rate, and saturates one Node
process by construction: its latency is queueing at overload, which SLO #1 and SLO #4 do not describe.

- **Sessions in step** are `commits-n16-instep`: an open loop at the capacity model's N = 16 rate in which all 16
  sessions of one org start every turn in the same instant. SLO #1 (commit p99 ≤ 100 ms) and SLO #4 (admission
  p95 < 150 ms) apply at their own bounds, unwaived. The absolute gate at those bounds is not waived: it is taken on a quiet host at FINAL-VERIFICATION stage 12 (PERF-C measured only paired differences on a loaded host).
- **Overload** is `commits-n16-burst`, held to what overload must not do, not to SLO #1 or #4:

  | Requirement | Bound | Why |
  |---|---|---|
  | Transactions do not abort each other | MongoDB's aborted transactions per committed one ≤ 1 over the run | PERFB-F1 was a storm of 13.5–14.7; a healthy run is near 0 |
  | Throughput does not collapse | commits/s ≥ 2 × the capacity model's N = 16 rate (2 × 18.3) | the storm held the rig to 1.2–1.3 ×; from the model, not from today's measurement |
  | A user is still admitted | admission p95 ≤ 1 s | **proposed, awaiting confirmation**: no overload bound existed; a user should not wait more than about a second to be admitted |
  | No run is lost or duplicated | 0 and 0 | every turn becomes exactly one run that ends |

**What sessions in step rest on (PERF-D).** Requests of the same instant share one Node event loop, so k of them that
each need c ms of it end about k × c ms after they arrived. Profile `commit-cpu` measures c as CPU, not latency (the
event-loop CPU and the store commands of an admission, a step commit and an ending commit), and `slo_gates.py` holds
them as `PERFC-F1` bounds: a request that gets dearer fails the weekly job on any host.

**Decision (2026-10-18, PERFD-F1): in step is held per Node process.** Compose ships one Node process; Helm ships
one per pod. SLO #1 and SLO #4 for sessions in step are measured and held on one process, as `commits-n16-instep`
runs them, and are never restated for a multi-pod topology: a user feels the latency of the process that serves
them, and nothing pins a session's requests to one pod. They are met by less work per request (PERF-E,
PERF-E2 and PERF-E3), not by a looser gate. Scaling out is the autoscaler's job, and Helm's now scales on a
signal one Node thread reaches (one core of CPU, or Node's own event-loop utilization), not on a share of a
multi-core request.

The thresholds are in `integration-tests/perf/slo_gates.py`.

## Measurement method per metric

All latency runs use the fake LLM with fixed token rates (TEST-STRATEGY §8.2), so a number measures
the harness and not a provider. Percentiles come from at least 200 samples per profile; p99 from at
least 1,000. Every run records the stack profile, broker, Mongo topology and runner size in the
result JSON, and `compare.py` only compares runs with the same environment label (the rule the
existing `baselines/<label>.json` files already follow).

### 1. Commit latency (p99)

- **What:** wall time of `POST /internal/harness/commit` from the worker's send to its 2xx, which
  covers the Mongo transaction (`w:majority`, `readConcern: snapshot`), receipt, seq counter, run
  CAS and outbox (REPORT §6.1.4).
- **How:** the worker exports a histogram per commit kind (`model.response`, `intent`, `outcomes`,
  `suspend`, …) and `bench_harness.py` reads it after each profile. Load: N concurrent sessions at
  the corpus-mean mix from `capacity-baseline.md`, N = 16 per worker (≈ 10 commits/s at the assumed
  latencies), plus the 5k-call code-mode profile on one session to exercise the single-session seq
  counter (robustness #3).
- **Why these numbers:** a turn makes 2–3 commits on its critical path (model response, write intent,
  outcomes); at 100 ms p99 each, commits stay a small fraction of a 3 s model call. 3-member RS pays
  one extra majority round trip. WriteConflict retries count against the latency, not as separate
  samples.

### 2. Non-model latency overhead

- **What:** time to first token (and to `turn.completed`) minus the fake model's own latency, on the
  harness path vs the legacy path, same stack, same prompt.
- **How:** `integration-tests/perf/bench_harness.py --profile short-turn` runs both routes against
  one stack (the org's Labs flag switched between blocks of 20 samples) in the same job, so runner
  noise cancels. The scripted model runs inside the bench (200 ms to first byte, answer chunks 20 ms
  apart) and every call is timed, so TTFT subtracts the model's time until it wrote its first
  answer chunk and turn done subtracts all of it. The profile is one question, one read tool
  (`list_toolsets`) and a streamed answer: two model calls on both routes. `--container` adds the
  durable breakdown from the lifecycle logs' timing fields. Weekly in `perf-harness.yml` (eval
  stack plus the harness overlay, which has the replica set); results per label in
  `integration-tests/perf/baselines/<label>-harness-short-turn.json`, judged for drift by
  `compare.py`. Command and flags: `integration-tests/perf/README.md`.
- **Gate (decided 2026-09-27):** an absolute budget, not a ratio. Harness non-model p50 ≤ legacy + 75 ms at
  TTFT and ≤ legacy + 100 ms at turn done; with `--container`, every durable commit kind's p50 ≤ 25 ms, so a
  regression shows where it happened (`--fail-on-gate`; budgets are the `*_BUDGET_MS` constants and CLI flags).
  **Why absolute:** durability costs a fixed number of majority-acknowledged commits before the first answer
  token (the commit rules), so a ratio against a 200 ms fake model mostly measures the fake model's speed; with
  real models (0.5–3 s to first token) the same overhead is a few percent of the turn. The earlier 1.15× gate is
  kept in the report as information only.
- **P1a measurement (2026-09-27, `local-m4-eval-redis`):** after the B-2 optimizations, TTFT
  271 ms vs 203 ms (1.34×) and turn done 320 ms vs 228 ms (1.40×). The
  commit rules put five majority-acknowledged transactions before the first answer token of a
  read-tool turn (admission, claim + pin, pre-run, `model.response`, the read outcomes), about
  45 ms of Mongo transaction time on that machine against a 30 ms budget (15% of legacy). As
  defined then (1.15×), the gate could not pass without changing a commit rule; the absolute budget
  replaced it, and this run passes it: +68.4 ms TTFT, +92.0 ms turn done, commits p50 9–24 ms.

### 3–5. Admission, first frame, LiveBus delta

- **Admission:** Node receives the request → `run.admitted` committed.
- **First frame:** request sent → `conversation_created` SSE frame received by the client.
- **LiveBus delta:** worker publishes a delta (timestamp in the frame) → SSE client receives it; the
  bench runs the client on the same host as the stack so clocks agree.

### 6. Recovery after lease expiry

- **What:** from the lease's `validUntil` (DB time, REPORT §6.1.5) to the next `run.claimed` of that
  run by a live worker, and then to its next commit (runnable).
- **How:** the fault suite kills the worker (`kill9` failpoint, P0.8) at each commit-rule crashpoint;
  the test reads `run.claimed` timestamps from the journal. Soak repeats it with random kills. The
  bound covers lease period + sweeper tick + jitter; the P1 lease constants must be chosen to fit it.
- **After a full control-plane outage** (P1b C-13): counted from Node's return. The sweeper no longer
  holds off after a gap, so its first tick expires what lapsed; L4 `control_plane_outage` measured the
  run's next claim 5.2 s after Node returned from a 45 s outage.

- **After the Node that answered the claim went away** (OPS1). A claim whose transaction committed and whose
  answer never reached the worker is held by nobody: the run waits for that attempt's lease to lapse and then for a
  sweeper. Counted from the claim's commit, it is runnable again within

  `max(L, T) + I`

  | Term | What | Shipped | Fault suite |
  |---|---|---|---|
  | `L` | the attempt's lease (`WORKER_LEASE_MS`; the worker asks for it) | 60 s | 10 s |
  | `I` | the sweep interval (`SWEEP_INTERVAL_MS`) | 5 s | 5 s |
  | `T` | the takeover of sweeper leadership | see below | see below |

  `T` is 0 while the leader lives, and 0 when it stops gracefully (SIGTERM: it releases its leader lease before
  anything else, another replica takes it on its next tick, and a replica that starts asks for it at once). A
  gracefully stopping Node also answers every request it accepted before it closes its store, so a rolling deploy
  orphans no claim in the first place. `T` is the sweeper's leader lease, 15 s (`SWEEPER_LEASE_MS`, three sweep
  intervals), when the leader crashed (SIGKILL, OOM, a lost host); with a single Node it is that Node's restart
  time when that is longer. So: 65 s shipped and 20 s in the fault suite after a crash of the leader; counted from
  the lease's `validUntil`, as the rest of this SLO is, `max(0, T - L) + I`, which is 5 s shipped. The lease is not
  shortened by any of this: only an idempotent claim (a retried claim returns the claim it made) would make a
  lost answer cost a retry instead of a lease, and that changes the claim contract (P1b finding 7; open).
- **How:** fault suite `test_recovery_bound.py` on both brokers, with one and two Nodes: the leader is killed, or
  sent SIGTERM, at the moment a claim's transaction has committed (the fault Node's failpoint); the times are the
  store's own.

### 7. Cancel latency

- **What:** client `cancel` request → run reaches `cancelled` (or the in-flight write resolves to its
  outcome/unknown and then `cancelled`).
- **How:** `bench_harness.py --profile cancel` cancels at random points of a long fake stream and of
  a slow fake tool; Playwright `stop-cooperative` asserts the UI state. Redis-down variant comes from
  the outage suite (§6.4), where only the durable `run.cancel_requested` + renew poll can deliver it.

### 8. Reconnect

- **What:** SSE reconnect with `Last-Event-ID` → first frame newer than that id.
- **How:** Playwright `reconnect-last-event-id` for correctness; k6 (`xk6-sse`) reconnect storm for
  the latency distribution under load (TEST-STRATEGY §8.2).

### 9–10. Commits and journal bytes

- **Projected (every PR):** `tests/harness_replay/capacity.py` projects the replay corpus onto the
  commit rules; `test_capacity.py` fails when any corpus turn exceeds 2 + 2 × tools commits, or when
  `capacity-baseline.md` is stale. This is a design check: it catches a change to the corpus or the
  rules, not the implementation.
- **Measured (P1):** `bench_harness.py` replays the same corpus scenarios through the harness route
  with the scripted model and sums BSON sizes of the journal events per run (inline) and CAS bytes
  (claim-checked). Gate: per scenario, inline bytes ≤ 1.5 × projected and commits ≤ projected + 1;
  any inline payload > 256 KB fails outright.
- **Baseline numbers (projected):** corpus mean 8.1 commits and 15.5 KB inline journal per run; the
  busiest recording is 1.1 commits/s per run. The scripted corpus has short answers and small tool
  results, so real traffic will be larger per run; P1 replaces the projection with measured journals.
- **Finding for P1/P5:** a 5k-call code-mode run projects to 56 commits but 5,018 events and ≈ 12 MB
  of inline journal (≈ 400 MB/hour for one session at 50 calls/s). Batching read outcomes per commit
  (robustness #23) bounds commits, not bytes. P5 needs either one claim-checked batch payload per
  commit or code-mode read results written to `/tool-results` with only digests journaled.

### 11. Cache-read share

- **What:** `cache_read_tokens / input_tokens` of each ended durable run.
- **How:** the scripted usage fixtures of the parity cases fix their own share, so they check the arithmetic, not a
  model's caching; the number that matters is production's.
- **In production (C5.05):** each ended durable run's own `cache_read / input`, as its budget account summed it, is
  one sample of `pipeshub_agent_harness_run_cache_read_ratio` (Node, `adapters/telemetry/chat-path-metrics.ts`;
  no labels, so it is the fleet's distribution, not per model). `HarnessCacheReadShareLow`
  (`deployment/monitoring/prometheus/agent-harness.rules.yml`) warns when the median of 20 or more runs in six hours
  stays under 70% for an hour; the dashboard's "Per-run cache-read share" shows the median and the worst tenth.

### 12. First token with 5 MCP servers

`bench_harness.py --profile mcp-5-servers`: 5 fake MCP servers (HTTP) attached to the agent; first
token vs the P0 legacy run with the same servers.

### 13. Approval-prompt rate

- **What:** runs that raised at least one approval interaction ÷ benign runs, over the parity cases.
- **How:** `approval_prompts` of each case's result (`tests/support/parity_cases/harness_trial.py`). Legacy has
  no approval gate; the threshold is absolute, so approvals must come from policy precision (write
  intents the user did not ask for), not from prompting on every write.

### 14. Injection success

- **What:** cases where something bound for the attacker left the run (a committed fake-connector
  effect, a remote image or data-carrying link in the answer, sandbox egress), per `graders.py`.
- **How:** deterministic lane with a compromised scripted model, so the number measures the harness
  alone. Gate: 0 at P2 exit, held on every PR.

### 15–16. Footprint

- **What:** `docker stats` memory usage per container (cgroup usage without page cache), and PSS/RSS
  per supervised process inside the app container from `/proc` (children charged to their service),
  after health plus a settle period, peak of 3 samples 10 s apart.
- **How:** `deployment/docker-compose/tests/footprint.sh` installs the `eval` profile in an isolated
  Compose project, measures, turns the harness processes on (the
  `docker-compose.agent-harness.yml` settings), measures again and uninstalls.
  `FOOTPRINT_PROJECT=<name>` measures an already running stack read-only.
- **CI (S1):** `published_hub_smoke.sh` runs `footprint.py measure` + `check` when
  `PIPESHUB_SMOKE_FOOTPRINT=1`; the `eval` job of `published-hub-smoke.yml` sets it, so every PR
  touching the compose files and the weekly schedule fail when the shipped `eval` profile is over
  budget. The harness-on variant needs a second app start (~3 min) and runs by hand or nightly with
  `footprint.sh`; it becomes part of the S1 job once the harness is on by default in any profile.
- **Baseline (2026-09-26, `footprint-baseline.md`):** `eval` total 5,260 MiB harness off, ≈ 5,880 MiB
  harness on; app 3,577 / 4,199 MiB. The idle harness worker is 667 MiB PSS (852 RSS), **over** the
  350 MB row-16 budget: it builds a full `QueryAppContainer`.
- **WP-88 (2026-11-06):** the worker no longer builds one (`HarnessServices`, lazy resources). `run_worker` started
  on the host (the fault rig's worker: the production composition with a scripted assembler), after its warm-up and
  two minutes idle: **330 MiB RSS** (292 anonymous, 38 file), within the row-16 budget. The worker is non-dumpable,
  so its PSS is not readable from outside it.
- **R25-OPS (2026-11-11), in the image:** `footprint.sh` on the image built from this tree, `slim`, harness on,
  120 s idle, load ≈ 9.5 on 32 cores: the worker **723 MiB** PSS (children with it) and the sandbox broker
  **218 MiB**, both **over** their rows (350 MB, 100 MB); the model gateway 350 MiB. Importing the worker's module
  alone is 276 MiB. R25OPS-FU-1 finds what the running worker and broker add (footprint-baseline.md).
- **R26-FU (2026-11-11), in the image:** the same run after R25OPS-FU-1's fixes (bytecode in the image, lazy package
  re-exports, `app.edition_services`' services on first read, the freed startup heap given back): the broker
  **100 MiB** (was 218; at the row), the worker **625 MiB** RSS (was 723), the model gateway 270 (350), every Python
  service 17 to 68 MiB smaller, harness-on total 6,181 MiB (6,653). The idle worker adds nothing after its start: it
  is its import and configuration (~220 MiB), the tokenizers' rank tables (64) and C-17's warm-up of what its first
  run imports, the graph driver included (~350). The row's 350 MB fits a worker that has not warmed up (WP-88's rig, 330);
  R26FU-FU-1 asks whether the row is restated for a warmed worker or the agent stack is slimmed
  (footprint-baseline.md "R26-FU re-measure").
- **Budget source:** the design's `desktop-eval` budget (app ≤ 4.5 GB, total ≤ 7.5 GB), constants

### 17–19. Sandbox, code mode, soak

As TEST-STRATEGY §8.3 and §10.3 (P5, P9 rows); no change from P0.9.

Row 19 (WP-88): `perf-harness.yml`'s `harness-soak` job runs `bench_harness.py --profile soak` for 1,440 minutes on
the fault-stack rig: ten users (60% of the capacity model's N = 16) paced at its turn period, mixing the corpus's
read, write, answer turn, a streamed answer and, every tenth turn, a slow read the user stops. Node's and the
worker's resident set (and Node's open files; the worker is non-dumpable, so no other process may list its) are read
every 30 s. After the load, two lease lengths of drain, then what is left: runs not ended, worker-owned runs whose
lease nobody holds, outbox rows pending, publishing or failed (each must be 0), and growth, the last tenth's median
over the second tenth's (the first is start-up), under 10%. The rig runs loop runs, which start no sandbox; orphaned
sandboxes are the broker reaper's, gated by its own suite.

### 20. Interactive session ready under saturation

G-45 / GA-24. One worker of four slots holds 16 scheduled runs of 24 one-second steps; then a turn of two steps
arrives every two seconds, twelve in all. Session ready is admission to the run's first model call, on the
deterministic clock, with a fake model and no network, so the number measures the queue and preemption, never the
host. The bound is the warm-pool target, since a person's turn should not feel the load: p95 ≤ 5 s. Measured (WP-44)
1.1 s, every scheduled run completed and no step ran twice; the same load without preemption is 16.2 s, which the test
asserts too so it keeps measuring something.

WP-48 adds a mixed load: the loop's own model calls and the engines' calls through the model gateway take their
slots from one provider limit, shared over Redis (`app/harness/provider_gate.py`). Eight scheduled loop runs and
eight background engine runs of twelve calls fill a worker of four slots and a provider limit of four; then twelve
loop turns and four interactive engine runs arrive. The provider never serves more than four calls at once, loop
session ready p95 is 2.1 s, an interactive engine run's first call waits at most 0.5 s, and every background run
completes. As WP-44 built it (the gateway's own gate, the loop's calls unadmitted) the same load reaches nine calls
at once, which the control asserts.

On the real stack, `integration-tests/perf/bench_harness.py --profile saturate` measures the same row with the
scripted model (no paid calls): webhook-fired scheduled runs fill the stack, then interactive turns are admitted
among them, and session ready is admission to each turn's first model call. It is built and its parts are
unit-tested; it has not run (the PERF lane's; README "Interactive session ready under saturation").

## Browser latency (QA-AUTO)

What a person waits for in the classic chat, measured in the browser on the harness lane's stack with the scripted
model (no provider in the number): `frontend/tests/e2e/qa/latency.spec.ts` (project `qa-latency`) and, on the real
engine path, `qa/latency-engine.spec.ts` (project `harness-engine`, `run.sh durable`). QA-AUTO measured the new
interface; QA-CLASSIC moved the specs to the classic chat (UI-ASIDE, 2026-11-10) and kept every budget. Each time is
the page's own clock (`performance.now()` at the trigger, a MutationObserver at the result), so it includes the
browser's work and none of the runner's polling. The answer is the answer's own text: the scripted directives also
show in the person's message, the composer and the chat's title in the sidebar, which never count. A p50 or p95 over
its budget fails the spec; `scripts/qa_full.py` reports every
metric against its budget. The budgets are `frontend/tests/e2e/qa/latency-budgets.json`, kept equal to this table
by `scripts/test_qa_full.py`. Each budget is about twice the first measurement on the shared reference host (32
cores, other lanes running), so host noise does not fail a run but a doubling does. One QA-CLASSIC run on a loaded
host missed two p95s (first token 2389 and 2206 ms, turn completion 2809 and 2444 ms, first try and rerun), with
every second sample slow; three runs after it on the same build held every budget. It is STATUS follow-up
QA-CLASSIC-FU-7, not a budget change.

## Volume (QAFINAL-FU-VOL)

Counts, not wall clock, written down before the first measurement (R30-LAT) in

EV-15's 2 s. A store operation over many records makes a number of store commands that does not grow with the
records (a person's deletion request), or grows by at most a stated amount per thousand (a conversation's erasure, in
batches of 1,000); a key rotation reads each record at most once per pass and writes only the records it moves.

## Availability, error budget, RPO and RTO (G-47, C20.48)

Rows 1–19 are latency and resource bounds. This section adds availability and disaster recovery. The targets are
**new**: proposals with a rationale, in the convention of this file. The dashboard and alert rules in
`deployment/monitoring/` measure the run-execution and session-API rows; the DR drill has been rehearsed on a lane,
not yet run on staging. The drill procedure is [DR-DRILL.md](./DR-DRILL.md).

### Targets (new)

| Deployment | Availability, per 30 days | Error budget | Why this number |
|---|---|---|---|
| Helm with a three-member Mongo replica set (`values-cloud.yaml`, `values-eks.yaml`) and two or more app replicas | 99.9% | 43 min | G-47's example. One Mongo member, one app pod or one node can fail without an outage (the chart sets PodDisruptionBudgets on the app and on its own StatefulSets) |
| Helm across three zones (`values-eks.yaml`) | 99.9% | 43 min | as above; a zone loss is also survivable for Mongo (`DoNotSchedule` zone spread). Not raised to 99.95%: the sandbox broker is one replica by design, so engine runs stop while it reschedules |
| Docker Compose, one host | 99.5% | 3.6 h | one host, one Mongo member, no failover: a host or Docker restart is an outage |

Measured as: good minutes over total minutes in the window. A minute is bad when the canary fails or cannot reach
the deployment, or when more than 1% of session-API requests in it return 5xx. Planned maintenance counts unless
it was announced to users.

**Error budget policy.** When a deployment has spent its budget for the window, harness releases to it carry only
fixes for the cause, until the 30-day window has room again. The owner of the deployment (platform / deploy) decides
exceptions and records them here.

**Helm's base `values.yaml` does not meet the harness's journal rule.** Its Bitnami Mongo is two data members and an
arbiter. Node's journal probe refuses a set with an arbiter (`probeJournalDurability`, reason `arbiter`, in
`backend/nodejs/apps/src/libs/repositories/agent-harness/journal-startup/mongo.ts`), so the harness stays off there,
and `GET /api/v1/health` says so in `agentHarness.detail`. Use `values-cloud.yaml` or `values-eks.yaml` (three data
members, no arbiter) for durable runs. FLAGS.md "Where the journal is durable" lists every preset; C-16 FM-10
(`backend/nodejs/apps/tests/cohesion/c16-shipped-truth.test.ts`) runs the probe on each. Changing the chart's own
default is a deferred Helm item (the project tracker).

### RPO and RTO

RPO is how much committed data a failure can lose. RTO is how long until runs work again.

| Failure | What is lost | RPO | RTO (target, new) | Grounded in |
|---|---|---|---|---|
| One Mongo member, three-member set | nothing: journal commits are `w: majority` transactions | 0 | ≤ 2 min: election, then the sweeper requeues runs whose lease lapsed (SLO #6, ≤ 60 s, `max(L,T)+I` = 65 s worst case) | `backend/nodejs/apps/src/libs/repositories/agent-harness/durable-transaction/mongo.ts`; fault suite `test_degraded.py` `ix_dd_1` |
| The Mongo primary on Compose (one member) | nothing on disk if the volume survives | 0 | the time to restart the container, then as above | `restart: always`; Node exits on lost Mongo and restarts (P9 §8.6) |
| Redis | live frames (`harness:live:<runId>`, capped at 8000 frames, 1 h TTL), run-ready hints | 0 for durable state: Redis holds none | none for runs: streaming falls back to Mongo, claims to polling, cancel to the renew poll (SLO #7) | `test_degraded.py` `ix_dd_3a`–`3d` |
| Sandbox broker | sandboxes in flight | 0 for the journal; the engine's turn restarts from its checkpoint | the broker's restart (one replica, `Recreate`) | `ix_dd_4` |
| The Mongo data (all members, or the Compose volume) | everything since the last backup: journal, run queue, receipts, wrapped data keys | the age of the last backup. Target ≤ 24 h | ≤ 4 h from the decision to restore (unmeasured; the drill measures it) | see "Backups that exist" |
| Blob storage (artifacts, journal claim-check payloads, workspace objects) | objects since the last copy | the blob copy's age. Target ≤ 24 h | as Mongo, restored together | as below |
| Sandbox snapshots (optional, `HARNESS_ENGINE_SNAPSHOTS`) | a whole-deployment dump and blob copy carry them; the one-session backup does not | as Mongo and blobs; none for a one-session restore | a session restored on its own starts its next engine turn cold (OP-06: "marked lost") | `backend/nodejs/apps/src/modules/agent-harness/domain/session-backup.ts` leaves `agentSandboxSnapshots` out |

### Backups that exist

- **EKS (`deployment/helm/aws/deploy.sh`):** an AWS Backup plan `<cluster>-daily` snapshots every volume tagged
  `pipeshub-backup=true` at 03:00 UTC (`cron(0 3 * * ? *)`), kept 30 days. That gives the 24 h RPO above, if your
  storage class adds the tag (`deploy.sh` says so when it does not). The S3 bucket has versioning on.
- **Compose:** nothing scheduled. [ADVANCED_DEPLOYMENT.md](../../deployment/docker-compose/ADVANCED_DEPLOYMENT.md),
  "Backup", gives the commands: `mongodump --archive --gzip --oplog`, the `mongodb_replset_key` volume and `.env`.
  Local-mode blobs live in the `pipeshub_root_local` volume. To meet the 24 h RPO, the operator schedules a daily
  dump and a copy of that volume.
- **Helm without EKS:** [the chart README](../../deployment/helm/pipeshub-ai/README.md) gives a `mongodump` and
  `mongorestore` pair. Nothing is scheduled.
- **One session:** the session backup CLI (guides/operator-guide.md, "Session backup and restore") exports and restores one
  conversation's Mongo documents. It copies no blobs, and leaves out audit, leases, snapshots, budgets, schedules
  and memories on purpose. It is for moving or recovering one session, not for disaster recovery.

There is no point-in-time recovery tooling and no backup of Qdrant, etcd or Redis. Qdrant and Neo4j hold the
indexed knowledge, which can be rebuilt by re-indexing; that rebuild is outside this RTO.
