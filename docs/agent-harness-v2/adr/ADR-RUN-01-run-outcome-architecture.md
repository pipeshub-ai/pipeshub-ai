# ADR-RUN-01: Run outcome architecture: one record of what a run produced, typed instructions, provenance by contract

- Supersedes: the per-defect fixes of WP-77, WP-81, WP-82, WP-83 and WP-93 as the design of record. Their behaviour stays; their code moves behind the structures below, and their tests stay as regression cases.
- Related: ADR-OWD-05 (durable run and session), ADR-OWD-09 (policy and approvals), ADR-OWD-15 (data classification), ADR-OWD-16 (workspace ownership), ADR-OWD-11 (adapter contract).

## Context

Six long live research runs found about fifteen harness defects. Each one was fixed where it showed up. Those fixes were correct, but the failures share a few design faults, and every fix added another special case on top of them:

| Run | Defect | Design fault |
|---|---|---|
| 5 | A cut-short run rewrote the report its engine had already written, and the rewrite became the answer | F1 |
| 5 | The writing reserve was shorter than one model step | F4 |
| 5 | 21 of 32 cited sources were dropped by a size bound applied before narrowing | F3 |
| 6 | Cloned repositories went into the saved workspace and broke the 20,000-file commit cap | F2 |
| 6 | A refused save crashed the kernel (an `ExceptionGroup` none of the type-matched handlers caught) and threw away 36 minutes of work | F6 |
| 6 | Working time ignored the run's deadline | F4 |
| 7 | A successful clone made every later web read look private, so the person got 23 approval prompts | F3 |
| 7 | Links into the fetched repositories are not recorded as citations | F3 |
| 8 | The harness's "delegate now" steer reached the root model as if the person had said it; the model copied it into the engine's task, and the engine refused to work | F5 |
| 8 | The person was told "everything it gathered is saved" when nothing had been gathered | F1 |

Each fix was found on a real model run, because no deterministic test reproduced the shape of a long research run (F7).

### Design faults

- **F1: no single record of what a run produced.** The outcome is reconstructed at the end by heuristics: the request text is parsed for a file name several times (`deliverable_name`, `named_deliverable`, `unfinished_deliverable`, `written_deliverable`, `owed_at_end` in `handoff.py`), with placeholder size thresholds, and separate branches for normal end, cut, owed file, child failure and refused save (`kernel.py`, `turn_limit.py`). The words the person reads are composed in at least four modules plus five `[PipesHub]` model instructions in `deep_route.py`. When the branches disagree with reality, the person is told something untrue.
- **F2: one store for three kinds of data.** The workspace store holds the person's files, fetched or cached copies (repositories), and engine bookkeeping, under one set of limits, sync and retention rules. Each new kind of content breaks a limit; skip lists in the sync are the patch.
- **F3: provenance is optional per tool.** A tool result has no required provenance; a tool nobody labelled reads as "unknown" (`own_work_label`). Citations are a separate, web-only pipeline (`citations.py`, `CitationJournal`), and the flow guard derives its own view. Two consumers of the same facts disagree.
- **F4: time and money are computed in several places.** Working time, the writing reserve, the run deadline, step limits and the USD share are derived separately in `allowance.py`, `controller.py`, `profiles.py`, `time_bound.py` and the kernel. A child's limits are not derived from its parent's, and the cut is a hard stop that can land in the middle of a model step.
- **F5: instructions are untyped text.** Harness control messages travel as prose in the conversation, and the delegated task is a brief the model writes in its own words. Nothing stops a harness instruction from being read as the person's, or from being forwarded.
- **F6: failures cross layer boundaries as exceptions.** A store refusal travels up through MCP task groups and the controller; whether the run survives depends on exception types matching.
- **F7: no deterministic test of a long research run.** Unit tests cover each branch; nothing runs the whole shape (clones, many fetches, a 140 KB report, a time cut, a refused save, a child failure) without paying for a model.

## Decision

Seven structures replace the special cases. Each has one owner module and one reason to change (SRP); producers and consumers depend on the structure, not on each other (DIP); a new tool, engine or storage kind extends the system by registering, not by editing branches (OCP).

### D1. Run outcome ledger: the only record of what a run produced

- At admission the harness resolves the request's **deliverable** once (a named file, an answer in chat, or none) and pins it in the run spec. It is never parsed again. The person can see it in the run header ("Writing **report.md**").
- The ledger is a projection of the journal: it derives typed facts from the run's journaled events at each turn boundary and cut (amended 2026-11-10, WP95-FU-1): `ArtifactWritten(path, revision, bytes, state=draft|final)`, `SourceGathered(provenance_id)`, `NoteSaved(path)`, `StepCompleted`, `LimitReached(kind)`, `ChildEnded(status)`, `SaveRefused(reason)`.
- The run ends with one typed **outcome**: `Completed`, `Partial(reason, delivered, missing)`, or `Failed(reason, delivered)`. `delivered` lists what exists (the report revision, the sources, the notes), from the ledger, not from a heuristic.
- One **OutcomePresenter** turns the outcome into everything the person reads: the status line, the answer's opening, the artifact card and the action offered ("Continue" only when there is material to continue from; "Retry" when nothing was gathered). It uses locale keys only. Kernel branches stop composing words.
- One **OutcomeBriefing** turns the same outcome into the parent model's instruction when a child ends. This replaces `ENGINE_FAILED_INSTRUCTION`, `ENGINE_FAILED_WITH_WORK_INSTRUCTION` and their variants.
- Rule: a file the engine wrote is never replaced by a wrap-up. A wrap-up runs only when the deliverable is missing, and writes only what is missing.

### D2. Storage classes: person's files, references, scratch

- **Durable**: the person's files. Versioned in the workspace store, capped, retained, shown.
- **Reference**: fetched or cached content (repositories, mirrored pages, package caches). Stored as an address plus version (`url@commit`, cache key) with its provenance. Materialised in the sandbox on demand and never committed. A later turn that needs it materialises it again from the cache, under the same approval.
- **Scratch**: engine bookkeeping. Kept for the run, never shown, dropped at the end.
- A producer declares the class of what it creates (`ph git clone` registers its checkout as a reference) through one `StorageClassRegistry`. The sync asks the registry and keeps no skip lists. WP-82's `.git/config` marker becomes one registration.
- A save returns a typed result: `Saved(revision)`, `Partial(saved, skipped, reason)` or `Refused(reason)`. It never raises out of a turn (see D6). The cap is enforced on the Python side before the request, with the same constant as Node, pinned by a cohesion test.

### D3. Provenance by contract

- Every tool result carries a required `Provenance { readers: public | principals | unknown, integrity: first_party | external, sources: [SourceRef] }`. The type has no default. The tool registry refuses a tool whose declaration lacks a provenance rule, so a new tool cannot silently produce "unknown".
- A `SourceRef` names a web page (URL, fetched-at), a repository file (`url@commit:path`), a record, a connector item or a memory. Repository files are first-class sources.
- One **ProvenanceLedger** per session is the only store of these facts. The flow guard reads confidentiality from it, citations are rendered from it (web and repository sources alike), and audit exports it. `CitationJournal` becomes a view over it. Narrowing to cited sources happens before any size bound (WP-81), by construction.
- WP-83's decisions D1–D4 stand: public content is public input; private input is labelled by its source; after a private read, an outgoing public request still asks, per tool and destination; repository content counts as outsider-written.

### D4. Run budget tree

- One `RunBudget` is created at root admission: deadline, USD cap, token backstop and step cap.
- A child receives a slice: `budget.child(share)`. A child's deadline is never later than its parent's minus the parent's answer reserve, and its USD comes out of the parent's.
- A **phase plan** is derived from the budget and from step times as they are observed: gather until `write_by`, then write, then deliver. The reserve for writing covers at least two of the turn's longest model steps so far (WP-81) and the reserve for delivering covers the parent's answer (WP-82). The engine is told the plan in its brief ("about 25 minutes; start writing by 17:20"), and is steered at `write_by`. The hard stop is the last resort, and the ledger records what was delivered when it fires.
- `allowance.py`, the controller's wall and deadline arithmetic, `time_bound.py` and the profile limits read from `RunBudget`. None computes its own.
- A cut call is charged a best estimate with cache credit; the budget's hard bound stays uncredited (WP-81 D3).

### D5. Typed instruction channels and a structured task spec

- Every message carries an `origin`: `person`, `harness`, `tool` or `agent`. Harness control goes through the system/developer channel or a tool-choice constraint (to route deep work, force `code_task`). It is never mixed into the person's turn as prose. The model's view marks harness instructions as the harness's.
- A delegated task is a `TaskSpec` the harness composes: the person's request verbatim, their constraints, the pinned deliverable (D1), references to what was already gathered (D3), the budget slice and phase plan (D4). The parent model may add only a `notes` field, which is shown to the child as the parent's notes. Text in `notes` that reads as a harness instruction is dropped, and the drop is logged.
- The child's framing comes from its role: "You are the engine doing this task. You have no code_task tool. Do the work and write the deliverable." A forwarded instruction cannot stop it.
- The five `[PipesHub]` strings in `deep_route.py` become harness-channel messages built from typed values, with their wording in one place.

### D6. Failures are values at boundaries

- Ports to the workspace store, journal, gateways and broker return typed results for expected refusals (cap, conflict, stale attempt, quota). Unexpected exceptions are caught once at the turn boundary, including `BaseExceptionGroup`, and mapped to a typed `RunFault`.
- A **degrade policy table**, in one place, maps each fault to its behaviour. For example, a save refusal keeps the last revision and saves deliverables on their own; a gateway 5xx is retried, then the fault is recorded; a stale attempt stops quietly.
- No fault leads to a from-scratch redrive that discards saved work. A redrive resumes from the ledger.

### D7. A long-run scenario lane, before live runs

- A deterministic **research-run scenario**: a scripted model plays the shape of a long research task. Two clones of about 10,000 files each, 150 fetches, a 140 KB report written in appends, model steps of about 300 s on a virtual clock, a time cut, a refused save, a child failure, a leaked steer in the parent's notes, and a public-read-after-clone sequence.
- It runs on the Docker lane in the round gate, asserting on the ledger, the presenter's words, the approval count, the citations and the budget, with no spend.
- Fault injection covers each degrade-policy row.
- Live runs measure quality and model behaviour. They are not how harness defects are found.

### Consequences

- **UX.** The person sees one honest status line, the report, every source (web and repository), and the action that matches what exists. Public reads never prompt. The time a deep task will take is stated up front.
- **Code.** About six modules shrink: the heuristics and duplicate wording in `handoff.py`, `kernel.py`, `turn_limit.py`, `deep_route.py`, `citations.py` and the limit arithmetic. Four small owner modules are added: ledger, presenter, provenance ledger, budget.
- **Tests.** The WP-77..WP-93 tests stay as regression cases. Each structure gets contract tests, and D7 covers the whole shape.
- **Compatibility.** Journal events are additive. New ledger events are `x.pipeshub.outcome.*` and `x.pipeshub.provenance.*`, under the event catalog's additive rule. Old runs replay through an adapter that derives a ledger from their events. No new Labs flag: the change is internal, behind the existing harness flag.
- **Cost.** About four to five days of work packages and one batched round gate.

### Plan

The structures land in this order, each tests-first:

1. **D7 scenario lane.** It must reproduce run 5–8's defects on today's code (red), then go green as the steps below land.
2. **D5** typed channels and `TaskSpec` (absorbs WP-93).
3. **D1** outcome ledger, presenter and briefing (absorbs WP-81's cut paths, WP-82's save degrade and WP-93's message).
4. **D3** provenance contract and ledger (absorbs WP-83 and the repository citations).
5. **D2** storage classes (generalises WP-82's skip).
6. **D4** budget tree (absorbs WP-81's reserve and WP-82's deadline cap).
7. **D6** fault values, folded through steps 3 and 5.

Work that does not touch the run core continues in parallel: WP-84 leftovers, WP-87 docs, WP-85 supply chain, WP-86 kill switches, WP-90 admin UI. WP-89 (chat UX notices) waits for D1's presenter, and WP-91 (engine runtime) waits for D2 and D4.

## Deviations

WP-96 (D3) makes three scoped choices, recorded in STATUS ("WP-96 evidence"). (1) The required, default-free `Provenance` is on the recorded result (the stamp's record and the ledger's fact). `ToolExecution` carries only the host tool's optional claim, so the 167 places that build an execution do not each name a provenance. (2) `CitationJournal` remains the run's citation state (refs, short ids, blocks), because the answer pipeline restores and numbers it. Its sources reach the ledger through the stamp, repository citations come from the ledger, and its only bounded output for a child is `cited`, which narrows first. (3) Today's loop outside the durable path has no journal, so its flow guard (`legacy_flow_guard`) keeps its per-call notes.

WP-96 (D3), reverted after review: connector results stay first party, as the flow guard read them before WP-96. The approvals rule (approvals follow main #4313; toolset writes run, deletes and sends ask; the flow guard is unchanged) takes precedence over this ADR's "connector results … external integrity". Outsider-written items a connector call cites still mark the run as having read untrusted content (KN-08).

WP-95: the ledger is filled at the engine run's turn ends (its facts are read from the journal's invocations and the workspace head then), not at each tool call; `ChildEnded` is replayed from `child.completed` but not yet recorded live by the parent's join, and the loop executor uses the presenter's words without journaling a ledger. `deep_route.py` still reads a child's answer text (`is_cut_short_fallback`) and words the up-front failed answer itself, where `OutcomeBriefing.brief` now offers the typed reading. (Closed by WP-89: `deep_route.py` reads a child only through `ChildReport.read` and `OutcomeBriefing.brief`. The rest of this paragraph's WP-95 items were follow-up WP95-FU-1, closed by the 2026-11-10 amendment below: deriving the ledger at turn boundaries is the design, not a deviation. The loop's settled outcome for a completed run stays WP-100's open item.) WP-93 records two scoped choices in STATUS ("WP-93 evidence"): plan-gate and context-compiler notes stay injected messages for now (follow-up WP93-FU-2), and `TaskSpec` carries no budget slice until D4's `RunBudget` exists (WP-99 added it). WP-99: Node's hard deadline stays the root's for every child (Node pins `absoluteDeadlineAt` from the parent and moves the tree's together); the child's tighter deadline is its budget's (`of_claim` by depth), which the engine and the loop end their work by, so the Node sweeper remains the last resort. The engine is steered at `write_by` through its own steer channel as a typed `HarnessInstruction` (its words unchanged), not wrapped in the loop's `<pipeshub_instructions>` frame. The time plan notice is journaled on the engine run's own stream: a code_task child's plan shows in the child's own view, not yet in its parent's chat header. (Closed by WP-89: the `ChildInteractions` relay says it on the parent's stream, so it shows on the parent's answer.) Person waits inside a turn pause its working time; a person's wait that suspends the run is held by Node as before (FIX-P1-F3, WAITCHILD).

WP-89 (D1 follow-ups): the words a person reads come from the settled outcome in the web chat, but the presenter's English closing stays journaled (`presented.closing`) and the answer a parent's model and an older Node read stays the whole English text: they are surfaces with no UI, and a rolling upgrade in either order keeps the words (an older Node never takes `presented`; an answer saved before WP-89 renders as saved, and the chat adds no second note when it carries the English words). The loop journals a settled outcome only when it presents a child's answer; its own no-model answer (`turn_limit.cut_short_fallback`) is still the presenter's English text with the chat's cut-short note, as before.

WP-98: re-materialisation is on demand (the engine runs the `ph git clone` the brief names), not automatic at turn start, so a turn that does not need the repository moves nothing; scratch lives in the sandbox only, so a redrive on a new sandbox starts without it (the ledger keeps the facts).
