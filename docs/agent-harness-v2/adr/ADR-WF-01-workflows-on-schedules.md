# ADR-WF-01: Workflows on schedules

- Builds: plan gap G3 of the UI revamp ("Workflows: build by asking, canvas, Runs, Versions, Run now, Dry run"), under the plan's decision D3: in v1 a workflow is a schedule plus an agent plus its run history, built by asking and confirmed with decision cards; the canvas shows steps derived from the set-up and is not a free-form graph editor.
- Related: P8a scheduled runs and TR-02..TR-07 (the schedule, its firings and the firer), G-03 (the dry-run gate), G-07 (the end-of-run summary), OWD-14 (agent versions), ADR-OWD-09 (policy and approvals), main #4313 (deletes and sends ask), ADR-SEC-02 (org binding). Design: `lr-pipeshub` §6B.12 (a workflow does not own a conversation), §6B.20–21 (a run is an answer; the outcome verb comes from the artifact), `WorkflowRow`, `WorkflowRun`, `RunOutcome`, `RunOutput`, `RunArtifact`, `WorkflowVersion`, `WorkflowChat`, `WorkflowStep`.

## Context

The design's Workflows surface needs things a schedule did not have: a status in the design's words, editing, an immutable version per edit, a record of each run with its outcome, a dry run that sends nothing, a way for the chat's agent to draft one that the person confirms, a canvas of steps, the chats that used a workflow, and sharing one as a template. Schedules already had create, list, get, delete, pause, resume, an agent version pin, run now and firings, each checked by `ScheduleService` (its owner everything, an org admin may read, pause, resume or delete, anyone else is told it does not exist).

Two facts constrained the design. A firing document keeps ids, times and reason codes only, never content (REPORT 6.12). And a scheduled run starts a new conversation per firing, so a workflow cannot "own" one; the design says the same for its own reasons (§6B.12).

## Decision

**D1. A workflow is a schedule.** Its id is the schedule's; every rule of who may do what stays in `ScheduleService`, and `WorkflowService` is a read model and a few verbs over it. Three fields join the schedule: `revision` (the version its settings are), `origin` (the chat, run and question call whose proposal made it) and `templateOf` (the workflow a template copy was taken from). A new trigger kind, `manual`, is a workflow that runs only when its owner runs it.

**D2. Status in the design's words**, derived, never stored: `needs_setup` (a template copy, `statusReason: needs_setup`), `ready` (paused with `statusReason: ready`: built, not switched on), `active`, `waiting_for_input` (active with its latest run waiting on the person, or paused by the system for something only they can supply: an agent they may no longer run, a disabled account), `paused` (a person paused it; a disabled schedule reads as paused with its reason), and `building`, which no stored workflow has: it is a proposal in its chat not yet confirmed. Trigger in the design's words: `schedule` (cron), `on_change` (webhook or connector), `manual`.

**D3. Edit writes an immutable version, in one unit.** `PATCH` changes name, trigger, instructions, notices, overlap, cost cap and deadline, each checked as a create checks it; the store moves the schedule from `expectedRevision` to the next and writes the version (`ScheduleStore.edit`, a transaction on Mongo and a unit on PostgreSQL), or writes nothing. An edit that changes nothing writes no version; one made on a version another edit moved past is refused `SCHEDULE_CHANGED`. A version records who (`you`, or `agent` for a draft the person confirmed in its chat), a summary (the person's words, else the fields' names), when, and the settings, whose instructions are sealed as the schedule's are (GAPS-1). A schedule made before versions gets its version 1, as it stood, beside its first edit's. Restore puts an earlier version's settings back as a new version ("Restored v2"); versions are never rewritten. A trigger that becomes a webhook mints a new secret, shown once; one that stops being a webhook drops its credential.

**D4. Each run is recorded with an outcome derived from its journal**, once its run ended: the firer's watch already ends each fired run's watch exactly once (`unwatch`), and that call derives the record (`RunTimelineService.firingResult`) and keeps it on the firing (`ScheduleStore.recordResult`, once). The record is names and counts, never content, so the firing stays content-free: outcome, the rule's reason, the artifact by kind, action and app and how many, the step it stopped at, a dry run's held writes, duration, cost and when. A firing that could not start reads as `failed` (its reason code), a skipped slot as `skipped`. A failure is logged as a run and changes nothing of the workflow's status. The version a firing ran is stamped on it at its creation.

**D5. The outcome rules** (`projection/workflow-run-result.ts`), the first that applies decides:

| Rule | When | Outcome, reason |
| --- | --- | --- |
| R1 | the run failed | `failed`; `run_expired` at its deadline (`deadline_exceeded`), else `run_failed`; stopped at its first failed call |
| R2 | the run was cancelled (a person or an operator stopped it) | `skipped`, `run_cancelled` |
| R3 | a dry run held a write | `sent`, `would_deliver`, every held write listed |
| R4 | a write was made | `sent`, `delivered`; the artifact is the kind of the last write made, counted |
| R5 | a write failed, none made | `failed`, `write_failed`; one declined (a person's denial or a rule's block), none failed or made: `skipped`, `write_declined` |
| R6 | it ended asking the person (`needs_input`) | `skipped`, `needs_input` |
| R7 | it was granted a tool that delivers and called none | `nothing`, `nothing_found` |
| R8 | otherwise | `sent`, `answered`: the chat is the destination, the answer is the artifact |

A write is a call whose `tool.intent` declared `effect: write`; an `execute` stays in the run's sandbox and a `workspace` in its files. A shadowed outcome (G-03) is a held write, never a made one, whether or not the firing is marked dry. What a write made is decided by the tool's verb, its first word (`send_message`, `create_issue`), so a read of messages or files is never taken for a send; `draft` anywhere makes a draft. The kinds are the design's `RunArtifact`: `message`, `answer`, `edit`, `draft`, `records`. The summary line is a key and its facts for the app to write in the reader's language, with the line in English for the API.

**D6. The dry-run guarantee.** A dry run is a manual firing in its own slot namespace (`dry:<key>`), admitted through the ordinary admission path with gate `dryRun` (`ScheduledAdmission.gates`, kept by admission and pinned as `RunSpec.gates.dryRun`; a gate only narrows, so neither the agent's gates nor an answer can drop it, WP-64). The worker's effect runner, which both the loop and the Tool Gateway use, intercepts every write, send, delete or other outside effect and records it as what the run would have done (`tool.outcome.shadow`, with whether it would have asked); a sandbox has no egress beyond the gateways and a repository is never pushed. Reads run for real, against the real data. Node adds: a dry run tells no channel (no in-app, email or Slack notice: it is read where it was started), is not a run of the workflow (not counted, listed apart, `?dryRun=true`) and never advances anything a real run would. Nothing leaves the system.

**D7. Build by asking: nothing is created without the person's confirmation.** The chat agent's tool `propose_workflow` (internal tools) creates nothing: it validates a proposal (`ext/pipeshub/api/workflow-proposal.schema.json`: name, trigger, instructions, notices, agent) and answers a question card, the existing interaction contract (`kind: question`, journaled `x.pipeshub.question.asked`, the run ends `needs_input`) with "Set it up / Change something / Not now" and the proposal as `workflow`. Confirming is the person's own authenticated request, `POST …/workflows/proposals/{conversationId}/runs/{runId}/{toolCallId}/confirm`: Node reads the proposal from the asking run's journal (never from the request), only for the run's own person, only from a `propose_workflow` call, checks it as any create, and makes the workflow `ready` (switched off, for a dry run first), version 1 by the agent, the chat its origin, logged as that chat's "created". A second confirm answers the same workflow (`origin` is unique per org). The person then answers the card in the chat, so the agent carries on.

**D8. A workflow does not own a conversation** (§6B.12): `originChatId` and a usage log, one row per chat and workflow with its latest use (`created`, `edited`, `ran`, `asked`), the creating chat marked for good. A request names the chat it was made from (`conversationId`), which the caller must be able to see.

**D9. Steps are derived, not stored** (D3): trigger from the schedule; read from the agent's knowledge, its tools that change nothing (one step per app) and web search; one reason step; ask from the agent's plan-approval gate and from the sends and deletes that ask under the rules every org starts with (main #4313); act from its write tools, one step per app. The agent's set-up is read through the agents export with the caller's own credential, so the canvas never shows what they may not read; an agent they may not read draws only what the schedule says.

**D10. Sharing shares the template.** Its owner offers it to colleagues of the org (each a live member). A recipient's accept makes their own copy from the workflow as it is then, `needs_setup`: nothing runs, by schedule, run now or dry run (the service refuses `SCHEDULE_NEEDS_SETUP`, and the firer refuses such a firing should one reach it). Finishing setup is switching it on: resume pins the agent version they may run. A connector or webhook trigger becomes manual in a colleague's copy, since a connector trigger is an admin's to set and a webhook secret is never copied. The share keeps references only; a source that is gone is not offered.

**D11. A run's changes are pushed to its owner (UI-B5, UIP5-FU-1).** The firer tells the workflow's owner, on the app's existing notification socket (`workflowRun`, `workflow-run-change.schema.json`, the transport the Inbox count already uses), whenever one of its firings settles (admitted: running; refused: failed; skipped), its run starts or stops waiting on them (the firer's watch reads each watched run's status every tick and tells only a change of state), and its record is kept (done, with the outcome). Names and states only, never content: the screens re-read `…/runs` once per change instead of every few seconds. Best effort: a socket that throws loses the push, never the run or its record, and a change nobody was connected for is in the list. A dry run is pushed too: it is read where it was started. One state per firing is remembered per replica (at most 10,000, the oldest forgotten first); another replica that checks it tells it once more, which a client reads as no change.

**D12. `about` and the owners' names (UI-B5, UIP5-FU-2).** A workflow has an optional `about`, one plain line of what it does (at most 500 characters), set from the confirmed proposal's `about`, by `PATCH` (`null` drops it) and copied into a colleague's template copy. It is a versioned setting like the name (an edit of it writes a version, "Changed what it does"; restore brings it back) and plaintext like the name: unlike the sealed instructions, everyone who may see the workflow reads it, so a share and an admin's view can say what it does. A share's `about` is the workflow's own, else its trigger in English (as before). Views and shares name their owners (`ownerName`, `sharedFrom.ownerName`) from the org's own user records, resolved on the server in one read per answer; someone no longer a member is left unnamed, and names that cannot be read leave every answer whole.

**D13. A question asked from the workspace is logged when its chat is made (UI-B5, UIP5-FU-3).** The composer's turn names the workflow (`workflowId` on the chat and agent create routes); once the agent harness admits the turn, the chat it made is logged as the workflow's `asked` use (`WorkflowService.askedFromTurn`, after the same read check as every workflow route). The log never refuses or delays the turn: a workflow the caller may not read is left unlogged and logged as `workflow.turn_use_unlogged`. Today's loop never sees the field; a turn it serves logs nothing (workflows need the harness).

**D14. Bulk pause, resume and delete (UI-B5, UIP5-FU-4).** `POST …/workflows/bulk {action, ids}` (1 to 50 ids): each workflow is checked on its own, only its owner may (an admin is refused `SCHEDULE_FORBIDDEN` for that one; anyone else finds it not there, as the single routes say), then the schedule service's own verb runs with every rule it holds; one refused changes nothing of the others. One result per id, in the order asked, a repeated id once; a refusal carries the wire code the single route answers with. Repeating it changes nothing more (pause and resume already answer an unchanged workflow; a deleted one is not found). A store failure answers the whole request 503; what changed before stays changed, and a retry is safe.

**D15. Run records name their action by stable keys (UI-B5, UIP5-FU-5).** Every action a run record names (its artifact, the step it stopped at, a dry run's held writes, the summary line) carries `actionKey`: the tool's own name in snake case (`send_message`), its verb (`send`) and its app's machine key (`slack`), so the app words it in the reader's language; `action` and `app` stay as the English fallback. The keys are derived from the tool id when the record is read (`toolKey`, beside `describeTool`), so records kept before them have them too and nothing stored changed.

## Deviations

- UI-P5: an edit's `input` is merged over the stored template, field by field: the Workflows screen edits the instructions alone (the view shows nothing else of the template), so the model, tools and capabilities a schedule was made with stay unless the edit names them (`UIP5-B1`).

- A tool's kind of change is read from its name's verb. A tool whose name has no verb the table knows counts as `edit` when it writes, and as delivering nothing for R7. A tool-declared action type (OWD-18's `writeIdentity` types are per action, not per tool) would be the stronger source once tools declare one.
- R7 decides "nothing to send" from the run's grants: an agent granted a send that answered without sending had nothing to send; an agent that answers by design but also holds a send tool reads the same. The derived steps show which it is.
- The ask step draws the rules every org starts with (sends and deletes ask), not each org's own approval rules or a person's tool rules; the approvals themselves always follow the org's rules.
- A workflow's run and its output live in the run's own conversation (one per firing): the record says what it did; the full answer or message is one click away there. The design's `misses` ("what it left out") are not derived: no journal fact says them.
- The record of an engine run counts the parent's calls; a `code_task` child's own writes are its own run's.
