# ADR-OWD-07 — Tool identity, naming and catalog pinning

## Context

[OWD-7](../one-way-doors.md) fixes how tools are named across PipesHub toolsets, MCP servers and dynamic tools, and how the catalog is versioned in a session. Names live in transcripts, approvals, policies, audit, skills and replay goldens, and prompt caches need a byte-stable tool prefix.

## Decision

Adopt OWD-7 with two names per tool:

- **Model-facing names follow the spec**: `pipeshub_<toolset>_<tool>`, with MCP tools prefixed by their server instance slug.
- **The internal id stays the instance-scoped canonical id** built in D7 (`<source>@<instance>/<tool>`). It is what journals, approvals and policies already store, so history is not rewritten.
- The catalog is pinned per session and ordered deterministically. An unavailable tool stays listed and returns an actionable error.
- Risk class in the tool metadata contract includes `destructive` and `financial`.

## Deviations

These contradict OWD-7 with no recorded decision, so **the code changes**, in WP-22 POLICY-EXT (Wave 5):

1. Model-facing names have no `pipeshub_` prefix. **Built** in WP-22, off for every engine: the recorded cassettes and scripted harness cases pin today's names, and tool results still name tools the old way (`knowledgegraph__fetch_record(...)` hints), which the gateway answers. Turning `spec_tool_names` on for an engine waits on measuring that engine on them. The native loop keeps today's names for the same reason; its tool list is main's (`app/agents/agent_loop/tool_loader.py`).
2. The engine catalog was pinned per run. **Closed** by WP-22 (2026-10-29): the engine's gateway list is pinned per session, as the loop's.
3. Risk is effect plus sink; there was no `destructive` or `financial` class. **Closed** by WP-22.

Decision, R26-LAZY (2026-11-11), refining D-DISC-2's next step (MCP tools are loaded lazily, on demand):

Root cause. A harness run could know an MCP tool only as a live-listed adapter in its registry, and every claim step assumed that object: the catalog's grant check, the effects (tags from the listing's annotations), the capability observation, the tool port, the engine's list, the approval gate's lookup. On the default chat the grant itself (the tool names) was made from a listing. With no stored listing on the harness path (the hub's process cache only, never main's per-sign-in catalog) and no "list on first use" seam, admission and claim both listed every attached server on every turn.

- **D-LAZY-1. Stored knowledge comes before first use.** Until a run lists a server, it knows it from the instance (name, description), its catalog entry and this sign-in's stored tool catalog: main's `tool_cache` (per instance and sign-in, credential-stamped, target-fingerprinted, 24 h), one store for the classic chat and the harness. Every harness listing writes what it found there, unless it is unchanged and fresh (no write per run). Nothing ever lists to fill it, and nothing a run calls is taken from it: it names, ranks and counts (`app/agents/agent_loop/mcp_known.py`).
- **D-LAZY-2. Admission lists nothing.** A saved agent's servers grant the attachment's tool names without digests. The default chat grants each authenticated server whole: `x.pipeshub.mcp[].tools: "at_first_use"`, the tools its first listing in the run offers. Node sends that only while a live worker advertises `mcp_first_use`; an older worker gets today's spec. Under an edition's approval gate, admission pins the stored approved manifest, as before, and "offered now" (WP-79) is checked at first use. A sign-in missing from the stored records keeps its admission notice.
- **D-LAZY-3. The claim registers servers, not listings.** Each granted server is one lazy group (`LazyMcpServers`, `app/agents/agent_loop/mcp_lazy.py`, through the registry's `ToolsetProvider` seam): its granted tools are named as a listing would name them (`exported_tool_name`) and described by the stored catalog's one-liners, and none is built. Until first use they are deferred: in the catalog (no effect, schema or digest read), in the tool port (named in its grant, described once built, built before a call of one runs), and in the capability observation (a lazy server is never in `capabilities.observed`; its pin holds it, D-LAZY-5). The claim's item check reads the run's own pins for MCP (vacuous there): the pins are enforced at first use. A run whose model could not search for a tool keeps the claim's listing and every check on it (WP-79, WP-84, D8, D9): lazy disclosure turned off by the operator (`PIPESHUB_ENABLE_LAZY_TOOLS`), an agent that chose to list every tool, a deep run (`disclosure.mcp_at_first_use`).
- **D-LAZY-4. First use is one awaited step, and MCP is always deferred.** A server is listed when the run first loads one of its tools (`search_tools` or `fetch_tools` answering it: the registry builds what they answer, `materialize_many`) or calls one (the kernel's step before it plans a turn's calls, `DurableKernel.prepare_calls`, and the tool port before it runs a deferred tool). `list_toolsets` describes a group from the stored one-liners and lists nothing. A call is a first use whatever its spelling (R27REST-FU-2, owner: tools load lazily on demand, and a direct call by name is a demand): the run's exported name, the server's own name for its tool (`ph tools call create_ticket`, a name the engine has from the source list or the task), an engine client's `<server>__` prefix, or the one granted name it ends. One step resolves it (`LazyMcpServers.prepare`) at every direct-call entry: the kernel before it plans a turn's calls, the Tool Gateway's `tools/call` and `call_tool` before it resolves the call, and the tool port before it runs one; the call then runs as the tool it names, under that tool's own per-call rules. A name no tool known to the run's servers has lists only the servers granted whole that name no tool yet, the only place it can be, and stays refused when none has it. One listing per server per attempt, shared by concurrent callers. MCP schemas are never in a first request, whatever the disclosure threshold: an eager grant with MCP tools is disclosed lazily with every other group of it pinned, so only the MCP groups wait behind the search (`Disclosure.decide`). A small MCP grant costs one search step before first use; a turn that never uses a server sends it nothing. Connector toolsets are unchanged. The goal step's grounding check (ADR-RUN-03 D1) is a first use too (QAFINAL-FU-GROUNDLAZY, 2026-11-12): it picks a server's search from what is stored of it (read-only by its hints, the subject alone fits its schema, the person's rule runs it unasked) and builds only that through `LazyMcpServers.prepare`; what the listing serves is checked again before the call. A server granted whole with nothing stored is listed to learn its tools; a server with no such search is not listed.
- **D-LAZY-5. The pin is journalled at first use and holds for the run.** The tools the first listing served (those the scanner passed, under approvals only the approved ones) are journalled as their descriptor digests in the run slot `mcp.pins` before any result reaches the model. A resumed attempt lists again only on use, pinned to that slot: a tool now at another digest is not registered and its call is refused (`ToolChanged`), as D-MCP-5 refuses one at the claim; a tool added since first use is not granted. Why the property holds: no schema reaches a model and no call is made before the listing that is pinned, and every later listing in the run is checked against it. What moved is only when "what the server offers" is read, from admission to first use; between them no model has seen the tools, so the trust is the one today's admission listing already gave. A child run is pinned to its parent's pin of every server its parent has listed, and pins at its own first use only a server its parent has not listed (D-LAZY-8, R31HOT2).
- **D-LAZY-6. A failed first listing and the scanner act at first use.** Sign-in refused, unreachable, no tools, all flagged, or some tools held: the same per-server notice as before (`mcp_unavailable` with its reason, `mcp_tool_held`), journalled once per run as `x.pipeshub.run.notice`, and the meta tool or the call answers with the same words; the run goes on without the server. Per-call rules (Ask, Allow, Block, class defaults, the flow guard) are unchanged.
- **D-LAZY-7. The source list is stored metadata only.** `ConnectedSources` reads the grant, the instance, the catalog entry and the stored catalog. `JobTask.sources[].tools` is optional: a server granted whole and never listed has no count, not 0.
- **D-LAZY-8. A child holds what its parent holds whole (R31-HOT, 2026-11-12).** Root cause of a manual-test report (every `code_task` job of the default chat ran with `mcpServers=0`, Atlassian Rovo gone): what a parent "holds" was read from `grants.tools` alone, in the ⊆ rule's tools dimension and in the child's MCP pins (`childRunSpec`: a server followed only the `mcp@<instance>/<tool>` ids the child kept). A server granted whole names none of its tools there, so every child dropped it and could not ask for one of its tools either (`CHILD_GRANT_TOO_LARGE`, a deep sub-agent naming a listed Rovo tool). One answer now, `heldTools` (Node `domain/child-runs.ts`, Python `harness_core.journal.children`): a spec holds its tool grants, and for a server it holds whole the server (`mcp@<instance>/*`) and any one of its tools. A request that names no tools (a `code_task` job, a harness agent) holds every server whole that its parent does, pinned exactly as the parent's entry; one that names the server whole keeps it whole; one that names tools of it is pinned to exactly those (an entry without `tools`, its digest bound to the parent's whole pin, and one tool grant each), never the server; one that names neither drops it. Nothing widens: a server pinned by its tools cannot be asked whole, and a narrowed child's own children hold only its tools. A child that holds a server whole requires `mcp_first_use`, as its parent did. Per-call rules hold for the child's calls as for the parent's (Ask, an explicit Allow lifting the engine default under D-ALLOW-1, Block, an org rule, the flow guard), because they are decided per call on the child's own tool, whether it listed the server itself or holds its parent's pin (below).   - **Carried pins (R31HOT2, 2026-11-12).** A child inherits the first-use pins of the servers its parent has listed, rather than listing them again at its own first use. Why: the child then sees exactly the tools its parent saw and approved against, and its first use of a server costs no listing round trip on the job's critical path. How: the parent's kernel carries the run's pins (`DurableKernel.mcp_pins`, the attempt's `LazyMcpServers.pins`) on its spawn as `mcpPins`, only to a Node that advertises `child_mcp_pins`; Node pins each kept server's entry with `pins` (`x.pipeshub.mcp[].pins`: tool by the server's own name to its descriptor digest) narrowed to what the child holds, and such a child requires `mcp_carried_pins`. The parent's own spec pin, when it has one (it inherited it), wins over what its worker reports: Node trusts its pinned spec, so a worker can narrow a child but never widen it. Never widen: a server held whole that the parent has listed holds exactly its pin, so a child asking for a tool of it outside the pin is refused `CHILD_GRANT_TOO_LARGE`; a child narrowed to named tools keeps only their pins; a pin for a server the parent does not hold is dropped. The child's worker holds such a server to the pin as its own (`LazyMcpServers(carried=…)`: a tool outside it is not the run's, one at another digest is refused `ToolChanged`, nothing is journalled again) and, under the MCP hub, builds the tools from the sign-in's stored catalog that the parent's listing wrote (D-LAZY-1) when every pinned tool is there at its pinned digest, through the same admission (approvals, the scanner, the attachment); the digest is the trust, so a stale or rewritten catalog is never used and the server is listed instead, held to the pin (`MCPToolProvider._stored_pin`). With the hub off main's session already reads the stored catalog and lists once before its first call. A parent that has not listed the server carries no pin, and the child lists at its own first use and pins that for its own children. A parent that lists at the claim (a deep coordinator, lazy disclosure off) carries that listing the same way, for the tools it still holds (R38IDENT-FU-13, 2026-11-13, `McpSource.pins`): before, only a first-use listing was carried, so a deep run's sub-agent listed every server again on its own critical path, and a STDIO hub server that did not answer that second listing left each of its calls `not_available` (gate line `J-agent.deep-seeded-hub`). Decision, R49-PLAN (2026-11-14, R49PLAN-1), on the plan tool:

- **D-PLAN-1. Every root loop turn the chat starts may show a plan.** Finding: a long multi-step request on the default chat kept no plan (no `write_todos` offered, no `task.*` journaled). Root cause: UXR-B1 offered `write_todos` to root `react` and `auto` runs only, to keep `quick` byte for byte; but `quick` is the only strategy the chat offers (`AGENT_STRATEGIES`), so the default chat's Agent mode (the system assistant, ASSIST1) and every saved agent never had a plan. Options weighed: (a) offer it only when a request looks multi-step — rejected: a classifier is either a model call before the first token or a brittle heuristic, and a tool list that changes from turn to turn misses the provider's prompt cache on every switch; (b) a planning model call — rejected for the TTFT reason UXR-B1 gave; (c) always offer it on root loop turns — chosen: the tool's own description already limits it to work of three or more steps and never before a direct answer, so a short answer has no plan and makes no extra call, and the cost is a fixed, cached prefix. Now `PLAN_MODES` is `quick`, `react`, `auto` (`app/harness/assembly/plan.py`); never the built-in assistant's search modes (one source, one answer: requests unchanged), deep mode (`create_plan`) or a deep child.
  - **Deep work still goes to the engine.** On a run that may hand off (`code_task` offered, DEEPROUTE) the description adds: "Work you hand off with code_task is planned there; do not plan it here first." The engine journals its own todo list as its run's `task.*` (UXR-B1), so the chat never shows the same work planned twice.
  - **The plan is shown as the plan, never as a tool.** The checklist the classic chat already draws (CTL-3, `PlanChecklist`, plain statuses Done / In progress / To do / Dropped) reads `task.*`. The `write_todos` call itself is hidden from the steps and the activity drawer (`HIDDEN_TOOLS` in `app/harness/presentation.py`). A chat saved before that, and an engine's todo tool in its activity lines, read "Updated the plan" (`TOOL_DISPLAY` builtin `updatePlan`, i18n `toolNames.updatePlan` in all ten locales), never a tool id.
  - **Cost.** Default chat Agent mode, measured on the assembled first request: tools +693 chars (the `write_todos` schema), system prompt +64 chars (its listing line), about 190 tokens, part of the cached prefix from the second request on; +78 chars more where `code_task` is offered. Quick requests otherwise unchanged; the search modes 0. The TTFT pair UXR-B1's B1-23 measured is re-run on a lane (R49PLAN-FU-1).
