# ADR-SEC-06: Release trust outlives a stolen key, an air gap and an operator's download

- Findings: R41SUPPLY-FU-6 (`RELEASE_KEYS` compiled in, with no revocation list and no not-after; SEC-D-04 fix 5),
  R41SUPPLY-FU-7 (an air-gapped install pins cached digests but checks no signature), R41SUPPLY-FU-10 (operator
  scripts download kubectl, helm and the AWS CLI with no pinned checksum).
- Related: ADR-SEC-01 (one trust model, the release root), ADR-SEC-05 (signed images, DOWNLOAD-HASH), OWD-8 (release
  keys are code), [SUPPLY-CHAIN.md](../guides/SUPPLY-CHAIN.md), [RELEASE-CHECKLIST.md](../RELEASE-CHECKLIST.md).

## Context

ADR-SEC-05 gave the delivery chain a root, but three edges still took something on trust for ever. A release key
(`RELEASE_KEYS`, which signs the vendor rules, their sign-in hosts, the ACP profiles and engine-image attestations)
could be revoked only by shipping a release, and installs that do not upgrade trusted a stolen key indefinitely. An
air-gapped host, which cannot ask a registry for signatures, loaded whatever archive it was handed. And the EKS tool
installer "checked" kubectl and helm against sums read from the same server it downloaded them from, and the Linux
AWS CLI against nothing.

The common fault: each check was anchored on something the attacker could also replace or that never expires.

## Decision

### D1. A release key has a not-after, and a signed list revokes it

- **Not-after.** `RELEASE_KEY_NOT_AFTER` (Python `harness_engines/vendor_rules.py`; Node's mirror is generated by
  `sign_vendor_rules.py`) gives every key an instant, at most three years after the key was made (a test holds the
  bound). From then nothing it signed verifies, in either language: the trusted set is `RELEASE_KEYS` minus expired
  minus revoked (`harness_core/supply_chain/release_keys.py`, `domain/release-keys.ts`). The shipped key's is
  `2029-11-10T00:00:00Z`. A release ships the next key well before; an install that has not upgraded by then loses
  model access with `vendor_rules_invalid`, which is the point: a stolen key expires on its own on a host that never
  hears of the theft.
- **The list.** `pipeshub.revoked-keys/1`: `{schema, issued, revoked: [key ids]}`, detached-signed by a release key
  like other release data. It only narrows trust. It is applied only when it is newer than the list in force, at most
  a day ahead of the clock, and keeps every key that list revoked, so no later or earlier list brings a key back. Its
  signer must be in force under the list in force (listed, not expired, not already revoked) but may revoke itself:
  with one release key, the owner can revoke it only with it. A thief holding a key could revoke the good key; that
  fails closed (the owner then revokes the stolen key too, and ships a new one), never open.
- **Shared vectors.** `contracts/release-keys/revocation-vectors.json`, written by
  `scripts/engines/release_key_vectors.py` (deterministic throwaway keys, `--check`), is run by Python and Node, so
  the two verifiers cannot drift.
- **Where a process learns of it.** The harness worker fetches the list (`PIPESHUB_REVOKED_KEYS_URL`; default the
  repository's `revoked_keys.json` and `.sig` in `contracts/release-keys/` on `main`; empty or `off` disables) at start in
  the background and every 6 h, and stores the newest valid one under `/services/harness/revokedReleaseKeys` as the
  last good copy. The worker and the sandbox broker read that copy before they verify anything, and Node every 10
  minutes; each checks the signature itself, so the store is trusted for availability only. A release may also ship
  a list in the package (`revoked_keys.json(.sig)`), the floor both languages start from.
- **The fail-safe.** Unreachable, offline or nothing published: keep the list in force and go on. Revocation is the
  fast path for an install that can hear of a theft; an air-gapped one is bounded by the not-after, which needs no
  network. Failing closed on an unreachable list would stop every air-gapped and firewalled install for a fetch that
  carries no new risk (nothing fetched can widen trust). A list that does not verify, is older, drops a revocation or
  is dated ahead: refused, logged, the list in force stays. After 7 days without a successful fetch (fetching on),
  each refresh logs `release_keys.revocations_stale`. Only a revoked or expired key fails closed.

### D2. The air-gapped bundle is signed by the release and checked offline before `docker load`

- `release-publish.yml` `offline-bundle` (after `sign` and `promote`, signing on, per architecture): the signed app
  and sandbox images by digest, saved, gzipped and split under the 2 GiB asset limit; a line-based manifest
  (`pipeshub-offline-bundle 1`, version, arch, the tags it holds, each part by SHA-256) signed keyless with
  `cosign sign-blob --new-bundle-format` (or the vault-held key); checked with install.sh's own verify function, then
  attached to the release with `sigstore-trusted-root.json`.
- `install.sh --offline-bundle MANIFEST`: `cosign verify-blob --offline` against the Sigstore trusted root the
  installer pins by SHA-256 (`deployment/docker-compose/sigstore-trusted-root.json`, beside it or the manifest; the
  copy beside the manifest is accepted only with that digest, so a swapped root cannot vouch for a swapped bundle),
  on the release identity; then each part's SHA-256; then `docker load`; then each named tag. Any failure refuses
  with what to do, and nothing is loaded. Under `PIPESHUB_IMAGE_VERIFY=warn` a bundle still needs its signature (the
  release signs every bundle it publishes); `off` skips it and keeps the checksums. An image ID is not compared after
  the load: it depends on the host's image store, and the parts are the signed bytes already.
- cosign must be on the host (the pinned cosign image cannot be pulled offline); the refusal says where to get it.

### D3. A script an operator runs installs only what it checked against a pin it carries

- `install-deps.sh` pins helm, eksctl and the AWS CLI (Linux zips and the macOS package, whose signature is still
  checked too), and kubectl per cluster minor (1.33 to 1.36; another minor is refused with what to do), with SHA-256
  per platform. No version or sum is read from a download server. The kind setup pins kind and kubectl; install.sh's
  gVisor checks the tarball against a carried SHA-512 (another release needs `PIPESHUB_GVISOR_SHA512`).
- `DOWNLOAD-HASH` covers shell scripts: a download the script then installs, unpacks, marks executable or runs needs
  `sha256sum -c` (directly or in a function of the script) against a pinned value; a sum from `$(curl …)` or a fetched
  `.sha256`/`.sha512`/checksums file is refused, because it proves the transfer, not the bytes.

### Alternatives not taken

- **Fail closed when the list is unreachable.** Bricks every air-gapped install for no gain: nothing a fetch returns
  can add trust, so a missed fetch only delays a narrowing the not-after bounds anyway.
- **A separate revocation key.** One more owner-held secret and ceremony; self-revocation plus monotonic lists give
  the same safety with the key that exists.
- **Image IDs in the bundle manifest.** They differ between Docker's classic and containerd image stores; the signed
  part digests already fix the bytes.
- **Trust the trusted root shipped with the bundle.** An attacker who swaps the bundle swaps the root too; the pin
  lives in the installer the operator already trusts.

## Deviations

- No revocation list is published yet, and none is packaged: signing one needs the release key (owner). Until then
  the fetch finds nothing (404) and the not-after is the only bound.
- The ACP profiles are read once per process (`packaged_acp_agents` is cached); a key revoked later takes effect for
  them at the next restart, for everything else at the next verification.
- The offline bundle's keyless signing and offline check have not run on GitHub (no signed release yet), and cosign's
  `--new-bundle-format`/`--trusted-root` flags are checked only there; the workflow runs install.sh's own check before
  upload so a mismatch fails the release, not a customer's install (R43SUPPLY-FU-1).
- The pinned Sigstore trusted root was taken from the public-good TUF repository's `targets.json` (version 14) over
  TLS, not by walking TUF's root chain; Sigstore's rotations need the file and its pin replaced (RELEASE-CHECKLIST.md).
