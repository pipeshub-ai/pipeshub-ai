# ADR-OWD-01 — Secrets never enter the sandbox

## Context

[OWD-1](../one-way-doors.md) asks that no model key, connector token, git credential or PipesHub token is ever present in a sandbox. Once harness configs or user scripts expect a key in env, it cannot be taken out, and every snapshot taken with a secret inside stays contaminated.

## Decision

Adopt OWD-1 as written. Credentials are added on the way out by the egress proxy and the gateways. The sandbox holds only placeholders and base URLs that point at the proxy, and a placeholder is bound to its sandbox and run attempt.

## As built

Audited at `959c3bda72`. Decision rows: the v2 architecture report §5.1 #5, D8, D22; [ARCHITECTURE.md](../ARCHITECTURE.md) §3.1 #3; P5.4 egress proxy.

- Sandbox containers are created with no environment: `backend/python/app/harness/sandbox/docker_broker.py`.
- Placeholders are minted per attempt in `backend/python/harness_core/engines/controller.py`. The proxy swaps them for run-bound tokens on gateway routes only: `backend/python/harness_core/sandbox/egress/proxy.py`.
- Passing in the gate:

  - `backend/python/tests/unit/harness/engines/test_e2e3_tool_matrix.py::test_cn_a_connector_read_and_write` (docker.xml, three real engines)
- The C-13 secret scan `backend/python/tests/cohesion/test_c13_sandbox_reaches_only_gateways.py` (docker.xml) runs since WP-06 rebuilt the `pxh-sandbox:x1` image.

## Deviations

The audit at `959c3bda72` found the code contradicting OWD-1 in two places. Neither was a deliberate exception, so **the code changed**, in WP-06 SECRETS-RESIDUE (Wave 2):

1. **Legacy `run_code` registry and database passwords** (`backend/python/app/agent_loop_lib/sandbox/coding/credentials.py`) were written into the sandbox as a 0400 file. Now they never enter it. An install from a registry configured with a password gets an egress allowlist of the registry's host, and its pip or npm sends a placeholder as the Basic password. The egress proxy holds the credential sealed in the route, ends the TLS with its own authority (the install first trusts it), and puts the real credential on each request (`CredentialInjection.BASIC`). A PostgreSQL run reaches the database through the proxy's database route: the proxy signs in with the sealed credential (SCRAM-SHA-256, MD5 or cleartext) and psql is never asked for a password (`backend/python/harness_core/sandbox/egress/postgres.py`). Without the egress proxy (`SANDBOX_MODE=docker`) a credentialed registry or database is refused with the reason. Local mode runs no sandbox and keeps its password file, removed before user SQL.
2. **MCP-runner secrets** (D23, P5.10 MD-5) were in the server process's environment. Now the server gets a placeholder for each secret, and each listed host gets a substitution route carrying the secret sealed (`CredentialInjection.SUBSTITUTE`): the proxy puts the secret where the placeholder appears in a header or the URL, inside TLS it ends. The bridge first trusts the proxy's authority. A runner with a secret is refused when the deployment has no key to seal it with. A secret a server uses locally rather than on its requests (a request signature, a local database password) cannot work under OWD-1; such a server has to run as an HTTP MCP server instead.

How a credential reaches the proxy: the trusted caller seals it with the deployment's `SECRET_KEY` into the route's `credential_ref` (`backend/python/harness_core/sandbox/egress/sealed.py`, AES-256-GCM, the placeholder as associated data). The broker, its logs and the proxy's durable state see only ciphertext; the sandbox never sees the spec. The proxy's TLS authority is per deployment, kept sealed in the proxy's durable state (`backend/python/harness_core/sandbox/egress/interception.py`), and a sandbox reads its certificate from the proxy.

The `pxh-sandbox:x1` image was rebuilt from `deployment/sandbox/Dockerfile` so the C-13 scan runs in the gate.

**C6.10 (SEC-EG-11)** is not applicable yet: engine sandboxes have no setup phase, so they get no clone, install or setup secret at all. Separate setup and agent-phase egress policies, and the setup-secret wipe OWD-1 describes, come with the git workflows that add a setup phase (GIT-FLOW, P1). WP-26 added it: a run's repository is cloned under a setup policy whose read credential the egress proxy injects, then the same sandbox is re-bound to the agent policy (session-branch pushes only) and checked before the engine starts; the token is never in the sandbox in either phase (`backend/python/harness_core/engines/git_checkout.py`).

## Owner amendments

- **2026-10-26, SIGNIN exception.** When an admin turns on Claude sign-in, Claude Code's own login token lives in that user's own sandbox, for their own interactive turns. PipesHub never collects, stores or relays it. No other secret is excepted. See [ADR-OWD-17](ADR-OWD-17-vendor-subscription-logins.md) and [ARCHITECTURE.md](../ARCHITECTURE.md) §4.6.4.
- **2026-11-07, WP-103: a credential shape in a model call's context is hidden, not a refusal of the call.** Evidence: a long live research run's Codex child. After 17 minutes the engine printed its notes of PipesHub's public personal-access-token page, whose paste block holds an example token of the `pipeshub_pat` shape (the forbidden list's 8th pattern, the vector's 10th); the next model call carried it and the egress proxy refused the call (`forbidden_pattern`), so the run ended "the coding engine ran into an error". First principles: the tripwire exists so that a credential never leaves through the proxy; the body of an engine's call to the Model Gateway is the run's own context going to the org's model, and public pages and repositories routinely hold documentation examples of these shapes, so refusing the call ends long runs on a false positive while hiding the shape keeps the guarantee. **Rule.** (1) The body of a request to the Model Gateway alias, in the clear: each forbidden shape (the vector's and the policy's own) is replaced with `[credential hidden by PipesHub]` and the call goes on; a match holding JSON syntax is refused, never rewritten (`policy.hide_in_body`). The Model Gateway applies the same rule to a parsed body (`hide_forbidden_in`), so a path that reached it without the proxy behaves the same. Each hide is logged by kind (`egress.secret_hidden`, `model_gateway.secret_hidden`) and journaled once per run, gateway and kind as the audit event `gateway.secret_hidden` (kind only, never the value). (2) Unchanged and refused: a shape in a header, a URL or the `Authorization` of any request; any body to the tool gateway (a tool call's arguments are effects, which must never be silently altered), an allowed website or a git host; the run's live gateway token anywhere (`token_replayed`); another sandbox's or another destination's placeholder. (3) A refusal of the secret class tells the engine in words with the typed code `[gateway:secret_blocked]`; the model gateway's `forbidden_credential` (a key in a call's header) is the same class. The kernel cuts the run short as `secret_blocked` (ADR-RUN-01 D1's presenter words it "PipesHub blocked a request that looked like it contained a secret", in every locale), keeping and answering from what was written; with nothing gathered it fails with `secret_blocked`. Rejected: provenance-based exemption (ADR-RUN-01 D3) — the proxy sees bytes, not sources, an engine's shell output mixes them, and a real key committed to a public repository is still a real key; letting the shape through — a real secret must still never leave. No new hole: what reached the provider before (nothing, the call was refused) now reaches it without the shape; encodings stay out of scope as before (a tripwire, not DLP).

**Accepted** (2026-10-26). Built for engine sandboxes with the SIGNIN exception; since WP-06 the legacy code sandbox and MCP runners hold placeholders only, the proxy injecting their credentials.
