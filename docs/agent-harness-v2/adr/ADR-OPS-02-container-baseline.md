# ADR-OPS-02: Every container starts from one hardened baseline, declared on the service

- Findings: SEC-D-02 (the egress proxy and the sandbox broker run as root with Docker's default capabilities) and SEC-D-10 (the product's containers miss baseline hardening).
- Related: ADR-KEY-01 and ADR-KEY-02 (what the proxy and broker hold, SEC-D-03), ADR-SEC-01 (supply chain).

## Context

The image drops privileges in its shell entrypoint (`deployment/docker-entrypoint.sh`: `setpriv --reuid=1000 … --bounding-set=-all --no-new-privs`). Compose overrides that entrypoint for the egress proxy and the sandbox broker, so both ran as uid 0 with Docker's default capability set (`NET_RAW`, `DAC_OVERRIDE`, `SETUID`, …) and a writable root. These are the two services sandbox code reaches first. The stores were the same: only `pipeshub-ai` set `no-new-privileges`, no service dropped a capability, few had a memory limit and none a process limit. In Helm the app and broker had a writable root, qdrant ran as root with no security context, the builtin MongoDB ran as root, and every store pod mounted the namespace's default service-account token.

The fault is shared: privilege was something a process did to itself at start, not something the deployment declared. Any service that reused an image with another command silently ran as root, and nothing checked.

## Decision

1. **The deployment declares privilege; the process does not decide it.** Each Compose service merges one anchor, `x-hardened`: `cap_drop: [ALL]` and `no-new-privileges:true`. Docker's own seccomp and AppArmor profiles stay on; no service may set them `unconfined` (the profile is not named explicitly, because naming `apparmor=docker-default` stops the stack from starting on a host without AppArmor, and Docker applies it wherever it exists). Every service has a memory limit and a process limit under `deploy.resources.limits` (Compose refuses `pids_limit` beside a `deploy` limit).
2. **Capabilities come back only where an image proves it needs them, with the reason beside each.** These were found by starting each image with none and adding back only what its start failed on, then restarting it on the same volume:
   - `pipeshub-ai`: `CHOWN DAC_OVERRIDE FOWNER SETUID SETGID SETPCAP`, held only by the image entrypoint while it hands earlier root-owned volumes to uid 1000 and drops to it. `setpriv --bounding-set=-all` needs `SETPCAP`; no service process holds any capability. Since R44-STOP also `KILL`, for the init that stays root as PID 1 (Amendment R44-STOP).
   - `mongodb`, `neo4j`: `CHOWN DAC_OVERRIDE FOWNER SETUID SETGID`, for their entrypoints' hand-over and `gosu` drop; `neo4j` also `KILL`, for the image's tini (Amendment R44-STOP).
   - `redis`: `CHOWN DAC_READ_SEARCH SETUID SETGID` (`DAC_READ_SEARCH` reaches into the `0700` `appendonlydir` an earlier root-running redis left, so its files can be handed over; found by starting on a volume the base file had written). Its command now goes through the image entrypoint (`exec docker-entrypoint.sh redis-server …`): started straight from `sh -c`, redis-server ran as root, which only worked because root held `DAC_OVERRIDE`. The entrypoint's `chown` pass also takes over files an earlier root-running redis left.
   - Every other service (qdrant, arango, etcd, zookeeper, kafka, searxng, crawl4ai, nginx, prometheus, grafana, the proxy, the broker): none.
3. **The sandbox plane runs as uid 1000 with a read-only root.** The proxy and broker declare `user: "1000:1000"`, `read_only: true` and a small `tmpfs` at `/tmp`. The broker reaches the Docker socket through the socket's group (`group_add: ${DOCKER_GID}`), never as root. `install.sh` reads `DOCKER_GID` from the socket on every run (a host's docker group id can change) and writes it to `.env`; the default `0` fits Docker Desktop, whose socket is `root:root`. The lane's `run.sh` writes it the same way, and the e2e overlay no longer sets its own `group_add`, so a lane stack runs the shape an install runs.
4. **Read-only roots wherever the image writes only to its volumes:** the proxy, the broker, redis, etcd, the web-readers gateway (nginx as its own uid 101, with `tmpfs` for its cache and pid) and the one-shot sandbox image service. The app, MongoDB, Neo4j, Kafka, ZooKeeper, arango, qdrant and searxng rewrite configuration or keep caches inside their image at start, so they keep a writable root and rely on the other layers.
5. **Helm keeps the restricted Pod Security profile on every pod but DinD.** Every container sets `allowPrivilegeEscalation: false`, drops `ALL`, runs as non-root under the `RuntimeDefault` seccomp profile, and no pod mounts a service-account token (`serviceAccount.automountServiceAccountToken: false` for the app; `automountServiceAccountToken: false` on every store pod, which never call the API). The app and broker have a read-only root with `emptyDir`s for `/tmp`, `$HOME` and logs. The model caches the image ships (`/root/.cache/huggingface`, `fastembed`) are copied into a per-pod `emptyDir` by a `model-cache` init container, so a newly chosen model can still be downloaded and an air-gapped cluster keeps the bundled ones. Qdrant moves to the `-unprivileged` image as uid 1000 (`fsGroup` hands an earlier root-written volume over on the first start). The builtin MongoDB runs as uid 999 from the start; its keyfile init container no longer needs root, because the copy it makes as 999 is already 999's. The DinD sidecar stays privileged, the one documented exception (values.yaml `sandbox.dind`).
6. **A standing check, not a one-off fix.** `tests/unit/harness/security/test_container_baseline.py`:
   - every service of the shipped Compose files keeps the baseline, in the file and as `docker compose config` merges it;
   - every Compose file under `deployment/docker-compose` is classified as shipped or not, and none of them, shipped or not, may open a hole (`privileged`, a host namespace, `unconfined`, `cap_add: ALL`, a device, a narrowed `cap_drop`, a `!reset` of a hardening key);
   - no lane overlay loosens the proxy or the broker;
   - every rendered Helm container keeps the baseline in two variants (broker with DinD; builtin stores);
   - the shapes an attacker would try next (root spelled `0`, `00`, `ROOT`, empty; `seccomp=unconfined` in any case or separator; `CAP_`-prefixed adds; host namespaces) are each caught.

**What follows.** A compromise of the proxy's HTTP or CONNECT parser lands as uid 1000 with no capabilities on a read-only root: no raw sockets, no reading past file modes, nothing persists across a restart. Since R43-SOCK the broker holds no socket either: a foothold in it reaches Docker only through the policy proxy's broker profile (Amendment R43-SOCK). An install that does not run `install.sh` on Linux must set `DOCKER_GID`; until it does, the Docker API proxy cannot open the socket, its healthcheck stays red and the broker waits for it.

## Deviations

- SEC-D-02 fix item 3 was not built by R38-IDENT; R43-SOCK built it (R38IDENT-FU-1), as decided by R42-SMALL. See "Amendment R43-SOCK" below.
- Contributor, legacy and integration Compose files (`build.neo4j`, `prod-legacy`, `integration.*`) are not held to the full baseline; they may not open a hole. Moving them to the anchor: R38IDENT-FU-2.
- The Helm app's read-only root was checked by render and schema (`deployment/helm/tests/check_chart.sh`, 16 variants), not on a cluster: R38IDENT-FU-3.
- AppArmor is Docker's default where the host has it, not named in the files (decision 1).

### Amendment R43-SOCK (2026-11-13): the broker's socket behind the policy proxy (SEC-D-02 fix 3, R38IDENT-FU-1)

Built on `harness/v2-r43sock` to the R42-SMALL design (the earlier Deviations entry).

1. **One socket holder for both modes.** `docker-socket-proxy` (`app.docker_proxy_main`) moves into `docker-compose.yml` under the `sandbox` profile and is the only container that mounts `/var/run/docker.sock`, as uid 1000 in the socket's group (`group_add: ${DOCKER_GID}`, moved off the broker), with the base file's hardening. The broker loses the socket and the group; it reaches the proxy at `tcp://docker-socket-proxy:2375` on `sandbox_docker`, an internal network only the two are on, and waits for it healthy. `docker-compose.sandbox-legacy.yml` only adds the app's credential, the legacy image and `sandbox-control` to the same service.
2. **The credential picks the profile.** One transport (`DockerSocketProxy`: head parsing, framing, credential, forwarding) holds each caller to its own profile: `DOCKER_PROXY_BROKER_TOKEN` to `BrokerApiPolicy` (`app/sandbox/docker_proxy_broker.py`), `DOCKER_PROXY_TOKEN` to the legacy `DockerApiPolicy`. The two must differ; the proxy refuses to start with neither, or beside a platform key. Each credential is compared in constant time and every one is compared. `install.sh` generates the broker's (`get_existing_val`, so an existing one is kept) and heals an older `.env` (`REGENERABLE_CREDENTIALS`).
3. **The broker profile is closed** and derived from the broker's code: a test reads every docker-py call of the broker's modules and fails on one with no route (`test_every_docker_call_the_broker_makes_has_a_route`). Creates are checked by the broker's own `HardeningPolicy` (one rule set: the profile builds the same class from the same shared constants, now in `docker_policy.py`) inside the legacy profile's struct rules (case-folded and duplicate keys, closed `HostConfig` plus the four fields the broker sends: `Ulimits`, `ExtraHosts`, `Dns`, `BlkioDeviceWriteBps`), with `refuse_host_reach` and the pinned log driver shared with the legacy profile. Volumes: the data volume or the broker's prefix, no `DriverConfig`, a `Subpath` that stays inside; named volumes created only with tmpfs driver options; the data volume is never removed. The one root container is the egress firewall helper, `NET_ADMIN` alone, in the network namespace of a sandbox this install owns. Exec only in the install's sandboxes, never privileged, never as root; an exec start's hijacked stream is piped both ways with its half-close. List calls are forced to the install's labels. Networks: the shared open-egress bridge on its pool (the legacy rules), and per-sandbox internal bridges with exactly the broker's options on the sandbox pool; connect and disconnect only for the install's sandboxes and the configured egress proxy. An object that does not exist answers 404, as the daemon would, so the broker's not-found handling still works.
4. **Stamp migration.** Every container, named volume and per-sandbox network the proxy admits carries `ai.pipeshub.docker-proxy.install=<install>`. A container the broker made while it held the socket (a warm sandbox across the upgrade) has the install's broker labels but no stamp: it can still be inspected, stopped and removed, and is used (exec, archives, start, network attach) only while its live configuration passes the same `HardeningPolicy`.
5. **Not an image allowlist.** The broker's image rules (its allowlist and ADR-SEC-01 signatures) stay the broker's. The proxy's guarantee is that no image, whatever it holds, gets host reach: every create meets the floor with no host path, device, namespace or capability. Mirroring the broker's allowlist into the proxy would need every image variable the broker reads (release pins, registry, MCP runner, test trust roots) and would fail closed on any drift.
6. **Helm.** With DinD, the broker pod gets the same proxy as a sidecar (broker profile, loopback, the broker's credential from the chart secret), and the broker no longer mounts the DinD socket; dockerd sets the socket's group (`sandbox.dind.socketGroup`), so the proxy runs as uid 1000, not root. The legacy app-pod sidecar uses the same helper and now gets `DOCKER_PROXY_TOKEN` on both sides, which it lacked since SEC-A-04. Checked by render (`check_chart.sh`), not on a cluster (R38IDENT-FU-3).
7. **Upgrade.** `migrate_sandbox_to_broker` starts `docker-socket-proxy` with the broker so Compose recreates it from this run's files, and once the broker serves removes any project container still on the legacy `sandbox-control` network that mounts the socket (SOCKPROXY-1). The lane's `run.sh` backfills the new credential and gives a stack made before `sandbox_docker` existed its subnet.

**What follows.** A foothold in the broker can start sandboxes and act on this install's, which is its job, but cannot create a privileged, host-mounted or host-networked container, exec into the app or a store, or mount another volume of the host. A rollback to an image from before this release keeps the app but not code execution until that release's own files are used: the older broker sends the legacy credential, and the older proxy knows no broker profile.

**Tests.** `tests/unit/sandbox/test_docker_proxy_broker.py` (the derived allowlist and the bypass suite), `tests/unit/harness/sandbox_broker/test_docker_broker_through_proxy.py` (docker: SB-1..SB-30 through the proxy on runc and gVisor, and a foothold's asks refused on a real daemon), `tests/cohesion/test_c12_sandbox_plane.py` (the render: only the proxy holds the socket), `test_container_baseline.py`, `deployment/docker-compose/tests/sandbox_plane_test.sh` IN-5b, `deployment/helm/tests/sandbox_topology.py`, the human smoke's socket-holder check.

### Amendment R44-STOP (2026-11-14): the stop signal reaches the server (R43SOCK-FU-3, -4, -5)

Built on `harness/v2-r44stop`.

**Root cause.** Docker stops a container by signalling PID 1. In two shipped services PID 1 is an init that started as root and stays root while the server it supervises has dropped to another user: `pipeshub-ai` (`init: true`, so `docker-init` (tini) → the image entrypoint → `setpriv` to uid 1000 → `process_monitor.sh`) and `neo4j` (the image's own `ENTRYPOINT ["tini", "-g", "--", …]` → `gosu neo4j`). A process may signal another only if their user ids match or it holds `CAP_KILL`; uid 0 without capabilities is just a uid. With `cap_drop: [ALL]` and no `KILL`, tini's `kill()` fails with `EPERM`, tini treats that as fatal (`Unexpected error when forwarding signal`) and exits 1, and the kernel then kills everything in the container. Reproduced on Docker: neo4j exited 1 in 0.6 s with no shutdown log; the app exited 1 in 0.9 s and the durable worker never saw SIGTERM, so no run drained on `docker compose stop`, on an upgrade or on a restart. Only a service that both starts root under an init and drops to another user can hit this, and under `cap_drop: [ALL]` only `SETUID` lets a process change user, so the class is exactly "root init + `SETUID`": the app and neo4j in the base file (and their copies in the contributor files). Every other service was checked by stopping it from the base file: MongoDB and Redis (`gosu` execs the server as PID 1, which Docker signals from outside), ArangoDB, etcd, ZooKeeper, Kafka, searxng, the web-readers gateway, and the sandbox plane (`init: true` with `user: "1000:1000"`: init and server share a uid). Helm runs every container as a non-root `runAsUser` with no init, so no pod has the hop.

Two more faults sat on the same path once the signal got through:

- `process_monitor.sh` waited in a foreground `sleep 20` between checks, and Bash runs a trap only when its foreground command returns, so the drain began up to 20 s after the stop: with the worker's 40 s drain wait and Node's 8 s that is past the 60 s grace. Measured on the app image: SIGTERM at 00:31:35, drain from 00:31:52.
- qdrant's image runs `entrypoint.sh` as PID 1, which passes SIGTERM to qdrant and exits at once (143), killing qdrant mid-shutdown. Neo4j needs about 11 s to stop cleanly, past Compose's 10 s default, so with the signal delivered it was then SIGKILLed (137).

**Decision.**

1. **`KILL` for exactly the services whose root init signals another user** (`pipeshub-ai`, `neo4j`), with the reason beside it. Removing the hop instead was weighed and rejected: for neo4j it means replacing the upstream image's entrypoint (and losing its tini), for the app either dropping the init (the process monitor would reap every orphan as PID 1) or moving tini into the image after `setpriv`, which changes the image Helm runs and still leaves older images under these files. `KILL` is the capability Docker's default set grants for this; here only root processes hold it: tini, which only forwards signals and reaps, and an operator's `docker exec` (the app's services run with an empty bounding set; neo4j's java dropped to uid 7474 with `no-new-privileges`). It reaches only the container's own PID namespace. Risk accepted: a process that takes over PID 1 could signal the container's other processes, which it could already stop by exiting.
2. **The rule is derived, not listed.** `stop_signal_gaps` (`test_container_baseline.py`) holds every Compose service of the shipped and contributor files to it: an init (`init: true`, or an image in `IMAGE_INITS`, the images whose `ENTRYPOINT` is an init) that starts as root, with `SETUID`, must add `KILL`; `KILL` anywhere else is refused. A Docker-marked test checks `IMAGE_INITS` against the images on the host, and another starts a root init over a child that drops to another user with each service's own capability set: exit 0 with it, tini's exit 1 without `KILL`.
3. **The drain starts with the signal:** the process monitor waits on its idle `sleep` (`wait` returns as the signal arrives) and its cleanup stops that sleep. `tests/unit/deployment/test_process_monitor_stop.py` runs the script against stub services: the worker gets SIGTERM under 2 s after the stop, Node only once the worker has finished, exit 0.
4. **qdrant runs `./qdrant` under `init: true`** (no user hop, so no capability); **neo4j's grace is 120 s**, as qdrant's.
5. **The broker's firewall helper runs only its rules script (R43SOCK-FU-4).** `HardeningPolicy.check_firewall_helper`, which the broker and the proxy's broker profile both call, now also requires the image's entrypoint cleared, no environment, and a command `["sh", "-c", <script>, "egress-firewall"]` whose script passes `sandbox_floor.firewall_rules_script_ok`: the same fixed lines and IPv4 rules as the legacy script's grammar (one table, `_RULES_HEAD`, now shared by both checks), then `exit 0` and nothing else. `sandbox_floor` imports only the stdlib and `agent_loop_lib` imports nothing from `app`, so the builder and the grammar stay two files; `tests/unit/sandbox/test_firewall_script_grammar.py` keeps every script either builder writes accepted and every added command refused.
6. **Rollback says what it cannot undo (R43SOCK-FU-5).** The image carries `ai.pipeshub.sandbox-plane.version="2"` (the broker behind the proxy's broker profile). `rollback.sh` reads the target's label (local copy, else the registry's config without pulling); a target without it, or with a lower value, gets a warning that code execution stops while the app keeps working and how to keep it (that release's own `deployment/docker-compose` with this `.env`), and at a terminal a yes/no question. The release tooling test keeps the Dockerfile's value equal to the script's.

**Proven on Docker** (compose projects `pxh-r44s-*`, base file from this branch, removed with their volumes after): the app image used (`pipeshub-ai:cg-b11-final-py`, the newest with the shipped entrypoint; it predates the harness, so a stand-in `app.harness_main` with the worker's drain bound logged when SIGTERM arrived and when its drain finished) with this branch's `process_monitor.sh`: without `KILL` exit 1 in 0.9 s, the worker never signalled; with `KILL` and the old monitor, drain 17 s late; with both fixes the worker got SIGTERM within a second, drained 30 s, Node stopped after it, exit 0 in 34 s (60 s grace). neo4j exit 0 in 11 s with `Stopped.`; qdrant exit 0 (was 143); MongoDB, Redis, ArangoDB, searxng, the web-readers gateway, etcd exit 0 with their shutdown logs; ZooKeeper and Kafka 143 (the JVM's exit on SIGTERM after its shutdown hooks; Kafka logged `shut down completed`).

**Not proven here.** A real durable run drained in the app container: no image available for the test carried the harness; the worker's drain on SIGTERM is the L4 fault suite's (RU-4a, RU-5a), which does not start at this base (R44STOP-FU-1). crawl4ai, Prometheus and Grafana were not started (no `SETUID`, so no user hop; whether their entrypoints exit before the server is unchecked: R44STOP-FU-2).

### Amendment R44-MCP2 (2026-11-14): the firewall helper's image is pinned (R44STOP-FU-3)

Built on `harness/v2-r44mcp2`. Decision: pin it.

**Gap.** Amendment R44-STOP 5 held the helper to its command, but the helper ran from the run's own image (`spec.image_digest`) and the proxy's broker profile holds no image allowlist, so a foothold in the broker that made a sandbox from an image of its own still got its own `sh` and `iptables` as root with `NET_ADMIN` in that sandbox's namespace.

**Decision.** The helper runs from the deployment's own sandbox image, the one the broker already runs its other helpers from (`helper_image`, `SANDBOX_DOCKER_IMAGE`; install.sh pins it to its registry digest as `PIPESHUB_SANDBOX_PINNED`, and that image carries iptables), never the run's. `HardeningPolicy.firewall_image` names it and `check_firewall_helper` refuses any other image, and every image when none is named; the broker passes its helper image and the proxy's broker profile reads `SANDBOX_DOCKER_IMAGE` as the broker does (Compose gives the proxy the broker's expression, Helm's docker-proxy sidecar gets the sandbox image in both profiles, the e2e overlay the lane's image). A broker with no helper image refuses open egress (`egress_firewall_unavailable`). An engine run now gets its firewall from the sandbox image, so engine images no longer need iptables. Tests: the policy refuses three other images and an unset pin, the broker runs the helper from the pinned image under an engine image and refuses with none, the proxy answers 403 for three other images, the profile reads the variable; `sandbox_topology.py` (check_chart) and `image_signature_test.sh` keep the proxy and the broker on one image.
