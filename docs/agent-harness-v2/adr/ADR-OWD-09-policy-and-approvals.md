# ADR-OWD-09 — Policy decisions, taint and approvals as protocol concepts

## Context

[OWD-9](../one-way-doors.md) makes approvals and policy decisions first-class events and states. The approval shape, its scoping and the taint semantics get encoded in the UI, the public API, Slack, audit and compliance reports.

## Decision

Adopt OWD-9 with taint built as labels:

- Decisions are `allow | deny | ask | allow_with_redaction`, each with a reason.
- Taint is carried as **labels and a flow policy** (REPORT D15): integrity and confidentiality readers set by the gateways and propagated to children and parents, instead of the three named booleans. The flow rule asks before an external write in a conversation that read private or untrusted content (the Rule of Two in effect).
- Approval requests carry a concrete effect preview; decisions are audited and immutable, and the sandbox can never forge one.

Spec item amended here (UX-first): **C3.72** — an expired *hold* stays actionable, so the person can still decide when they return; an expired approval *TTL* denies. The deny reason reaching the harness lands in WP-10.

## Deviations

- **Labels instead of booleans.** Accepted divergence (D15): labels carry who may read what, which booleans cannot, and the Rule of Two suite passes on them.
- **`allow_with_redaction` redacts results, not arguments.** A write's arguments are what the person asked to send; redacting them would change the effect. The decision masks what the model reads back. Closed by WP-22.

## Owner amendments

None to OWD-9 itself. Which actions ask is set by the approvals rule (toolset writes run, deletes and sends ask) and by the rule that in-sandbox code with no egress is auto-allowed.

Amendment (applying the approvals rule): checklist C3.81 / GT-04 said a run's pull request is opened "after approval". The approvals rule outranks it: opening the pull request (`open_pull_request`, WP-26) is approved exactly as the GitHub toolset's `create_pull_request` is. It has that tool's effect class and, in main's rules, its approval target, so it runs unless a rule asks; an admin's (or a personal instance owner's) Ask or Block on `create_pull_request` holds or refuses it too. No rule is added for pull requests. In an engine run the engine's own safety default (UX2/UX4: a write that leaves the person's space asks, answerable for the conversation) applies to both tools alike, as to every engine write.

**D-ALLOW-1** (MCPNOTE-FU-2). On an engine job, a tool that a person (or an admin, for the org) has explicitly set to Allow runs without asking, as on the default chat and saved agents. Cause: the engine chain (`engine_guarded`) puts main's per-tool rules (`ToolRulesPolicy`) over the org's governance, under the flow guard, under the engine's release default (`ENGINE_APPROVALS`: a write that leaves the person's space asks) in `DefaultAskPolicy`, and that took the stricter of the two; the person's Allow could never get past it. Precedence, strongest first:

1. A block from any layer, and the flow guard (ask or deny), always win.
2. An org rule that asks wins over a person's Allow: the org's and agent's approvals, an engine profile the org, agent or task narrowed (`profile_rules`, the org's named ceiling). These are governance, inside the chain's base.
3. A specific per-tool Allow lifts the engine's class default for that one tool. The policy that holds the rule says so through `LiftsDefault.lifts_default` (`harness_core/effects/types.py`); `ToolRulesPolicy` answers yes only for an Allow that is someone's setting (the person's or the instance's rule, never the tool kind's default), and `FlowGuardedPolicy` passes the question to its base. `DefaultAskPolicy` lifts only its own ask, never its deny, and logs `effects.default_lifted`.
4. With no specific rule, the release default stays: an engine run's write that leaves the person's space asks, answerable for the conversation, over main's class defaults.

No other layer changes: repository asks, the org's policy webhook and any extension point an edition binds wrap the chain from outside. Tests: `tests/unit/harness_core/effects/test_allow1_default_lift.py` (the table with a stand-in rule store), `tests/unit/harness/assembly/test_allow1_engine_tool_allow.py` (the assembler's real `ToolRulesPolicy` in the engine chain), and the lane `test_mcpnote_unlisted_servers.py` (Allow runs without a card on opencode, codex and claude_code).

**D-SA-ASK** (R33JGAPS-FU-3; R34-FIX). A service-account agent's run asks the person who started it, as a user-principal agent's run does; it never refuses an Ask silently. Cause: the durable path built main's per-tool rules (`ToolRulesPolicy`, `app/harness/tool_rules.py`) with `watched=not is_service_account`, today's loop's rule for a run that has no card, so every Ask (an org or person rule, main's default Ask, and the flow guard's ask under it) became Block `unattended`: `tool.recovery choice=deny`, no card, the run answering as if nothing was held back. A durable run always has someone to ask:

1. The kernel's approval interaction reaches the run's actor, who is the person in the chat for an interactive turn (the member's own credential is the request's; only the tools act with the agent's account), and a schedule's actor through the inbox for a scheduled or webhook run, exactly as for a user-principal agent's schedule.
2. Who may decide is unchanged and read from the org's records, never the request (`SessionInteractionService.authorityFor`, `ApprovalQueue`, `ApproverDirectory`): the actor, and whoever a bound `ApproverDirectory` names (none by default). When the person in the chat may not decide, the card says who it waits on with the existing words (`approvalCard.noAuthority`) and the request is in the queue of those who may; nothing is routed anew.
3. A run whose actor is the service account itself (principal `agent_service`, no person behind the request) asks too; only an approver a bound `ApproverDirectory` names can decide it, and with none (the default) it ends as expired after the wait, said on the run. It is never a silent deny.
4. An admin's Block still refuses, with main's wording; an Allow still runs. Today's loop keeps its own rule (it has no card for such a run).

Tests: `backend/python/tests/unit/harness/assembly/test_r34_service_account_asks.py` (an Ask on a service-account agent asks, red on the base with `deny`; a Block still denies; a user-principal agent is unchanged). Journeys: `J-agent.quick-service-{deny,allow,flow}` and `J-scheduled.{cron,webhook}-service-{deny,allow,flow}`.

**D-MCP-ASK** (R34-FIX; found once R33JGAPS-FU-1 made `/mcp` turns durable). A run started through PipesHub's own `/mcp` (`pipeshub_chat`) that asks a person's approval asks, as any durable run does, and the MCP client is told so in words instead of waiting: its reader takes one stream to a terminal frame and cannot show a card, so the external audience's stream ends at the open card with the conversation as it stands (status `Waiting`, the answer "This needs a person's approval before it can go on. Open this conversation in PipesHub to approve or decline it; the answer will be saved there."). The run stays parked; the person decides in PipesHub (the chat and the inbox), where the answer is saved. Today's loop refused such a call outright; refusing would hide a write the person may want, and holding the client's call open for the person's wait (days) would hang the calling agent. Built: `RunProjector.awaitingApproval`/`handOff`, `RunStream.handOffIfAwaiting` (`projection/`); tests `projection/r34-mcp-hand-off.test.ts`, journeys `J-surface.mcp-seeded-{deny,flow}`.

**D-SLACK-ASK** (R35-SLACK, R34FIX-FU-2). A Slack turn whose run asks a person's approval no longer holds the thread. Reproduced on a runsc stack with a scripted Slack workspace (R35-SLACK's lane): the saved agent's run asked, the `slack` audience shows no card, so the thread read "Using Create ticket..." with no word of what waits or where; the bot's request stayed open on the stream's keep-alives (axios' timeout is an idle timeout, which they reset), the answer came only if someone happened to decide in PipesHub while that request was still open, and a bot restart lost it. The default assistant's Slack turns never reached the harness at all (`admission.legacy reason=chat_mode_not_supported`: only the web app asked for it), and today's loop refused the same write with no card and no word (a silent deny).

1. One rule for every audience that cannot show a card: its view says so (`AudienceView.handsOff`: `external`, `slack`; a shared viewer reads on in the web app), and its stream ends at the open card with D-MCP-ASK's hand-off. The frame's `meta` now also names what the run waits on (`waitingOn`: each call as its tool frames name it) and the conversation's link (`conversationLink`), so a client can say what waits and where.
2. The bot puts that in the thread: "This needs an approval before I can go on: *e2esaas · Create ticket*. Open this conversation in PipesHub to approve or decline it. I'll post the answer here once it goes on." (the link opens the conversation behind PipesHub's own sign-in). No buttons in Slack: the bot knows its Slack user only by the profile email it looks up, a weaker identity than PipesHub's sign-in, and an approval is an authorization decision; the card in PipesHub also says who may decide when the person cannot (D-SA-ASK, AP-08), which a button could not. AP-10's links ("the bot never decides for the person") are the same rule.
3. The run stays parked until someone decides. When it ends, Node posts its end in the thread, once, as the bot that answers the thread: the Slack route pins the thread on the run (`input.reply`: the bot from the verified token's `configId`, the channel and thread from the body's `slackThread`; Node's alone, never sent to a worker), the bot's open stream watches the conversation as the person's Slack thread (`slackThreadViewer`, beside and apart from the web app's lease), and on every run end `ThreadReplyService` posts unless that stream still reads it (then the bot does), claimed once per run (`claimRunNotice`). The answer is composed as the bot composes its own (`finishedAnswer`, shared by both), so the thread reads the same either way; a failed or stopped run says so and links the conversation. This also covers a bot that went away mid-run.
4. The default assistant's Slack turn asks for the harness as the web app's Agent mode does (`harness: "durable"`); the server decides from the org's rollout, and a thread that began on today's loop stays there (ASSIST1).

5. (R36-COVER, R35SLACK-FU-3, 2026-11-13) A person who writes in the thread while its run is parked at the card is not turned away: the message joins the run as steering (a parked run is steerable, `STEERABLE_RUN_STATUSES`) and the run reads it once someone decides and it goes on, so nothing they wrote is lost and the answer posted back (3) takes it into account. The reply says exactly that, as the hand-off: "This is still waiting for an approval: *e2esaas · Create ticket*. Open this conversation in PipesHub to approve or decline it. I've added your message; it will be read once this goes on, and I'll post the answer here." Considered and rejected: refusing the message ("can't be taken yet") throws away words the run can use, and the old reply, "Added to the running task.", reads as if the run were working on it while it waits on a person. Built: `ChatTurnService` answers a queued turn from a hand-off audience whose run is parked (`parkedAtCard`) with the hand-off's `meta` plus `queued: true` and what waits (`waitingOn`, read from the run's timeline; a read that fails still queues the message and names nothing), status `Waiting`, `QUEUED_WAITING_REPLY` (what an MCP client reads); the bot words it (`handOffText`, `queued`). The owner's web app, which shows the card, keeps its toast. Tests `r36-slack-parked-reply.test.ts` (SLACKPARK-1..5); journeys `J-surface.slack-{owner,seeded}-steer` reply in the parked thread before deciding (the `steering` feature).

Other surfaces: `/mcp` (D-MCP-ASK) and Slack are the only audiences that stream a durable run without a card; a webhook's delivery does not stream (its run asks through the inbox, D-SA-ASK), and `/run` never asks (code runs in the sandbox are allowed). A new audience must declare `handsOff`. Built: `projection/audiences.ts`, `stream-service.ts`, `run-projector.ts`, `application/thread-replies.ts`, `enterprise_search/adapters/slack-thread-replies.ts`, the bot's `utils/{hand-off,finished-answer}.ts`. Tests: `projection/r35-slack-hand-off.test.ts`, `r35-slack-thread-replies.test.ts`, `integrations/slack-bot/r35-hand-off.test.ts`; journeys `J-surface.slack-{seeded,owner}-{use,deny,allow}` on the scripted Slack workspace (`deployment/e2e/fake_saas/fake_slack.py`).

**D-MCP-OPENWORLD** (R38-AUTHZ, SEC-B-02). An MCP tool's sink is `self` only when the tool declares `openWorldHint: false`; every other MCP tool is `sink=external`, a read-only one included. Cause: `hint_tags` (`harness_core/mcp_hub/annotations.py`) tagged no sink on a read without `openWorldHint`, so `classify_tool_effect` gave it the first-party read default (`self`), `sends_out()` was false, and the flow guard allowed a third-party `search(query)` carrying private content after a private and an untrusted read, against the MCP spec's own default (`openWorldHint` is `true` when absent). For an MCP server the arguments always reach a third party, the server's operator, so a missing claim cannot narrow where they go.

1. `hint_tags` is the one mapping from hints to effect and sink, and always tags the sink; `declared_hints` is the one reading of the hints (exact protocol keys, booleans only: a string `"false"`, `0`, `null` or an odd-cased key is not declared). The starting approval rule (`app/agents/mcp/tool_kind.py`) and the stored-catalog descriptor (`mcp_tool_loader`) now read the hints through `declared_hints` too.
2. The hints stay inside the descriptor digest, so a server that re-lists a tool with `openWorldHint: false` added or dropped loses its approval and the run's pin; dropping it can only make the tool `external`, never wider.
3. Effect on people: a read-only MCP tool that does not declare `openWorldHint: false` is now held by the flow guard after a private read (asks on the durable loop and engines; refused on today's loop as a web fetch is). Servers that do declare it, and PipesHub's own `/mcp` code-graph tools, are unchanged.
4. Not built: an admin setting that marks an MCP instance as internal (its tools at most `self`, whatever the hints). No such instance setting exists; it needs the instance model, its route and OpenAPI entry, and the admin form, so it is a follow-up. Until then the server's own `openWorldHint: false` is the only way to `self`, held by the admin's approval of exactly that descriptor. **Built by R43-MCP (SEC-B-02-FU-1, 2026-11-13):** `PUT /api/v1/mcp-servers/instances/{id}/boundary` `{insideOrganization}` (org admins only, a strict boolean, stored on the instance with who set it, logged `mcp_hub.boundary_set` and audited by Node's control plane as `mcp-boundary`; an instance edit keeps it; any transport, hub on or off), and the instance's Configuration tab ("Where this server runs"). `hint_tags(..., inside_organization=)` caps the sink at `self` and never changes the effect; `MCPToolAdapter` reads only a stored `True`. Who may set it is the org admin. Tests `tests/unit/harness/test_r43mcp_inside_organization.py`, `tests/unit/harness/mcp_hub/test_routes.py::test_sec_b_02_fu_1_*`.

Tests: `tests/unit/harness/test_fg2_mcp_hints.py` (the table now says `read-only → external`, the bypass variants and the re-listing), `tests/unit/harness/security/test_r37secb_ai_attacks.py::test_sec_b_02_*` (the proof, no longer xfail).

**D-APPRPOL-SECTIONS** (R55-APPRPOL, closes R54APPR-FU-1). The org approval policy holds only what this repository decides: the org's rule, its agents' rules and who saved them. Who may decide stays the run's actor (the session owner and org admins may deny), through `ApproverDirectory`. Anything else an org's approval policy carries is an edition's **approval-policy section**, one value per org, behind a seam with do-nothing defaults:

1. Schema: the approvals document's root, the admin view's `policy`, `refused` and `names` are `x-extensible`; an edition's overlay (`*.extends.json`) adds its section as a top-level map of orgId to entry, and the view members. The policy layer's root, `lockedBy` and `updated` were already extensible. Node's reader (`domain/approvals.ts`, `APPROVALS_DOCUMENT_KEYS`) and the worker's (`app/harness/approvals.py`, `_SECTIONS`) take the known top-level keys from the generated model, so both accept exactly the overlay's maps; an unknown key still makes the document invalid (the worker asks for writes), and the worker reads no section.
2. Storage: `ApprovalPolicySection` (`domain/approval-policy-sections.ts`: `key`, `documentKey`, `empty`, `parse`, `isEmpty`), supplied as `HarnessEdition.approvalPolicySections` (empty here). While the KV document is the record its entry sits in the map `documentKey`; once the policy store is, in the org layer's section `key`. `ConfigApprovalSettings` reads and writes it with the org's rules under the same compare-and-set and audit entry; the dual write keeps both; the policy-layers migration (`legacyPolicyLayers`, the read-through and the CLI) copies it with them. Maps this build does not hold are kept as stored, and a save that leaves a section out keeps the org's entry, so a client that does not know the section cannot erase it.
3. Admin API: `GET`/`PUT /api/v1/agent-harness/admin/approvals` shows each section as `policy[key]` and `refused[key]` and adds the names its handler gives. A saved value is parsed by its section and checked by an `ApprovalPolicySectionHandler` (`ports/approval-policy-section-handler.ts`, bound by the edition as `AGENT_HARNESS_APPROVAL_POLICY_HANDLERS`). A member no section holds, a value the section refuses, or a non-empty value no handler checks is refused (`APPROVAL_RULES_INVALID`) before anything is written. `versionedSection` gives a decision the value with the org layer's revision (QA21-F2, CPD-9).
4. UI: the Approval policy page renders the `ApprovalPolicySections` slot (`config.ts`; nothing here) with the whole policy, `refused`, `names` and `onChange(key, value)`; the editor saves every member as read unless the slot changed it.

Named approvers are an extension point with no default in this build: the default refuses every named approver, and an edition can add policy sections through the slot above. Tests: `tests/modules/agent-harness/approval-policy-sections.test.ts` (APS-1..5), `adr-ui-03-admin-list-names.test.ts` (a section's names), `harness-edition.test.ts` (the edition's sections and handlers reach the settings), frontend `approval-policy.test.tsx` UP-6.
