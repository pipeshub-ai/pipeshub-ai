# ADR-GRANT-01: A conversation grant belongs to the conversation and the person who gave it, not to the run that asked

- Supersedes: UX1's rule that a sub-agent's card never offers "Allow for this conversation", and the grant as a fact of one run's stream. FLOWASK's keys (a site per registrable domain, the web search per provider) and WP-29's scope wording stay.
- Related: ADR-OWD-09 (policy and approvals), ADR-OWD-15 (data classification), ADR-OWD-19 (multi-participant sessions); main #4313 (deletes and sends still ask).

## Context

In a manual test (2026-11-07), a Claude Code child that read one private record asked 14 times: one external site 3 times, pipeshub.com 3 times, the web search 6 times, two clones. Every ask was `flow_external_write` with `conversationGrant: true` and a destination key that repeated; every decision was "Allow once"; no `interaction.granted` was ever written. The tester reported that a page allowed once in the session kept asking for approval, and the grouped card listed calls already approved.

The grant was lost in four places, one design fault under all of them: **a grant was a fact of the stream it was given on**.

1. Each run journals on its own stream and a worker reads only its own. A grant given on a child's ask reached only the rest of that child; the parent, siblings and the next runs never saw it. A child inherited only the grants its parent held when it was spawned.
2. Because such a grant would not have held for the conversation, Node's child projection forced `conversationGrant: false` on every child card frame, and the chat passed `conversationChoice={childRunId === undefined}`. Engine runs are children, so the person was never offered the choice.
3. A grant held for any data: given while the run had read nothing private, it later covered private data.
4. The chat grouped approvals by "model turns before it". An engine makes every call in one model turn of the harness's view, so its sequential asks were folded into one "Allow all N" card that also listed calls already approved.

## Decision

**D1. Node names the grant.** `interaction.granted` carries what it allows (`toolId`, the destination `key`, the `sensitivity` the run had read), copied from the worker's own `interaction.explained`, never from the client. Which asks offer a grant is unchanged (the worker's `conversationGrant`; never the org's own asks: policy webhook G-40, or an ask an edition's extension point raises): this ADR changes where a grant reaches, not what it may answer. A grant answers one tool to one destination, so a delete or a send with another tool or to another place still asks (main #4313).

**D2. A grant reaches the whole conversation** (`ConversationGrantReach`, after the decision commits): Node writes a copy (`fromRunId`: where it was given) on every other open run of the session, and resolves at once every open ask in the conversation that the grant covers, as the person's own approval for the conversation, through the usual decision path (journaled, audited, the run woken). The session's root stream holds the copy, so later runs read it; a child is pinned its parent's grants with their sensitivity. A copy never pairs with an ask of the run it lands on, whatever the ids (loop ids repeat across runs). Never another session: the reach lists the session's own runs.

**D3. A running run reads before it asks.** Before an ask that offered a grant, the engine kernel reads its stream once; a grant now held for the tool, destination and data answers it, and nobody is asked. The native loop does the same (WP-115): just before it journals a turn's asks it reads its stream and decides each ask again; one a grant now answers is not asked and stays pending, so the loop's next plan runs it through the same rules as any call (at most once per invocation an attempt, so a policy whose answer flips back can never keep a call from being asked).

**D4. Sensitivity bounds a grant.** It covers asks with the same or less sensitive data: a grant given while the run had read nothing private never covers private data it has read since. Content nobody can name (`unknown`) raises no grant: it holds at the highest sensitivity, which no grant answers, and a write's own reply is such content, so ranking it would re-ask right after every grant (UX2 EA5). A grant, offer or pin that names no data holds at the widest a grant reaches (private), as it did before this ADR.

**D5. The card says the scope, one click, never the default.** A sub-agent's card offers it; the button names the place ("Allow example.com for this conversation") beside the default "Allow once"; the receipt names what it covered. "Don't ask again" and Edit stay with the conversation's own run.

**D6. A card groups only asks that waited together.** Node counts the run's asks decided before each one (`decidedBefore`); the chat groups by it as well, and an open group lists, counts and allows only the calls still waiting.

**D7. Node answers an ask a grant it already holds covers** (WP-115, the decision on WP115-FU-2). Node is the grants' authority. When it accepts a worker commit that raises an ask offering a grant, in the loop or an engine, it reads the run's grants once (`ConversationGrantReach.answerHeld`, through `ExecutionService.onGrantableAsks`, before the commit's receipt is answered). An ask a held grant covers, by D1/D4's tool, destination and sensitivity rule (`coveringGrant`, the one matcher `coveredAsks` uses too), is resolved through the usual decision path: approved, `scope: conversation`, as the person who gave that grant, so the chat shows the same "Allowed … for this conversation by you" receipt. `channel: system`: no one answered on a channel then. A grant now names who gave it (`interaction.granted.by`, optional); an older one is its run's actor's. The reach reads a run again after it writes the copy, and answers what it finds there. So each side reads after its own write and at least one sees the other: an ask committed before the copy is answered by the reach, and one committed after it by the commit check. If the check fails, the ask stays with the person; the commit still lands, and nothing is allowed silently. The ask and its answer are two commits back to back. A live stream does not draw a covered ask's card in between (WP115-FU-2 follow-up, `projection/held-asks.ts`): the projector and the child relay fold the same journal with `runGrantState` and `coveringGrant`, hold an ask a grant the run held when it was raised covers, and draw the card with its answer, already decided, as a reload shows it; one not answered within `HELD_ASK_GRACE_MS` (3 s, a failed or lost answer) is drawn then for the person, and a replay of an older one draws it at once. The run's wait is told after the check, so an approver is not sent an ask Node answered.

**D8. The owner sees the conversation's grants and takes one back** (UI-B1 G5, 2026-11-09). `GET …/conversations/{id}/grants` lists what the conversation holds now, one entry per tool and destination at the widest sensitivity given, named by the ask the person saw (`destination` is the ask's label; the key is never shown), with who allowed it and when; `DELETE …/grants/{grantId}` takes one back (`grantId`: the tool and key, digested). Both are the owner's alone. A revocation is a node event, `interaction.grant_revoked {toolId, key, by}`, written in one transaction on every open run of the conversation and, when no root run is open, on the root stream itself (a session event, no run), so every reader that holds grants drops it from that point of its stream: Node's `runGrantState` (D7 answers nothing with it), the worker's `ConversationGrants` (D3's read before an ask), and a later root run reading the root stream; a child pinned the grant at its spawn drops it from the revocation on its own stream, and a child spawned later inherits only what its parent still holds. A grant given again after a revocation holds again; a revocation never closes an ask already answered. Audited (`toolId`, `key`, `by`) and in the audit search's approvals.

**D9. A conversation decision is one person's, and a decline is one too** (R38-AUTHZ, 2026-11-13; SEC-B-01, SEC-C-04, R36LIVE-FU-1). D1–D8 were written when a conversation had one person. OWD-19 then made each run act as its sender, and a grant kept reaching every run of the conversation: a collaborator's "Allow for this conversation" answered the owner's asks and was copied onto her runs (and back), so an injection one participant posted could send another's private data where it pointed. And a person's decline did not reach the conversation at all: a Codex job's `create_ticket` declined with a reason, then the parent loop made the same call and the person was asked again (seen in a manual test). One rule now covers both directions.

1. **A decision belongs to (conversation, person).** Node writes who gave it (`by`, a principal reference) on every grant and decline. It reaches, answers and is held only for runs whose actor is that person (`decisionReaches`): the reach skips another person's runs, Node's held-ask answer (D7) skips another person's decisions, `runGrantState` takes the run's principal, and the worker's `ConversationGrants` holds only its run's principal's grants (`principal`, from the run spec's `principalRef`), on its own stream, the shared root stream and the pairing of an ask with its resolution alike. A grant that names nobody (from before D7 named the giver) is the run's own actor's, where it was always read; a root-stream decision from another run counts only when it names its person and its call.
2. **Only the run's own person answers for the conversation.** `scope: conversation` from anyone else (an approver, the owner on a collaborator's run) is refused with `CONVERSATION_GRANT_NOT_OFFERED` and a plain message ("Only the person this task works for can allow it for the whole conversation. Allow it once or deny it."), at the one place every decision passes (`ExecutionService.assertInteractionOpen`), so no caller, present or future, can approve across people; the card offers the choice only to that person (`authority.edit`). Another person's denial (the owner's, an admin's) answers that one ask. AP-1/AP-2 are unchanged: who may approve or deny a single ask is as before.
3. **A decline holds like a grant.** When a run's own person declines an ask, Node writes `interaction.declined` (`toolId`, `key`, `by`, the `reason` they gave, redacted as the resolution's) in the same commit, then reaches their other open runs of the conversation with a copy (`fromRunId`) and declines at once every open ask there for the same call, with the reason. An ask raised later by any of their runs (the same run, a parent, a sibling job, the next turn) that the decline covers is declined by Node as it is raised (D7's check, which now reads the conversation's root stream too), `channel: system`, with the same reason, so the run is told why and nobody is asked twice. A decline's call is the grant's: the same tool and destination (`destination.key`); for an ask that names no destination, the same arguments (`argsDigest`, which the worker now journals on `interaction.explained`, to a journal whose claim names `approval_args_digest`). An ask that names neither (an older worker) is declined once, as before.
4. **The asymmetry is deliberate.** A grant widens what runs may do, so it is opt-in ("Allow for this conversation", never the default); a decline narrows it, so every explicit decline by the run's person holds for the conversation, with or without a reason. Expiry (`expired`) and Node's own answers (`channel: system`) never become declines. Where a person both allowed and declined the same call, their latest decision stands in a run's journal, and a decline wins where two journals disagree (the safer answer).
5. **The way back is the D8 list.** The conversation's permissions list shows declines beside grants (`decision: declined`, "Declined by you on …"), and removing one writes the same `interaction.grant_revoked`, after which the call asks again. Revocation stays the owner's, for anyone's grant or decline.

## Deviations

- D8: a worker that planned a call on a grant before the revocation reached its stream still makes that call; the next read before an ask (D3) and Node's check (D7) honour it. A worker older than the event ignores it (non-critical), so a mixed-version fleet keeps an old worker's grant until its run ends; Node's held-grant answer does not.
- D8: the list reads the conversation's whole root stream and its open jobs' streams on each request; it is read when the person opens the permissions row, not on every turn.

- A failure of the reach (after the decision committed) leaves asks to the person: fail closed, logged as `interaction.grant_reach_failed`.
- ~~A native loop run already running reads a copy at its next stream read, not before its next ask.~~ Closed by WP-115 (D3 now holds for the loop): it read the copy only after the ask commit, and then journaled the ask with the base policy's reason (`effect_class`), since the flow rule no longer asked.
- ~~A copy and an ask that cross in the same instant still ask once.~~ Closed by D7 (WP-115, WP115-FU-2).

- D9: a worker does not read declines before it asks (D3 holds for grants only); Node declines the ask as it is committed, so the run is told at once and no card is drawn for it on a live stream (the held-ask projection), except for a later turn answered from the root stream, whose card may show for a moment before its answer. Node's check reads the conversation's root stream on each ask that names its call: proportional to the conversation's length, on the ask path only.
- D9: the D8 list keeps one entry per tool and destination, the latest decision and who made it; two people's decisions for the same call list as the latest, and removing it takes back both.
