# PostgreSQL image and PgBouncer (compose profile `postgres`)

Opt-in: nothing starts unless `postgres` is in `COMPOSE_PROFILES`, and the application connects to it only with the document-store override below. Without the profile `docker compose config` is unchanged.

- `Dockerfile`: pgvector 0.8.7 base for PostgreSQL 18 (default) or 17, both pinned by digest and multi-arch; adds `pg_textsearch` 1.5.1 and PgBouncer 1.26.1 (source tarballs checked by SHA-256). Build: `docker compose --profile postgres build postgres`. The `postgres` and `pgbouncer` services run the same image.
- `pgbouncer.ini`: transaction pooling with `server_reset_query` and `server_reset_query_always = 1`, so session state (role, settings, temp tables, cursors) never reaches the next client. Do not weaken these. One server pool per login; the sizes add up to at most `max_db_connections`.
- `pg-roles.sh` (run by `initdb/10-roles.sh` at the first initialisation and by `pg-entrypoint.sh` on every start): creates what is missing of the role layout (one login per service, plus jobs, migrate and backup; every `PG_*_PASSWORD` is required, `PG_KV_PASSWORD` included), installs `pg_trgm` and `vector` (pgvector, which the image carries) into schema `ext`, and rewrites the SCRAM verifiers PgBouncer authenticates against in the `pgbouncer_auth` volume (mode 0600, read-only in PgBouncer). It never alters an existing role. The verifier file is written last and only when everything succeeded, so it is also the sign of readiness: `pg-entrypoint.sh` removes the old one at start, and the healthchecks of the server and the pooler require it. Because it runs on every start, a volume left without its roles (for example after an interrupted first start) gets them on the next start, and a lost `pgbouncer_auth` volume is refilled. No role has SUPERUSER, CREATEROLE or BYPASSRLS, and a service login holds no privileges until its unit of work switches to its service role. Tables, policies and grants on them come with the migrations.
- `pg-entrypoint.sh`: refuses to start (exit 78) when a required password is empty, before anything is written to the data volume; server defaults (`shared_preload_libraries`, `max_connections`, `shared_buffers`); a refusal to start on a volume whose cluster is not where `PGDATA` points; then the role setup above.
- `scram-verifier.pl`: computes the SCRAM-SHA-256 verifier of a password (read from the environment, printable ASCII only).

Password rule, enforced by `pg-entrypoint.sh` before anything is initialised: every `PG_*_PASSWORD` is non-empty and contains only letters, digits and `. _ ~ -` (the passwords go into connection URLs, and the SCRAM verifier needs printable ASCII). Anything else exits 78 with a message naming the variable.

Secrets: the passwords come from the container environment. They are not in the image, the build context, or the logs. The server never receives a clear-text password: `pg-roles.sh` computes the SCRAM verifiers itself and sends only those (so `pg_stat_statements`, the statement log and `pg_stat_tmp` hold verifiers, not passwords), and turns off statement tracking and logging for its session. The passwords stay in the container's environment (`docker inspect`, `/proc/<pid>/environ` inside), and the verifiers in the database and in the volume's backups; a verifier can be attacked offline, so use long random passwords. A password you set later with `ALTER ROLE ... PASSWORD '<clear text>'` is visible to the server the same way unless you send a verifier.

## Document store on PostgreSQL (`docker-compose.postgres-docstore.yml`)

For a **new** install, the Node API can keep its documents (users, organisations, conversations and the rest) in PostgreSQL instead of MongoDB (`DOC_STORE=postgres`). Run from a repository checkout (the migration job's image is built from `backend/db/Dockerfile`). The simplest way is the installer, from `deployment/docker-compose`: `PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-docstore.yml ./install.sh`, which sets both profiles and generates the passwords. By hand, put the `PG_*_PASSWORD` values in `.env` and activate **both** profiles `postgres` and `postgres-migrate` (the override depends on services of both):

```bash
cd deployment/docker-compose     # where .env and the compose files are
COMPOSE_PROFILES=graph-neo4j,sandbox,postgres,postgres-migrate \
  docker compose -f docker-compose.yml -f docker-compose.postgres-docstore.yml -p pipeshub-ai up -d --build
```

If a profile is missing, compose stops with `service "pipeshub-ai" depends on undefined service "pgbouncer": invalid compose project`; add the profile.

Start order: `postgres` healthy, `pgbouncer` healthy, `pipeshub-migrate` exits 0, then `pipeshub-ai`. The migration job (`python -m db.migrate`, built from `backend/db/Dockerfile`) connects straight to `postgres` (it needs a session and an advisory lock, so not through the pooler) as `pipeshub_migrate`. It is idempotent: a database at head is left as it is, an installed database is upgraded in one transaction, and a failed run changes nothing there. Exit 4 means the catalog or security-surface check found violations; the app is then not started: read `docker compose logs pipeshub-migrate`. Exit codes: `backend/db/README.md`. The app uses the pooled node and jobs logins (`PG_NODE_URL`, `PG_JOBS_URL`, built from the passwords). It also passes each Python service its own pooled login (`PG_CORE_CONNECTORS_URL`, `PG_CORE_INDEXING_URL`, `PG_CORE_QUERY_URL`, and `PG_CORE_KV_URL` for embedding, docling, parsing and extraction, which only read their configuration; `PG_CORE_URL` is the connectors login for anything else): `process_monitor.sh` gives each process only its own, so each acts as its own service role and gets only that role's grants and key-value prefixes. They are used once a Python store is on PostgreSQL. Cross-process change push (PostgreSQL `LISTEN`) is off, because the pooled node login cannot LISTEN and no direct address (`PG_LISTEN_URL`) is set; only the PostgreSQL-backed key-value store and queue (`KV_STORE_TYPE=postgres`, `MESSAGE_BROKER=postgres`) use it, and this override sets neither. A failed migration stops the app from starting. This does not copy existing MongoDB data, and MongoDB and the other stores stay as they are. `./install.sh --uninstall --yes` keeps the PostgreSQL data volume; add `--delete-postgres` to remove it (an interactive uninstall asks).

## Metrics (profile `postgres-metrics`)

Two Prometheus exporters, opt-in: `postgres-exporter` ([prometheus-community/postgres_exporter](https://github.com/prometheus-community/postgres_exporter) v0.20.1, port 9187) for the server (connections by state, locks, transactions open longer than a while, replication and WAL, dead rows and the last vacuum and analyze of each table, running autovacuums, transaction-id wraparound) and `pgbouncer-exporter` ([prometheus-community/pgbouncer_exporter](https://github.com/prometheus-community/pgbouncer_exporter) v0.12.1, port 9127) for the pooler (clients waiting for a server connection, the oldest wait, server connections in use per pool). Both images are pinned by digest. They log in as `pipeshub_monitor`, a login whose only membership is the predefined role `pg_monitor` and which holds no privilege on any table of ours: it reads the server's statistics, never an organisation's rows. In PgBouncer it is the only `stats_users` entry, so it may run the console's `SHOW` commands and nothing else.

1. Set `PG_MONITOR_PASSWORD` in `.env` (the same character rule as the other passwords) and rebuild and restart the server and the pooler: `pg-roles.sh` creates the login with `pg_monitor` on the server's start (only when it is missing; a later password change needs `ALTER ROLE`, as for the other logins) and adds it to PgBouncer's verifier file.
2. Add `postgres-metrics` to `COMPOSE_PROFILES` (next to `postgres`) and `up -d`.
3. Scrape `http://<host>:9187/metrics` and `http://<host>:9127/metrics`. The ports are published on `127.0.0.1` (`PG_METRICS_BIND` changes the address, `PG_EXPORTER_PORT` and `PGBOUNCER_EXPORTER_PORT` the ports); they are unauthenticated plain HTTP, so expose them only to your Prometheus.

The migration job accepts the login (`kernel_0019`, see `backend/db/README.md`); a database without it is unchanged. Statement statistics (`--collector.stat_statements`) are not available with this file: the server loads `pg_stat_statements`, but the extension is not installed in the database, and installing it changes the security surface the migration job compares, so the next `pipeshub-migrate` run would stop with exit 4. This file gives that job no way to accept the extra lines; on a server of your own, the migrate job reads them from the files named in `PG_MIGRATE_SURFACE_FILES` (`backend/db/README.md`). The application's own statement and search latencies (`pipeshub_pg_query_seconds`, `pipeshub_db_query_seconds`, `pipeshub_pgvector_leg_seconds` by search tier) are histograms of the services' telemetry registry, not of these exporters.

## PipesHub on PostgreSQL alone (`docker-compose.postgres-only.yml`)

For a **new** install that should run on one database: documents (`DOC_STORE=postgres`), the graph (`DATA_STORE=postgres`), vectors (`VECTOR_DB_TYPE=pgvector`), configuration (`KV_STORE_TYPE=postgres`), the message queue (`MESSAGE_BROKER=postgres`), the crawl scheduler (`CRAWL_SCHEDULER=postgres`) and what Redis would hold across processes (`REDIS_MODE=postgres`) all live in this PostgreSQL. The MongoDB, Qdrant, Redis, Neo4j, ArangoDB, etcd and Kafka services are removed from the project, so no profile selection (`--profile "*"` included) starts them. An install that already runs those stores keeps them: this override copies no data. Run from a repository checkout with Docker Compose v2.24.4 or later. The simplest way is the installer, which generates the passwords and keeps the override for later runs (`--stop`, `--upgrade`, `--uninstall`); its summary then lists `postgres` for the graph, key-value store and broker:

```bash
cd deployment/docker-compose
PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-only.yml ./install.sh
```

By hand, put the nine `PG_*_PASSWORD` values in `deployment/docker-compose/.env` (see `env.template` there) (`COMPOSE_PROFILES` needs no store profile, for example `COMPOSE_PROFILES=sandbox`; a store profile left in it starts nothing); `postgres`, `pgbouncer` and `pipeshub-migrate` start without their profiles:

```bash
cd deployment/docker-compose     # where .env and the compose files are
docker compose -f docker-compose.yml -f docker-compose.postgres-only.yml -p pipeshub-ai up -d --build
```

Start order: `postgres` healthy, `pgbouncer` healthy, `pipeshub-migrate` exits 0, then `pipeshub-placement` (creates each organisation's vector partition before its first vector write; see `backend/db/README.md`), `pipeshub-fold` (keeps the vector point counts) and the app. Query, indexing and connectors each use their own login through PgBouncer; the other processes read configuration as the key-value login, which is also the one that listens for change notifications on a direct connection to `postgres`. A failed migration stops the app from starting, as above. `tests/postgres_only_test.sh` (run by the `postgres-image` workflow) checks on PostgreSQL 17 and 18, with every profile switched on, that no other store renders or runs and that the app selects PostgreSQL for every store. The Helm chart has no equivalent yet.

## Data volume

The cluster lives in the named volume `<project>_postgres_data`, mounted at `/var/lib/postgresql/data` with `PGDATA` set to that path, on both majors (a `tmpfs` over `/var/lib/postgresql` keeps the 18 image from creating an anonymous volume). `down` then `up` keeps the data; only `down -v` removes it. `PG_MAJOR` is fixed per volume and there is no in-place major upgrade: dump from the old stack and load into a new volume. The server refuses to start on a cluster of another major, and `pg-entrypoint.sh` exits 78 instead of initialising an empty cluster beside one it finds elsewhere on the volume.

Changing a password later: `ALTER ROLE` as the administrative login, update `.env` to match, and restart the `postgres` service, which rewrites `/pgbouncer-auth/userlist.txt`. Existing roles are never altered by the setup, so `.env` alone changes nothing.

## Backups and point-in-time restore (`docker-compose.postgres-backup.yml`)

Opt-in. The backup is physical and covers the whole cluster (one database, `pipeshub`), so every schema, role and extension comes back together and at the same instant. What the application keeps there depends on the stores moved to PostgreSQL:

- with `docker-compose.postgres-docstore.yml` (the commands below; `DOC_STORE=postgres` only): the document store (schemas `identity`, `oauth`, `conversation`, `content`, `integrations`). The graph stays in Neo4j (`neo4j_data`), vectors in Qdrant (`qdrant_storage`), configuration, cache and queues in Redis (`redis_data`);
- with every store on PostgreSQL (`DOC_STORE`, `DATA_STORE`, `KV_STORE_TYPE`, `MESSAGE_BROKER` set to `postgres`, `VECTOR_DB_TYPE=pgvector`): also the graph (`graph`, `kg`), the vectors (`retrieval`), and the key-value store, queue, outbox and scheduled jobs (`platform`).

A PostgreSQL restore brings back only what is in PostgreSQL. Neo4j, Qdrant and Redis are not restored with it and have no point-in-time restore: back them up (with `.env`) the stop-and-copy way, and to bring a whole install back, restore those volumes and restore PostgreSQL to the moment that copy was taken.

**Tool: [pgBackRest](https://pgbackrest.org/) 2.60.0** (MIT licence), from the signed PGDG repository the image already uses; it adds about 1.6 MB to the image (pgBackRest and libssh2). It does full, differential and incremental backups, archives WAL from `archive_command`, restores to a time with `restore --type=time --target=...` and picks the backup that can reach it, expires old backups by retention, checks the archive (`check`), encrypts the repository (`aes-256-cbc`), and stores it on a local path, S3 or any S3-compatible store, Azure Blob, Google Cloud Storage or SFTP ([configuration](https://pgbackrest.org/configuration.html), [user guide](https://pgbackrest.org/user-guide.html)). WAL-G (Apache 2.0) also fits, but its incremental (delta) backups are off by default, a point-in-time restore is assembled by hand from `restore_command` and the recovery settings, and it is not in the PGDG repository ([WAL-G for PostgreSQL](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md)). On Kubernetes, an operator such as CloudNativePG brings its own backups (see Helm below).

**Turn it on.** Copy `pgbackrest.env.example` to `pgbackrest.env` (or name another file with `PGBACKREST_ENV_FILE`), choose the repository in it (default: the `pg_backup_repo` volume on this host, or the host directory named by `PG_BACKUP_REPO`, which the server hands to its `postgres` user, uid 999, at start; for anything that must survive losing the host use S3, Azure or GCS, and set `PGBACKREST_REPO1_CIPHER_PASS`), and add the file to the stack. Every later `docker compose` command and `scripts/pg-restore.sh` need the same files, project and profiles, so set them once (in the shell, or as these lines in `.env`); keep both `postgres` and `postgres-migrate` with the document-store file, or Compose rejects the project (`service "pipeshub-ai" depends on undefined service "pipeshub-migrate"`):

```bash
export COMPOSE_FILE=docker-compose.yml:docker-compose.postgres-docstore.yml:docker-compose.postgres-backup.yml
export COMPOSE_PROJECT_NAME=pipeshub-ai
export COMPOSE_PROFILES=graph-neo4j,sandbox,postgres,postgres-migrate
docker compose up -d
```

With `install.sh`, list the file in `PIPESHUB_COMPOSE_OVERRIDES` as well: the installer passes its own `-f` files, ignores `COMPOSE_FILE`, and reads the last `PIPESHUB_COMPOSE_OVERRIDES` line of `.env` (install.sh saves a command-line value only when it writes a new `.env`). On an existing install, append it and restart through the installer: `echo 'PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-docstore.yml:docker-compose.postgres-backup.yml' >> .env && ./install.sh --no-pull`; without it, a restart through the installer runs the server without archiving and without `pg-backup`. `scripts/pipeshub-compose.sh` is `docker compose` with the stack's files from any shell (`COMPOSE_FILE` when set, else `docker-compose.yml` plus that saved setting); `scripts/pg-restore.sh` and the documented commands use it.

The server restarts once (`archive_mode` is read at start) and from then on sends every finished WAL segment to the repository, and closes a segment at least every `PG_ARCHIVE_TIMEOUT` seconds (default 60). The `pg-backup` service creates the stanza, takes a full backup at once, then a full backup every `PG_BACKUP_FULL_DAYS` (7) and an incremental one every `PG_BACKUP_INCR_HOURS` (6); it reads the schedule back from the repository, so restarts neither skip nor repeat one. With `PGBACKREST_REPO1_RETENTION_FULL=2` the repository keeps two full backups and the WAL since the older one: any point of the last one to two weeks can be restored. `docker compose ps pg-backup` shows `healthy` while the repository holds backups within both intervals (also right after a restart) or the very first full backup is running, and `unhealthy` after a failure (read `docker compose logs pg-backup` then); `docker compose exec pg-backup pgbackrest info` lists the backups and the archived WAL range. Healthy during the first full backup is not protection yet: nothing can be restored until `pgbackrest info` shows `status: ok` and a `full backup: <label>` line (`docker compose exec pg-backup pgbackrest info | grep -E 'status:|full backup:'`). An archive that cannot reach the repository would keep WAL on the data volume until the volume filled and the server stopped, so the archive queue is capped at 4 GiB (`PGBACKREST_ARCHIVE_PUSH_QUEUE_MAX`; raise it, or set it empty for no cap, in `pgbackrest.env`). Beyond the cap pgBackRest drops WAL and reports it archived ([archive-push-queue-max](https://pgbackrest.org/configuration.html#section-archive/option-archive-push-queue-max)): the server stays up, and `pgbackrest-archive-push.sh` (the server's `archive_command`) adds a file per drop to `pgbackrest-wal-gap.d` in the shared socket directory. It sends pgBackRest's warnings to stderr for its own run, so a drop is seen even with the console and stderr log levels off. The file is named by the dropped segment and holds the commit time of that segment's first transaction (read with `pg_waldump` while the segment is still in `pg_wal`); its modification time is when the drop was noticed. The healthcheck fails at once while such a file exists, even during a backup; `pg-backup` logs the first and last dropped segment and when they were noticed. Recovery cannot cross a missing segment, so the gap starts at the earliest dropped one: the log gives that segment's first commit time when it has one (the first transaction lost; the last reachable point is the last commit before it), and otherwise says the last reachable point is before that segment. The noticed times are not the start of the gap (a dropped segment can hold earlier transactions). To restore exactly up to the gap, restore the end of the archive from the newest backup taken before it: `scripts/pg-restore.sh latest --set <label>` (the log names the label). pgBackRest has no per-backup pin, so `pg-backup` runs every backup with `--no-expire-auto` and runs `pgbackrest expire` itself after a backup only when, checked again then, no drop is uncovered and no gap is held. Each gap gets its own hold (a file named by its first dropped segment in `pgbackrest-gap-hold.d` in the socket directory, holding that gap's pre-gap label); a gap's drop files are cleared only once its hold is recorded, so a repository that cannot be read keeps the gap open rather than losing it. Release holds with `scripts/pipeshub-compose.sh exec pg-backup pg-backup.sh clear-gap-hold [<first dropped segment>]`: refused while a drop is uncovered; it takes the lock the scheduler holds around each backup and its expire, runs `pgbackrest expire` first when no other hold remains, and removes the holds only after that succeeded. The repository grows while a hold exists, so a hold nobody clears is released after `PG_BACKUP_GAP_HOLD_DAYS` (default 14, set in `pgbackrest.env`): `pg-backup` logs it loudly and that backup falls under normal retention. A time target just before the gap cannot be reached either, because recovery stops only at a later commit ("if a recovery target is configured but the archive recovery ends before the target is reached, the server will shut down with a fatal error", https://www.postgresql.org/docs/17/runtime-config-wal.html 19.5.6); `scripts/pg-restore.sh` refuses such a target before restoring anything (below). `pg-backup` then takes a full backup at once (retried every `PG_BACKUP_RETRY_SECS`, 300). A successful full backup removes the drop files it listed before it started, never one added during it, so the service is healthy again only when no drop is left uncovered; a restore can reach any time before the first dropped segment or after that backup, nothing between. A repository belongs to the cluster that created it: after replacing the data volume with a new, empty cluster (not a restore), archiving and backups fail until the repository is moved aside or `PGBACKREST_REPO1_PATH` names a new one.

pgBackRest runs as the server's `postgres` user: it connects over the Unix socket (shared by the `pg_backup_socket` volume) and reads the data volume read-only. pgBackRest's documentation runs it as that user and does not document a smaller set of privileges, so the `pipeshub_backup` login (row-level reads for logical exports, `db.restore_window`) is not used for this. Mount `pg_backup_socket` in no other container: it gives the same access. The repository's credentials and passphrase (`pgbackrest.env`) are in the environment of both containers, because the server itself pushes WAL.

**Restore to a point in time** (`scripts/pg-restore.sh`, run from this directory with the same `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME` and `COMPOSE_PROFILES` as above; with files or profiles that do not match, it stops on Compose's error before changing anything):

- `scripts/pg-restore.sh "2026-11-15 09:30:00+00"` restores into a **new** volume and starts it as a separate server (container and volume `<project>_pg_restore_<UTC time>`, or `--into <name>`). It keeps every transaction committed up to that time and none after. The stack is not touched, and the copy does not archive, so it never writes to the repository. It runs within the `pg-backup` service's memory limit (`PG_BACKUP_MEMORY_LIMIT`, default 1G). The script waits until the copy accepts writes; it stops with the copy's log if the server stops, if recovery pauses (a setting such as `max_locks_per_transaction` raised on the original after the backup: start the copy again with it raised), or after `PG_RESTORE_WAIT_SECS` (6 hours). Look at it with `docker exec -it <name> psql -h /tmp -U postgres -d pipeshub`; remove it with `docker rm -f <name> && docker volume rm <name>`.
- `scripts/pg-restore.sh "<time>" --in-place` puts the stack itself back to that time: stop the stack first (`docker compose stop`; the script refuses while `postgres` runs), run it, then `docker compose up -d`. The server replays WAL to the target (the role setup of the image waits until recovery ends, at most `PG_ROLES_RECOVERY_WAIT_SECS`, 6 hours, and logs that it waits), opens a new timeline and goes on archiving, and the next backups continue the same history. Everything committed after the target is gone from the live database (it stays in the repository until expired), so restore into a new volume first when you are not sure of the time.
- `--set <label>` restores from that backup instead of the one pgBackRest picks (after a WAL gap, `latest --set <newest backup before the gap>` restores up to the gap).
- Before restoring to a time or `lsn:`, the script checks in the repository itself (`pgbackrest info`, `repo-ls` and `repo-get`, so it works after losing the machine, when `pg-backup`'s gap files are gone too) that the archived WAL runs without a break from the backup pgBackRest picks to a commit later than the time (one exactly at it does not stop recovery), or a record at or after the location. When it does not (a WAL gap, or a target after the last archived segment), it stops with exit code 4 before touching any volume, naming the last reachable commit, the `latest --set <label>` command that restores up to it, and a later backup a target after the gap can be restored from. Without that check the restored server would stop at the end of recovery and, in place, be started again and again by `restart: always`. It reads the newest 64 segments it reaches at most; when it cannot tell (no commit there, or a segment it cannot read) it says so and restores anyway.
- `lsn:<location>` stops just after the first WAL record at or after that location; it needs no later commit to stop at, which a time does.
- `latest` instead of a time replays every archived segment.
- After losing the machine or its disk, which needs a repository off the machine (the default `pg_backup_repo` volume is lost with it) and `pgbackrest.env` (the repository's credentials and passphrase; the stop-and-copy backup keeps it, and keep another copy apart from the machine and the repository): bring back `.env`, `pgbackrest.env`, the files and the other stores' volumes, build the image (`docker compose build postgres`), and before starting the stack restore PostgreSQL in place to the mark of that backup. The mark is made before the stop-and-copy backup with the application stopped: `docker compose stop pipeshub-ai`, save `select pg_current_wal_lsn()` to `pg-restore-point.txt` in the backup's directory, `select pg_create_restore_point('regular-backup')`, then `docker compose exec pg-backup pgbackrest check` (archives it); restore with `scripts/pg-restore.sh "lsn:$(cat pg-restore-point.txt)" --in-place`, and start with `./install.sh --no-pull`. A time is not used for this: with nothing committed after the backup, recovery to its time cannot stop. The restore by location needs a backup older than the mark still in the repository, so set `PGBACKREST_REPO1_RETENTION_FULL` to cover the oldest stop-and-copy backup you keep (with the defaults, about one to two weeks). `latest` fits only when nothing outside PostgreSQL would be left behind (every store on PostgreSQL, files in object storage).

**RTO and RPO.** Measured by the restore drill (`tests/postgres_backup_restore_test.sh`, `DRILL_ROWS=500000`) on PostgreSQL 18: a 2.2 GB database (ten schemas of 0.5 million rows, one with a pgvector HNSW index), repository on a local volume, zstd, one pgBackRest process, on a shared 32-core host under load. Two runs:

| Step | Time |
|---|---|
| Full backup (562 MB in the repository with the incremental one) | 29-30 s |
| Incremental backup after about 10% of the rows changed | 13-14 s |
| A commit reaches the archive, under write load | 1.2 s |
| A commit reaches the archive, idle (small database; at most `PG_ARCHIVE_TIMEOUT`) | 39-42 s at 60, 20-21 s at 20 |
| Restore to a time into a new volume, until it accepts writes | 146-151 s |
| Restore to the end of the archive into a new volume | 132-137 s |
| Restore to a time over the stack's own volume (`--in-place`), until it accepts writes | 101-112 s |

The drill archived 2.3 GB of WAL (1,010 segments, zstd) for 2.2 GB of data loaded and changed.

- **RPO** (data lost when the database is lost): at most `PG_ARCHIVE_TIMEOUT` (60 s) plus the time to push one segment, while archiving keeps up. A mistake on a running database (a dropped table, a bad update) loses nothing: restore to just before it. With the repository on this host's volume, losing the host loses the backups too: put the repository off the host for a real RPO.
- **RTO** (time until the restored database accepts writes): the restore copies the backup, then replays the WAL since that backup. It grows with database size and with the WAL written since the last backup, which the incremental backup every 6 hours bounds. Raise `PGBACKREST_PROCESS_MAX` to copy in parallel; object storage is slower than a local volume. Targets for a Compose install with the defaults: **RPO 1 minute** (losing the database; 0 for a mistake), **RTO 15 minutes for a database up to 10 GB** with the repository on local disk (the drill restored 2.2 GB in under 2.5 minutes). Re-run the drill with `DRILL_ROWS` near your size, and your repository in `DRILL_PGBACKREST_EXTRA`, to measure your own.

**Helm.** The chart's PostgreSQL server (`postgres.enabled`) has no backups yet. The same pieces apply there: the image carries pgBackRest; the server container gets `PGBACKREST_*` from a Secret (the `pg-entrypoint.sh` archive settings follow `PGBACKREST_STANZA`), `PGBACKREST_LOG_LEVEL_FILE=off` and a writable `/tmp` for the lock file (the pod's root filesystem is read-only); a `pg-backup` container in the same pod runs `pg-backup.sh` with the data volume mounted read-only and `/var/run/postgresql` shared as an `emptyDir`; the repository is object storage (a volume in the same cluster is not a backup); a point-in-time restore is a Job that runs `pgbackrest restore --type=time --target=... --target-action=promote` into a new PersistentVolumeClaim (or `--delta` into the server's own claim with the StatefulSet scaled to 0). A `postgres.mode` of `cnpg` would use CloudNativePG's own backups instead.

## Tests

`tests/pg_entrypoint_layout_test.sh` (no Docker), `tests/postgres_persistence_test.sh` (17 and 18: data survives `down`/`up`, no anonymous volume) and `tests/postgres_roles_test.sh` (roles, privileges, PgBouncer authentication, an empty password refused before any data is written, a volume without roles repaired on restart, no clear-text password anywhere in the server's files, logs or statistics). `tests/pg_roles_script_test.sh` (no Docker) checks that `pg-roles.sh` stops before touching the server when any verifier cannot be computed or is empty, and `tests/postgres_role_failure_test.sh` that a start whose role setup fails leaves the server and the pooler unhealthy and a dependent service unstarted. `tests/postgres_nonroot_test.sh` runs the server and pooler as a non-root user with a read-only root filesystem, no capabilities and no privilege escalation (the restrictions a Kubernetes pod would put on them): first start, roles, pooler authentication, restart. `tests/pg_backup_schedule_test.sh` (no Docker) checks the backup schedule of `pg-backup.sh` and what it does after dropped WAL, and the queue cap of `pgbackrest-archive-push.sh`; `tests/postgres_backup_restore_test.sh` is the restore drill above (17 and 18), and also makes the repository unwritable until the cap drops WAL, and loses the machine: with everything but the repository removed (a local directory on 17 and a named volume on 18, standing in for off-machine storage) and no stack started, it restores in place to the WAL location marked with a restore point as the docs describe and checks the started stack holds that moment (and that a time after the last commit cannot be reached). The `postgres-image` workflow runs them all. The two Docker tests accept `PROJECT_PREFIX` (the compose project name) and `EXTRA_COMPOSE_FILE` (one more compose file, for example to put the project on a network of your own); both are for running the tests on a shared host only and change nothing when unset.
