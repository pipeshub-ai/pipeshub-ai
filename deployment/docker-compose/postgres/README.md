# PostgreSQL image and PgBouncer (compose profile `postgres`)

Opt-in: nothing starts unless `postgres` is in `COMPOSE_PROFILES`, and the application connects to it only with the document-store override below. Without the profile `docker compose config` is unchanged.

- `Dockerfile`: pgvector 0.8.7 base for PostgreSQL 18 (default) or 17, both pinned by digest and multi-arch; adds `pg_textsearch` 1.5.1 and PgBouncer 1.26.1 (source tarballs checked by SHA-256). Build: `docker compose --profile postgres build postgres`. The `postgres` and `pgbouncer` services run the same image.
- `pgbouncer.ini`: transaction pooling with `server_reset_query` and `server_reset_query_always = 1`, so session state (role, settings, temp tables, cursors) never reaches the next client. Do not weaken these. One server pool per login; the sizes add up to at most `max_db_connections`.
- `pg-roles.sh` (run by `initdb/10-roles.sh` at the first initialisation and by `pg-entrypoint.sh` on every start): creates what is missing of the role layout (one login per service, plus jobs, migrate and backup; every `PG_*_PASSWORD` is required, `PG_KV_PASSWORD` included), installs `pg_trgm` into schema `ext` (the image carries pgvector; `vector` is installed with the schema that uses it), and rewrites the SCRAM verifiers PgBouncer authenticates against in the `pgbouncer_auth` volume (mode 0600, read-only in PgBouncer). It never alters an existing role. The verifier file is written last and only when everything succeeded, so it is also the sign of readiness: `pg-entrypoint.sh` removes the old one at start, and the healthchecks of the server and the pooler require it. Because it runs on every start, a volume left without its roles (for example after an interrupted first start) gets them on the next start, and a lost `pgbouncer_auth` volume is refilled. No role has SUPERUSER, CREATEROLE or BYPASSRLS, and a service login holds no privileges until its unit of work switches to its service role. Tables, policies and grants on them come with the migrations.
- `pg-entrypoint.sh`: refuses to start (exit 78) when a required password is empty, before anything is written to the data volume; server defaults (`shared_preload_libraries`, `max_connections`, `shared_buffers`); a refusal to start on a volume whose cluster is not where `PGDATA` points; then the role setup above.
- `scram-verifier.pl`: computes the SCRAM-SHA-256 verifier of a password (read from the environment, printable ASCII only).

Password rule, enforced by `pg-entrypoint.sh` before anything is initialised: every `PG_*_PASSWORD` is non-empty and contains only letters, digits and `. _ ~ -` (the passwords go into connection URLs, and the SCRAM verifier needs printable ASCII). Anything else exits 78 with a message naming the variable.

Secrets: the passwords come from the container environment. They are not in the image, the build context, or the logs. The server never receives a clear-text password: `pg-roles.sh` computes the SCRAM verifiers itself and sends only those (so `pg_stat_statements`, the statement log and `pg_stat_tmp` hold verifiers, not passwords), and turns off statement tracking and logging for its session. The passwords stay in the container's environment (`docker inspect`, `/proc/<pid>/environ` inside), and the verifiers in the database and in the volume's backups; a verifier can be attacked offline, so use long random passwords. A password you set later with `ALTER ROLE ... PASSWORD '<clear text>'` is visible to the server the same way unless you send a verifier.

## Document store on PostgreSQL (`docker-compose.postgres-docstore.yml`)

For a **new** install, the Node API can keep its documents (users, organisations, conversations and the rest) in PostgreSQL instead of MongoDB (`DOC_STORE=postgres`). Run from a repository checkout (the migration job's image is built from `backend/db/Dockerfile`). The simplest way is the installer: `PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-docstore.yml ./install.sh`, which sets both profiles and generates the passwords. By hand, put the `PG_*_PASSWORD` values in `.env` and activate **both** profiles `postgres` and `postgres-migrate` (the override depends on services of both):

```bash
COMPOSE_PROFILES=graph-neo4j,sandbox,postgres,postgres-migrate \
  docker compose -f docker-compose.yml -f docker-compose.postgres-docstore.yml -p pipeshub-ai up -d --build
```

If a profile is missing, compose stops with `service "pipeshub-ai" depends on undefined service "pgbouncer": invalid compose project`; add the profile.

Start order: `postgres` healthy, `pgbouncer` healthy, `pipeshub-migrate` exits 0, then `pipeshub-ai`. The migration job (`python -m db.migrate`, built from `backend/db/Dockerfile`) connects straight to `postgres` (it needs a session and an advisory lock, so not through the pooler) as `pipeshub_migrate`. It is idempotent: a database at head is left as it is, an installed database is upgraded in one transaction, and a failed run changes nothing there. Exit 4 means the catalog or security-surface check found violations; the app is then not started: read `docker compose logs pipeshub-migrate`. Exit codes: `backend/db/README.md`. The app uses the pooled node and jobs logins (`PG_NODE_URL`, `PG_JOBS_URL`, built from the passwords). Cross-process change push (PostgreSQL `LISTEN`) is off, because the pooled node login cannot LISTEN and no direct address (`PG_LISTEN_URL`) is set; only the PostgreSQL-backed key-value store and queue (`KV_STORE_TYPE=postgres`, `MESSAGE_BROKER=postgres`) use it, and this override sets neither. A failed migration stops the app from starting. This does not copy existing MongoDB data, and MongoDB and the other stores stay as they are. `./install.sh --uninstall --yes` keeps the PostgreSQL data volume; add `--delete-postgres` to remove it (an interactive uninstall asks).

### Moving an existing install

`scripts/migrate-to-postgres.sh [--dry-run] [--drain-wait S] [--force-drain] [--flip]` copies the documents of a running MongoDB install into PostgreSQL with the `docstore-migrate` one-shot service (the application image; profile `docstore-migrate`): it drains chat turns, stops the application, runs preflight, copy and verify, and with `--flip` writes `DOC_STORE=postgres` to `.env` and starts the application. MongoDB is left as the rollback source. `scripts/rollback-to-mongo.sh [--reverse]` goes back (`--reverse` copies PostgreSQL changes to MongoDB first). The copy uses its own login, `pipeshub_import`, which is `NOLOGIN` except while a script runs; its generated password is in `.env` only for that run. `docker-compose.mongo-replset.yml` makes MongoDB a one-member replica set for an online move. `tests/migrate_script_fence_test.sh` (no Docker) and `tests/migrate_script_containers_test.sh` (real MongoDB, PostgreSQL, PgBouncer and schema job; the migrator CLI is stood in for) test them.

## Data volume

The cluster lives in the named volume `<project>_postgres_data`, mounted at `/var/lib/postgresql/data` with `PGDATA` set to that path, on both majors (a `tmpfs` over `/var/lib/postgresql` keeps the 18 image from creating an anonymous volume). `down` then `up` keeps the data; only `down -v` removes it. `PG_MAJOR` is fixed per volume and there is no in-place major upgrade: dump from the old stack and load into a new volume. The server refuses to start on a cluster of another major, and `pg-entrypoint.sh` exits 78 instead of initialising an empty cluster beside one it finds elsewhere on the volume.

Changing a password later: `ALTER ROLE` as the administrative login, update `.env` to match, and restart the `postgres` service, which rewrites `/pgbouncer-auth/userlist.txt`. Existing roles are never altered by the setup, so `.env` alone changes nothing.

## Tests

`tests/pg_entrypoint_layout_test.sh` (no Docker), `tests/postgres_persistence_test.sh` (17 and 18: data survives `down`/`up`, no anonymous volume) and `tests/postgres_roles_test.sh` (roles, privileges, PgBouncer authentication, an empty password refused before any data is written, a volume without roles repaired on restart, no clear-text password anywhere in the server's files, logs or statistics). `tests/pg_roles_script_test.sh` (no Docker) checks that `pg-roles.sh` stops before touching the server when any verifier cannot be computed or is empty, and `tests/postgres_role_failure_test.sh` that a start whose role setup fails leaves the server and the pooler unhealthy and a dependent service unstarted. `tests/postgres_nonroot_test.sh` runs the server and pooler as a non-root user with a read-only root filesystem, no capabilities and no privilege escalation (the restrictions a Kubernetes pod would put on them): first start, roles, pooler authentication, restart. The `postgres-image` workflow runs them all. The two Docker tests accept `PROJECT_PREFIX` (the compose project name) and `EXTRA_COMPOSE_FILE` (one more compose file, for example to put the project on a network of your own); both are for running the tests on a shared host only and change nothing when unset.
