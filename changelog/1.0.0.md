# 1.0.0 — Code graphs, deeper retrieval and agent tools, and stricter permission enforcement

**Released:** October 27, 2026 · **Channel:** Stable · **Tag:** [`v1.0.0`](https://github.com/pipeshub-ai/pipeshub-ai/releases/tag/v1.0.0)

1.0.0 is the largest PipesHub release so far: 719 merged PRs since [0.10.0](0.10.0.md). Code repositories get a code graph that agents can explore. Retrieval is rebuilt around one context pipeline, with focused reading and period-by-period timeline search now on by default. Agents can call an organization's own REST APIs as custom actions. Permissions move onto one access check that decides search, record open, the Knowledge Hub and agent tools. Classification and named-entity extraction run as their own pipeline stages after a record is searchable. A Zendesk connector arrives, and an audit of nearly every connector fixes pagination, deletion, partial-failure and access handling.

1.0.0 also removes things and changes defaults, so read the upgrade notes before upgrading. SAML and generic OAuth sign-in are gone. The graph database is migrated one way on first start, so back it up first. New `client_credentials` apps must name a service account. The Helm chart requires a Qdrant API key. Code-graph routes need a new `code:read` scope.

## Breaking changes & upgrade notes

- **Back up the graph database first. Permissions and the Knowledge Hub use a reworked graph model, and the migration is one-way.** Hierarchy now lives on one edge (`NODE_RELATION` on Neo4j, `nodeRelations` on ArangoDB), links between records move to their own edge (`RECORD_LINK` / `recordLinks`), and a nested record inherits from its hierarchy parent instead of from its record group. The connector service migrates an existing graph when it starts. The edge rename runs first and is the only migration that can stop the service; the rest run in the background with retries. Until they finish, a deployment lists less than it should, never more. Run a full sync of each connector after upgrading: it writes what an old graph does not record, such as per-node access rules and records nested under a record with its own grants. A release older than 1.0.0 cannot read the migrated graph ([#4255](https://github.com/pipeshub-ai/pipeshub-ai/pull/4255) — @shrikant-pipeshub).
- **Some access results differ from 0.10.0.** A record whose parent is in another record group (a Jira story under an epic of another project) keeps its own project's audience. An item shared with a user on its own, whose containers they cannot open, is listed directly under its connector. A grant on one connector never admits a record of another connector. A search whose permission check cannot run answers "permission check unavailable" instead of an empty result. The Collection roles `ORGANIZER` and `FILEORGANIZER` are read as `READER`, so re-grant `WRITER` where those users must still create folders or delete files ([#4255](https://github.com/pipeshub-ai/pipeshub-ai/pull/4255) — @shrikant-pipeshub).
- **Saved agents and knowledge sources:** an agent whose knowledge source lists `filters.recordGroups` or `filters.records` now searches only those nodes. The lists were stored but not applied before, so such an agent becomes narrower on upgrade. To keep searching the whole source, tick the whole source again in the agent builder, or clear the lists. A source whose stored `filters` cannot be read is no longer searched at all; re-save the agent to repair it ([#4255](https://github.com/pipeshub-ai/pipeshub-ai/pull/4255) — @shrikant-pipeshub).
- **Knowledge Hub API:** `GET /api/v1/knowledgeBase/knowledge-hub/nodes` and `.../nodes/{parentType}/{parentId}` page by a signed `cursor` and return `pagination.nextCursor` / `prevCursor`. `page` still works up to page 50; deeper paging needs the cursor. Five connector-service record routes with no gateway caller are removed: `GET /api/v1/records`, `GET /api/v1/kb/records`, `POST /api/v1/kb/{kbId}/records`, `POST /api/v1/kb/{kbId}/folder/{folderId}/records` and `GET /api/v1/kb/{kbId}/folder/{folderId}/user/{userId}` ([#4255](https://github.com/pipeshub-ai/pipeshub-ai/pull/4255) — @shrikant-pipeshub).
- **Sign-in:** SAML single sign-on and generic OAuth/OIDC sign-in are removed, and Azure AD sign-in is now Microsoft sign-in. Password, email OTP, Google and Microsoft sign-in stay. On first start a migration moves workspaces that used the removed methods to password sign-in, and Workspace → Authentication lists the people who have no password yet. They can use "Forgot password" (needs SMTP), or the operator can print a set-password link with `node dist/scripts/set-password-link.js <email>` in the backend container. See `docs/deployment/upgrading-to-1.0-sign-in.md` ([#4217](https://github.com/pipeshub-ai/pipeshub-ai/pull/4217) — @shekharkadyan).
- **Application identity:** a new application that allows `client_credentials`, or an existing one that gains that grant, must name the service account its tokens act as. Existing applications keep working; administrators can bind each one to a service account from its manage panel, which revokes its outstanding tokens ([#4517](https://github.com/pipeshub-ai/pipeshub-ai/pull/4517), [#4538](https://github.com/pipeshub-ai/pipeshub-ai/pull/4538) — @shekharkadyan).
- **Code graph:** the code-graph REST routes and MCP tools need the new `code:read` scope. OAuth tokens and personal access tokens issued before the upgrade get no code access until they are re-issued with it. If `.env` or Helm values set `MCP_SCOPES` explicitly, add `code:read`; without it the first-run bootstrap stops with "Scopes not allowed for this app: code:read". Repositories indexed before the upgrade get a graph only when re-indexed, or on the next start with `CODE_GRAPH_BACKFILL=true` on the connectors service ([#3841](https://github.com/pipeshub-ai/pipeshub-ai/pull/3841) — @tushar1245).
- **GitHub and GitLab:** "Index Test Files" is off by default, including on existing connectors. Test files are synced but not indexed until it is turned on; turning it on re-syncs the connector ([#3841](https://github.com/pipeshub-ai/pipeshub-ai/pull/3841) — @tushar1245).
- **Staged indexing:** classification and named-entity extraction run as the `classify` and `entities` stages, on the new topics `pipeline.classify` and `pipeline.entities`. On Kafka the indexing service creates both at startup; where its principal may not create topics, or the cluster needs more replicas, create them before upgrading. In split deployments, upgrade the Extraction service with or before the indexing service. `DEFER_EXTRACTION` is removed. Rolling back to 0.10.0 on ArangoDB needs a data cleanup first; see `docs/indexing-service.md` §2.5 ([#3270](https://github.com/pipeshub-ai/pipeshub-ai/pull/3270) — @abhishekgml1991).
- **Helm:** `qdrant.apiKey` no longer defaults to the public value `api_key`, and the chart refuses to render without a real key (generate one with `openssl rand -hex 32`). `arango.auth.rootPassword` may no longer be `root` ([#3893](https://github.com/pipeshub-ai/pipeshub-ai/pull/3893) — @abhishekgml1991).
- **Connector API:** `POST /connectors/:connectorId/filters` is deprecated and logs a warning on each call. Use `PUT /connectors/:connectorId/config/filters-sync`. The route is removed in a later release ([#4263](https://github.com/pipeshub-ai/pipeshub-ai/pull/4263) — @shekharkadyan).
- **Defaults:** focused reading (`TARGETED_RETRIEVAL`), timeline search (`TIMELINE_SUMMARIES`) and MCP servers (`ENABLE_MCP`) are on by default. A workspace that saved `ENABLE_MCP` keeps its saved value. Neo4j writes are atomic by default (`NEO4J_EXPLICIT_TRANSACTIONS=true`) ([#4343](https://github.com/pipeshub-ai/pipeshub-ai/pull/4343), [#4349](https://github.com/pipeshub-ai/pipeshub-ai/pull/4349), [#4430](https://github.com/pipeshub-ai/pipeshub-ai/pull/4430), [#4484](https://github.com/pipeshub-ai/pipeshub-ai/pull/4484)).
- **Experimental features stay opt-in:** knowledge-base push (`ENABLE_KB_PUSH`), the PostgreSQL infrastructure backends and their migration tooling. Artifact-set writes and reads are gated separately ([#4764](https://github.com/pipeshub-ai/pipeshub-ai/pull/4764), [#4704](https://github.com/pipeshub-ai/pipeshub-ai/pull/4704), [#4705](https://github.com/pipeshub-ai/pipeshub-ai/pull/4705), [#4706](https://github.com/pipeshub-ai/pipeshub-ai/pull/4706), [#4574](https://github.com/pipeshub-ai/pipeshub-ai/pull/4574), [#4599](https://github.com/pipeshub-ai/pipeshub-ai/pull/4599) — @abhishekgml1991).

## Highlights

### Code graph for code repositories

GitHub and GitLab repositories are indexed into a navigable graph of files, symbols and calls, and agents get tools to explore it and analyze the impact of a change. Later work improved TypeScript call resolution, extended impact traversal to five levels and path searches to eight hops. The routes and MCP tools are gated by a new `code:read` scope, and repositories indexed before the upgrade are re-indexed on request or with `CODE_GRAPH_BACKFILL=true` ([#3841](https://github.com/pipeshub-ai/pipeshub-ai/pull/3841), [#4809](https://github.com/pipeshub-ai/pipeshub-ai/pull/4809), [#4844](https://github.com/pipeshub-ai/pipeshub-ai/pull/4844), [#4926](https://github.com/pipeshub-ai/pipeshub-ai/pull/4926) — @tushar1245).

### Retrieval: one context pipeline, focused reading and timeline search

Search results reach the model through one relevance-ordered context pipeline, with deeper fusion, record-level result cuts, better exact-text matching and better handling of images, lists, tables and neighboring passages ([#3489](https://github.com/pipeshub-ai/pipeshub-ai/pull/3489), [#4143](https://github.com/pipeshub-ai/pipeshub-ai/pull/4143), [#4146](https://github.com/pipeshub-ai/pipeshub-ai/pull/4146), [#4254](https://github.com/pipeshub-ai/pipeshub-ai/pull/4254)). Agents can read only the part of a record that matters, search a date range period by period, and use timeline search automatically for spans longer than a month; focused reading and timeline search are now on by default ([#4291](https://github.com/pipeshub-ai/pipeshub-ai/pull/4291), [#4296](https://github.com/pipeshub-ai/pipeshub-ai/pull/4296), [#4373](https://github.com/pipeshub-ai/pipeshub-ai/pull/4373), [#4386](https://github.com/pipeshub-ai/pipeshub-ai/pull/4386), [#4343](https://github.com/pipeshub-ai/pipeshub-ai/pull/4343), [#4349](https://github.com/pipeshub-ai/pipeshub-ai/pull/4349) — @shekharkadyan). `POST /api/v1/retrieve` returns chunks with citations without storing a conversation ([#4732](https://github.com/pipeshub-ai/pipeshub-ai/pull/4732) — @shekharkadyan).

### One access check for permissions, and a faster Knowledge Hub

One batch access check now decides record open, search filtering and the agent tools, and the Knowledge Hub lists by walking the record hierarchy with per-node access rules and cursor paging. Connector sync writes record batches in real transactions of 100 ([#4255](https://github.com/pipeshub-ai/pipeshub-ai/pull/4255) — @shrikant-pipeshub). Around it, Jira issue-security levels are enforced, SharePoint and OneDrive sharing and inherited access are corrected, stored record access rules are preserved, and team grants no longer make knowledge-base members owners ([#4738](https://github.com/pipeshub-ai/pipeshub-ai/pull/4738), [#4383](https://github.com/pipeshub-ai/pipeshub-ai/pull/4383), [#4350](https://github.com/pipeshub-ai/pipeshub-ai/pull/4350), [#4772](https://github.com/pipeshub-ai/pipeshub-ai/pull/4772), [#4767](https://github.com/pipeshub-ai/pipeshub-ai/pull/4767), [#4626](https://github.com/pipeshub-ai/pipeshub-ai/pull/4626)). Synchronization is safer too: interrupted full syncs resume, cleanup waits for the sync to finish, and existing access is kept when a permission read fails ([#4081](https://github.com/pipeshub-ai/pipeshub-ai/pull/4081), [#4112](https://github.com/pipeshub-ai/pipeshub-ai/pull/4112), [#4119](https://github.com/pipeshub-ai/pipeshub-ai/pull/4119), [#4485](https://github.com/pipeshub-ai/pipeshub-ai/pull/4485), [#3732](https://github.com/pipeshub-ai/pipeshub-ai/pull/3732)).

### Staged indexing

A record is searchable as soon as its vectors are written. Classification and named-entity extraction then run as their own `classify` and `entities` stages, each with its own retries, behind one LLM gateway that caps, times out and circuit-breaks indexing-time model calls. A slow or unavailable model no longer stalls unrelated records, and a retry no longer re-parses and re-embeds the record ([#3270](https://github.com/pipeshub-ai/pipeshub-ai/pull/3270), [#4495](https://github.com/pipeshub-ai/pipeshub-ai/pull/4495) — @abhishekgml1991). Failed named-entity extraction can be counted and retried from the stats panels ([#4467](https://github.com/pipeshub-ai/pipeshub-ai/pull/4467), [#4564](https://github.com/pipeshub-ai/pipeshub-ai/pull/4564) — @abhishekgml1991), and stage status, connector fairness and recovery of stranded work are improved ([#4194](https://github.com/pipeshub-ai/pipeshub-ai/pull/4194), [#4215](https://github.com/pipeshub-ai/pipeshub-ai/pull/4215) — @shekharkadyan).

### Custom API actions

An organization's REST APIs can be connected from an OpenAPI specification and called by agents as actions. Users can add personal actions and connect actions directly from chat ([#4435](https://github.com/pipeshub-ai/pipeshub-ai/pull/4435), [#4324](https://github.com/pipeshub-ai/pipeshub-ai/pull/4324), [#4227](https://github.com/pipeshub-ai/pipeshub-ai/pull/4227) — @tushar1245).

### Sign-in and OAuth for 1.0

SAML and generic OAuth sign-in are removed, and existing workspaces move to password sign-in on their own ([#4217](https://github.com/pipeshub-ai/pipeshub-ai/pull/4217) — @shekharkadyan). OAuth gets granular connected-app consent, atomic refresh-token rotation, single-use authorization codes, device-token revocation and server-side session termination on logout ([#4451](https://github.com/pipeshub-ai/pipeshub-ai/pull/4451), [#4777](https://github.com/pipeshub-ai/pipeshub-ai/pull/4777), [#4776](https://github.com/pipeshub-ai/pipeshub-ai/pull/4776), [#4647](https://github.com/pipeshub-ai/pipeshub-ai/pull/4647), [#4790](https://github.com/pipeshub-ai/pipeshub-ai/pull/4790)), and new `client_credentials` apps act as a named service account ([#4517](https://github.com/pipeshub-ai/pipeshub-ai/pull/4517), [#4538](https://github.com/pipeshub-ai/pipeshub-ai/pull/4538) — @shekharkadyan).

### Zendesk connector, and a connector audit

A Zendesk connector syncs tickets, Help Center content, users, groups and organizations ([#2836](https://github.com/pipeshub-ai/pipeshub-ai/pull/2836) — @anupPradhan0). Nearly every connector went through a checklist audit, fixing pagination, deletions, partial failures, credentials, failure notifications and access synchronization; the fixes are listed under [Bug fixes](#bug-fixes).
