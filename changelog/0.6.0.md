# 0.6.0 — The new agent loop ships stable, and the query service gets ~1.8× faster

**Released:** August 10, 2026 · **Channel:** Stable · **Tag:** [`v0.6.0`](https://github.com/pipeshub-ai/pipeshub-ai/releases/tag/v0.6.0)

*This stable release finalizes [0.6.0-beta](0.6.0-beta.md); its notes cover the full range since 0.5.0.*

0.6.0 stabilizes the two engine rewrites introduced in the beta — the new agent loop and the standalone parsing & extraction services — and layers ~50 additional PRs of hardening on top: a query-service performance overhaul (~1.8× throughput, p50 latency halved), a fix for a Redis Streams producer bug that could poison publishing process-wide, OpenAI Responses API compatibility fixes, DOCX/CSV chat attachments, and an Omnigent integration for the PipesHub MCP server. Roughly 195 merged PRs since 0.5.0.

Operators upgrading from 0.5.0 should read the upgrade notes: this release runs a knowledge-base record-group migration, introduces the parsing-service flag, removes `GRAPH_DB_TYPE`, changes the Helm chart's default message broker to Redis, and raises the Docker image RAM limit.

## Highlights

### New agent loop, now the only mode

The agent runtime was reimplemented with a new loop ([#2702](https://github.com/pipeshub-ai/pipeshub-ai/pull/2702) — @abhishekgml1991) and, in this stable release, becomes the sole execution mode ([#2879](https://github.com/pipeshub-ai/pipeshub-ai/pull/2879)). The Slack bot was moved onto the new loop ([#2857](https://github.com/pipeshub-ai/pipeshub-ai/pull/2857) — @kaushal1999), prompts were tuned for it ([#2848](https://github.com/pipeshub-ai/pipeshub-ai/pull/2848)), and its navigate/lookup tools are now exposed as HTTP endpoints so the MCP server can consume them as MCP tools ([#2937](https://github.com/pipeshub-ai/pipeshub-ai/pull/2937) — @uncleSlayer). Reasoning-effort support runs through the stack: model handling ([#2858](https://github.com/pipeshub-ai/pipeshub-ai/pull/2858)), agent model fixes ([#2896](https://github.com/pipeshub-ai/pipeshub-ai/pull/2896) — @vishwjeet-pawar03), friendly provider names with the reasoning flag defaulted on ([#2870](https://github.com/pipeshub-ai/pipeshub-ai/pull/2870)), a reasoning parameter on indexing LLM calls ([#2932](https://github.com/pipeshub-ai/pipeshub-ai/pull/2932) — @tushar1245), and `defaultReasoningEffort` declared on agent schemas in the OpenAPI spec ([#2877](https://github.com/pipeshub-ai/pipeshub-ai/pull/2877)). Deep-agent stale tasks were fixed early in the cycle ([#2656](https://github.com/pipeshub-ai/pipeshub-ai/pull/2656) — @vishwjeet-pawar03).

### Query service performance overhaul

A chat turn was redoing work proportional to the whole answer on every streamed token — roughly 700 times per turn, in three independent places — plus a record-cache bug forced repeat fetches to re-download whole documents. All four were fixed ([#2872](https://github.com/pipeshub-ai/pipeshub-ai/pull/2872) — @shrikantNemiwal1): ~1.8× throughput (23 → 43 req/min at 4 workers / 16 users), p50 turn latency halved (36 s → 17.8 s), and SSE traffic down 28×, with the answer itself unchanged.

### Parsing and data extraction as standalone services

Document parsing and data extraction were split out of the indexing path into their own services ([#2541](https://github.com/pipeshub-ai/pipeshub-ai/pull/2541) — @abhishekgml1991), gated by a parsing-service flag ([#2734](https://github.com/pipeshub-ai/pipeshub-ai/pull/2734)). Follow-ups hardened concurrency ([#2738](https://github.com/pipeshub-ai/pipeshub-ai/pull/2738)), fixed the HTML parser and other parsing paths ([#2749](https://github.com/pipeshub-ai/pipeshub-ai/pull/2749) — @jatingaur18, [#2770](https://github.com/pipeshub-ai/pipeshub-ai/pull/2770)), added health status for both services ([#2845](https://github.com/pipeshub-ai/pipeshub-ai/pull/2845) — @rish664) plus build targets ([#2822](https://github.com/pipeshub-ai/pipeshub-ai/pull/2822)), and dropped base64 encoding when sending PDFs to the Docling service ([#2792](https://github.com/pipeshub-ai/pipeshub-ai/pull/2792) — @kaushal1999).

### Smarter, cheaper PDF and OCR pipeline

Docling is now the default PDF parser (with a BlockParser bug fix) and falls back to OCR when it fails ([#2724](https://github.com/pipeshub-ai/pipeshub-ai/pull/2724), [#2672](https://github.com/pipeshub-ai/pipeshub-ai/pull/2672) — @kaushal1999). OCR got safer and faster: an individual VLM-OCR instance per parse call ([#2739](https://github.com/pipeshub-ai/pipeshub-ai/pull/2739)), a cap on OCR-detection pages ([#2790](https://github.com/pipeshub-ai/pipeshub-ai/pull/2790)), Docling memory and latency optimizations ([#2809](https://github.com/pipeshub-ai/pipeshub-ai/pull/2809)), and batched LLM calls for table indexing ([#2844](https://github.com/pipeshub-ai/pipeshub-ai/pull/2844)).

### OpenSearch joins the supported backends

OpenSearch is now a supported search backend ([#2547](https://github.com/pipeshub-ai/pipeshub-ai/pull/2547) — @abhishekgml1991), extending deployment options for organizations standardized on OpenSearch.

### Redis Streams producer survives disconnects again

`disconnect()` on the shared Redis Streams producer used ioredis `quit()`, which is terminal — one request handler stopping the singleton producer poisoned publishing for the whole process until restart. The client is now recreated on reconnect, restoring producer/consumer recovery after any disconnect ([#2867](https://github.com/pipeshub-ai/pipeshub-ai/pull/2867) — @anupPradhan0).

### MCP grows: Omnigent integration and new tools

A ready-to-run Omnigent agent now ships under `integrations/omnigent/`, exposing the full PipesHub MCP tool set with chat-first routing (`pipeshub_chat`, `pipeshub_search`, `pipeshub_sources`, and more) against the existing `/mcp` server ([#2902](https://github.com/pipeshub-ai/pipeshub-ai/pull/2902) — @shekharkadyan). The MCP server itself was updated to v2.2.0 ([#2780](https://github.com/pipeshub-ai/pipeshub-ai/pull/2780) — @uncleSlayer), with a scope fix and a fetch-full-record API ([#2726](https://github.com/pipeshub-ai/pipeshub-ai/pull/2726)) and a fetch-full-record tool bug fix ([#2743](https://github.com/pipeshub-ai/pipeshub-ai/pull/2743)).

### Bulk user invites, with a review step

Admins can upload a CSV or Excel file of email addresses — parsed, validated, normalized, and deduplicated server-side, with invitations processed asynchronously ([#2715](https://github.com/pipeshub-ai/pipeshub-ai/pull/2715) — @anupPradhan0). The stable release adds a review screen so imports can be inspected before invites are sent ([#2912](https://github.com/pipeshub-ai/pipeshub-ai/pull/2912)).

## Breaking changes & upgrade notes

- Knowledge-base record groups are migrated to connectors; the migration runs as part of this release ([#2650](https://github.com/pipeshub-ai/pipeshub-ai/pull/2650) — @tushar1245).
- Parsing and extraction now run as separate services controlled by a flag — review your deployment config before enabling ([#2541](https://github.com/pipeshub-ai/pipeshub-ai/pull/2541), [#2734](https://github.com/pipeshub-ai/pipeshub-ai/pull/2734)).
- The env template was refreshed and the redundant `GRAPH_DB_TYPE` key removed from Dockerfiles; the Helm chart now defaults the message broker to Redis, deploying Kafka/ZooKeeper pods only conditionally ([#2887](https://github.com/pipeshub-ai/pipeshub-ai/pull/2887) — @tushar1245).
- The Atlassian site URL field was removed from connector configuration ([#2693](https://github.com/pipeshub-ai/pipeshub-ai/pull/2693)).
- The PipesHub Docker image RAM limit was increased — check host sizing ([#2853](https://github.com/pipeshub-ai/pipeshub-ai/pull/2853)); the database sandbox was disabled ([#2854](https://github.com/pipeshub-ai/pipeshub-ai/pull/2854)).
