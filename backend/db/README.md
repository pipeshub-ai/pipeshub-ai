# backend/db: PostgreSQL schema migrations

One Alembic environment for the whole product, SQL-first (no models, no autogenerate), on sync psycopg 3.
It runs in its own image (`backend/db/Dockerfile`, `pipeshubai/pipeshub-migrate`) with `python -m db.migrate`.

## Layout
- `versions/<module>/NNNN_<verb>_<object>.{py,sql}`: one directory per module = Alembic branch. Branches normally own their matching PostgreSQL schema; `kernel_0005` is the exception because it creates `platform.consumer_inbox` before the `platform` branch begins.
  The `.py` file is a short wrapper (`run_sql(__file__)`); the `.sql` file is the reviewed artifact.
- Revision ids are `<module>_<NNNN>`; `NNNN` is the module's **epoch**. `env.py` writes it to
  `kernel.schema_epoch` in the same transaction as the revision. On a database that already has revisions, one transaction covers
  all the pending revisions and the catalog and surface checks below, so a run that exits 4 rolls back the revisions and the epochs it
  applied and leaves the database as it found it. An empty database is built revision by revision and checked at the end (all of them in
  one transaction hold about 6,600 locks, more than a default `max_locks_per_transaction` is sized for); if an upgrade of an installed
  database ever fails with "out of shared memory", raise `max_locks_per_transaction` and re-run: the failed run changed nothing. A revision that sets `min_code_epoch = N` is a
  contract: code built before epoch N must not run (`boot_assert.schema_problems`).
- `kernel_0001`: roles (only when missing), schemas `kernel` and `ext`, `schema_epoch`/`set_epoch`,
  `completed_jobs`/`require_job_done`, `pg_major`, `has_extension`. `kernel_0002`: `platform.deployment_profile`
  and `kernel.assert_profile_epoch`. `kernel_0003`: the org isolation registry and helpers (see Org isolation). `kernel_0004`:
  the `kernel.rls_violations` catalog check. `kernel_0009`: registry columns, the vetted function checks (`kernel.vetted_violations`, folded into `kernel.rls_violations`). `kernel_0010`: `kernel.org_lineage` and its extension point (see Vetted functions). `kernel_0011`: person-level tables and functions, jobs-only import/sweep checks, the dedupe exception, the fence barrier, lock keys and sequence waivers (see Person-level tables and jobs functions).
- `platform` (schema = branch) starts empty at `platform_0001` and depends on the kernel. `platform_0001` adds `platform.store_epoch` (one row naming the live
  document store, its epoch and a read-only flag), `kernel.assert_store_epoch(int)`, the registered prologue fence that the Node write units call, and
  `kernel.postgres_store_epoch()`, the start-up reader (both SECURITY DEFINER, owned by `pipeshub_vetted_kernel`; the table is in `kernel.vetted_extension_reads`
  and the service roles hold no privilege on it). Other modules add their own branches and tables with the code that uses them.
- `platform_0002`: the state of background jobs. `platform.job_start`, `platform.job_finish` (executable by the owner role, for the operator) and
  `platform.job_checkpoint` (progress only, only while the job runs; the document-store copy saves it with the import login, and since `platform_data_0006` the jobs login, which every background process holds, may not) are the only writers of `platform.jobs`; owner `pipeshub_vetted_platform`.
  A unique partial index admits one running job of a kind.
- `platform_0003`: the runtime's own state when no Redis is deployed (`KV_STORE_TYPE=postgres`, `MESSAGE_BROKER=postgres`). `platform.kv_entries` (key, bytes, optional expiry) is the key-value store; `platform.queue_messages`, `queue_groups` and `queue_deliveries` are a work queue with consumer groups (claim with `FOR UPDATE SKIP LOCKED`, attempts, retry backoff, dead letter, NOTIFY wake-up; an ephemeral group is dropped when its process stops refreshing it). All four are `internal` tables (no org column: an event's org travels in its signed envelope), granted to the four service roles. Reached through `KernelDB.runtime_uow()` (Python) and `withUow({ preOrg: true })` (Node).
- `kernel_0014` (the key-value role): `pipeshub_kv`, a service role that reads and writes `platform.kv_entries` and calls the fence and holds nothing on any org table, for the processes that only read configuration (`PG_CORE_KV_URL`).
- `kernel_0016` (pinned writes): `kernel.vetted_write_pins`, `kernel.allow_vetted_write_op(function, table, op, ...)`, `kernel.pin_writers` and the checks 100-117, 120-125 and 130-135 in `kernel.pin_violations` (the privilege checks 124, 126 and 127 and the policy checks 118, 119 and 128 are `kernel_0017`'s) (folded into `kernel.rls_violations`). An org-scoped vetted write function may DELETE or use `ON CONFLICT` only where it is pinned, and only in the fixed shapes of "Pinned writes" below. Not a contract (`min_code_epoch` stays 11): no earlier code has a pin, and every earlier check still applies to a function without one.
- `kernel_0017` (per-org vetted policy): `kernel.require_vetted_org_policy(table, open_ops)` gives the vetted writer role of a table a row policy bound to `app.org_id` (not `USING (true)`), keeps its privileges equal to its pins and closes the table to every application role except the operations listed as open; checks 118, 119, 124, 126, 127, 128 (`kernel.org_policy_violations`; 118 and 128: every pinned table, and every table that its vetted role writes in a schema that owns a pin, must ask for the policy). Separate from 0016 so a deployment that wants no per-org machinery can leave it out of the chain it ships.
- `kernel_0019` (the monitoring role): check 37 accepts one more membership, `pipeshub_monitor -> pg_monitor`, inherited and without ADMIN or SET; any other membership of that role is still a violation. The role is opt-in: `db.bootstrap_roles` creates it, a login, only when `PG_MONITOR_PASSWORD` is set (granting `pg_monitor` needs an administrator, which the migrate login is not), and the compose image does the same (`deployment/docker-compose/postgres/README.md`, "Metrics"). `pg_monitor` reads the statistics views, the settings and the monitoring functions ([PostgreSQL: Predefined Roles](https://www.postgresql.org/docs/18/predefined-roles.html)); the role holds no privilege on any schema of ours, so a metrics exporter logged in as it sees the server's statistics and no organisation's rows. Statement text is part of those statistics (`pg_stat_activity.query`, `pg_stat_statements`); the services send values as bound parameters, not in the text. Its two surface lines are optional (below).
- `kernel_0020` (the org write hold): both write fences (`kernel.assert_profile_epoch`, the Python units', and `kernel.assert_store_epoch`, the Node document store's) also refuse, with `25006` like a closed fence, a unit whose org `kernel.org_writes_held(org)` holds. The fence reads the unit's org from `app.org_id`; both prologues (`app/core/db/uow.py`, `src/libs/db/uow.ts`) set it in their materialized `pre` subquery, which the subquery that calls the fence reads, so the org is set before the fence runs (a data dependency, not the order of expressions in one select list, which PostgreSQL does not define); a unit with no org is never held. The fence asks for the hold after it holds its install-wide barrier (`7341`, the profile fence; `7340`, the document store's), shared to commit, and takes no lock of its own for it. Whoever records a hold must first take both exclusively, `pg_advisory_xact_lock(7341, 1)` then `pg_advisory_xact_lock(7340, 1)`, in the transaction that records it: that waits for every write unit already past its fence to end, refuses (`25006`) the ones that start meanwhile (every org's, for that short transaction), and every unit whose fence runs after it commits sees the hold. A hold recorded without those locks does not stop a unit that passed its fence before. Recording a hold is rare and a write unit is not, so the pause is put on the first rather than a lock on the second. Here `org_writes_held` holds no org, so every write passes as before (one more call of a function that returns `false` per write unit that has an org); it is an extension point (see Vetted functions) for a deployment that pauses one org's writes, for example while that org is restored, instead of switching every login off.
- `kernel_0021` (the owner's erase policy): every org table and every partition carries `org_erase`, a permissive policy for the owner role only, `USING` and `WITH CHECK` `kernel.org_erase_allows(org_id)`. It lets the owner delete an org's rows under row security, so the table is never changed (no lifted `FORCE ROW LEVEL SECURITY`, no disabled trigger, no lock beyond the rows), and the triggers that write that org's derived rows while it goes can do so. `kernel._secure_rel` gives it to every new table and leaf. `kernel.org_erase_allows` is a plain owner function that answers `false` here, so the owner still reaches no org row; a deployment that removes one org's rows replaces its body from an extra migration location (the security surface pins it). Check 04 accepts the policy only in exactly that shape, and check 142 requires it on every org relation.
- `kernel_0022` (the jobs' write fence): `kernel.assert_org_writable(org)`, executable by the jobs role, takes the profile fence's barrier (`7341`) shared, to commit, as the Python write units do (so whoever records a hold waits for the job), and refuses (`25006`) an org `kernel.org_writes_held` holds. The per-org steps of the maintenance jobs (`fold`, `recount`, the bounds fill, `group-gc` and the nightly purge, through `db.lib.fold.org_lock`) call it first in their transaction, so a held org gets no derived rows from a job; it is reported as failed and folded on the next pass.
- `kernel_0023` (an extension schema's own vetted owner): `kernel.declare_extension_schema` also accepts a schema whose vetted owner exists, while that owner is fresh (`kernel._fresh_vetted_owner`), and refuses a schema the owner role does not own; see Vetted functions.
- `platform_0004`: the job scheduler without Redis. `platform.sched_jobs` (one row per run: waiting/delayed/active/completed/failed, `run_at`, attempts, progress, claim) and `platform.sched_repeats` (one row per schedule). Internal tables like the queue tables; claimed with `FOR UPDATE SKIP LOCKED`, so two Node processes never start the same run. Used by `PgJobQueue` / `PgJobWorker` (`libs/services/pg-job-queue.service.ts`) when `CRAWL_SCHEDULER=postgres`.
- `kernel_0018` (internal policies): `kernel.register_internal_policy(table, policy)` lets an internal table (no org column) carry row policies; check 04 skips a registered policy, and checks 140 (a registered policy is gone, or its table is no longer internal) and 141 (a registered policy's command, roles, permissive flag or expressions changed) keep it as registered. Its downgrade refuses while a policy is registered.
- `platform_0006` (key-value access by prefix): row policies on `platform.kv_entries` give each service role the key prefixes it uses (`platform.kv_may(key, write)`: node every key; connectors and query read all but the Node API's own mail, chat-bot, sign-in, MCP access-policy and crawl keys and write their own; indexing and kv read an allow-list of exactly the keys their code reads, with `platform.kv_admin_or_credential` (the Node API's own settings and the connector, OAuth-app, toolset, API-toolset, MCP, web-search and parked-turn keys) refused on top of it; indexing writes its own prefixes and kv writes nothing). `tests/test_kv_access_map.py` keeps those allow-lists in step with the code: every key the services can reach is listed with the line that reads it or with why it is not read, and the matrix grants exactly the listed keys. Its limits: it sees the keys the code names (constants, string and f-string literals) in each service's import closure, not keys assembled at run time from other values; it classifies reads only (the write allow-lists are checked by the per-role enforce tests in `tests/test_integration.py`); the closure is nearly the whole package, so a `NOT_READ` entry (a reachable key the service never reads) is a reviewed claim, not something the scan proves. The mode is one row, `platform.kv_access`: **shadow** (the default until `platform_0014`) admits everything and writes each access outside a role's prefixes to the server log (`pipeshub kv access outside the role's prefixes (shadow): role ..., read|insert|update|delete, key under <first three path segments>`; level LOG, never the value); **enforce** (the default from `platform_0014`) refuses it (the row is not visible; an insert or upsert fails with 42501). Set it with `PG_KV_ACCESS=shadow|enforce` on `python -m db.migrate` (applied after the upgrade; unset keeps the stored mode, any other value exits 2). Kill switch: `PG_KV_ACCESS=shadow` and run the migrate job again, or `SET ROLE pipeshub_owner; UPDATE platform.kv_access SET enforce = false` as the migrate login; the next statement of every service sees it. While the stored mode is shadow, every `db.migrate` run prints `WARNING key-value access by prefix is in shadow mode`. An expired row may be deleted by any role that can read its key: each service's expired-row purge removes only those, and the node role's purge (it reads every key) removes the rest. The table owner is not subject to the policies (row-level security is enabled, not forced).
- `platform_0007` (the spend guard's keys): `platform.kv_may` adds the two keys of the paid-call spend guard to the allow-lists. Indexing reads `/services/indexing/spendGuard` (the pause judge's limits) and reads and writes `/services/indexing/spendGuard/hmacKey`; kv reads and writes only that secret, which parsing and extraction create if absent and read at start (`fleet_redis.bind_service_fleet`), and reads `/services/redis`, the Redis the breaker lives in, read there too. Without them, in enforce, those services could not start, the limits read as absent and parsing and extraction fell back to the Redis of their environment.
- `platform_0008` (the parse admission key): `platform.kv_may` lets indexing read `/services/indexing/parseAdmission`, the live numbers of the class admission of parse work (`parse_engine/admission.py`), which only indexing attaches to the store (`indexing_main.attach_parse_admission_config`). Without it, in enforce, the read was refused and the numbers stayed at their environment defaults.
- `platform_0005`: the Node API's session and short-lived cache without Redis (`REDIS_MODE=postgres`). `platform.cache_entries` (key, JSON value, optional `expires_at`): sign-in sessions, the SAML desktop hand-off and the e-mail rate-limit counters, shared by every API process and kept across a restart. Apart from `platform.kv_entries`, so configuration listings never see a session key. Written by the Node role only. Used by `PostgresCacheService` (`libs/services/cache/postgresCache.service.ts`).
- `platform_0009`: `platform.queue_deliveries` gains `admission_ms` and `admission_mac` (both nullable). A Python queue consumer writes them after it opens a delivery's message with its signature and age verified: the MAC is made with the envelope key over the message's identity, the group, the message id and the stamp, so a row edited or copied without the key is not admitted. An admitted delivery is not refused for age when it is claimed again (a hand-back that waited through an outage, a handler that outlived the envelope). Earlier consumers ignore the columns and keep judging every message by its age.
- `platform_0010`: replaces `platform.kv_may` with `platform_0008`'s definition (platform_0006's plus the spend guard's keys and the parse admission key) plus one write prefix for the connectors role, `/services/vectordb/embedding_epoch/`. The search-index cleanup runs in the connectors service and makes a new epoch current for each records collection before it resets anything (it creates the collection's current-epoch pointer and the issuing and live keys of the new token), which the connectors role could not write under `PG_KV_ACCESS=enforce`. The confirmation of the drop and the precision pins are written by the indexing and query services; connectors still writes no pin key and no other `/services/vectordb/` key. Nothing else about the matrix changes; the downgrade restores `platform_0008`'s function from its `.sql` file.
- `platform_0011` (the sandbox alert cooldown claims): `platform.kv_may`, as `platform_0010` defines it, lets query write the keys under `/services/sandbox/alerts/`, one cooldown claim per scope and level of the code sandbox's load alerts (`services/sandbox_alerts/cooldown.py`: created if absent with a TTL, rewritten to mark it resolved or put back, deleted to release it), which only query writes (`query_main.py` starts the alert loop). Without it, in enforce, the claim was refused and no alert was sent. No other role gains anything.
- `platform_0012`: the agent harness's keys. Replaces `platform.kv_may` with `platform_0011`'s definition (`platform_0010`'s plus the sandbox alert cooldown claims) plus writes for the connectors and query roles on the harness credential vault (`/services/agentHarness/credentials/`), its key ring (`/services/agentHarness/credentialKeys`) and control-plane credentials (`/services/controlPlane/credentials/`), and for the connectors role on the harness worker's repository cache status (`/services/agentHarness/repositoryCache`) and its stored release-key revocation list (`/services/harness/revokedReleaseKeys`): query's routes and agents, the connectors service's token refresh and the harness worker and model gateway (which take the connectors login) write them, and under `PG_KV_ACCESS=enforce` could not. `platform.kv_admin_or_credential` also refuses the harness credentials, key ring, role and worker credentials, sandbox-plane component documents and control-plane credentials to indexing and kv. The Node API writes every other harness key. The downgrade restores `platform_0011`'s `kv_may` and `platform_0006`'s guard from their `.sql` files.
- `platform_0013` (the PDF page limit audit's keys): `platform.kv_may`, as `platform_0012` defines it, lets indexing read and write the keys under `/migrations/pdf_page_limit_audit` (the audit's done flag, cursor and rerun count, `modules/indexing/pdf_page_limit_audit.py`), which only indexing runs (`indexing_main.run_pdf_page_limit_audit_once`). Without it, in enforce, the flag read as absent, so the audit started again at every start, and its writes were refused, so it never finished. No other role gains anything.
- `platform_0014` (key-value access enforced by default): sets `platform.kv_access` to enforce, on a new install and on an upgraded one alike. A full shadow cycle on the PostgreSQL-only Compose profile (sign-up, Confluence and Jira sync and indexing, search, chat, Knowledge Hub, agents, collections, a scheduled crawl, the placement and fold workers, a restart) and the runtime suite logged no access outside a role's prefixes once `platform_0013` and the purge fix were in; CI runs the runtime suite in shadow too and fails on any such line in the server log. An install that must keep shadow sets `PG_KV_ACCESS=shadow` on the migrate job: it is applied after the upgrade, so the revision does not override it, and every run warns while it is on. The downgrade sets shadow again.
- `retrieval` (`retrieval_0001`, the baseline, and `retrieval_0002`, the permission scope fields of a group): the vector store of `VECTOR_DB_TYPE=pgvector`. The embedding-space and collection catalog (global, written by the jobs role only), the org-scoped points, text, membership, postings, count and placement tables (forced row-level security, a hash-partitioned default tree and room for a leaf per org), the permission scope fields of a group (`retrieval_0002`: `point_groups.path_ids`, `acl_scope`, `scope_stamp`, `scope_version`, `scope_generation`, NULL until the group is stamped; the two lists are mirrored as `group_members` kinds 4 and 5, written behind the same fence as the membership arrays), and the vetted functions that read and write them (owner `pipeshub_vetted_retrieval`). **It needs pgvector 0.7.0 or later installed by an administrator in schema `ext`** (`PG_BOOTSTRAP_EXTENSIONS=vector,pg_trgm python -m db.bootstrap_roles`, or `CREATE EXTENSION vector WITH SCHEMA ext`; the stock `postgres` image and the distribution packages do not ship it). Every `db.migrate` migrates every module, so a database without pgvector stops at this revision with a message that says so; the run rolls back and applies no other pending revision either. Upgrading an installed database: re-run `db.bootstrap_roles` (new vetted role), install pgvector, then `db.migrate`. The security surface snapshot records pgvector's operators and casts as of 0.8.7; CI pins that version and 0.8.1 was found to match, an older release may differ and then fails the surface check (exit 4).
- `retrieval_0004`: `retrieval.vrid_held_elsewhere(vrid)`, whether an org other than the caller's still holds a live point of a virtual record (true or false, nothing else; the indexing role only). The delete of a virtual record asks it to keep the one mapping row and stored content another org's points still need.
- `identity_0005` and `identity_0006` (the organisation gauges): `identity_0005` adds `identity.gauge_user_counts()`, `gauge_live_orgs()` and `gauge_auth_configs()`, vetted functions that return only the gauge columns, executable by the jobs role alone. `identity_0006` then revokes the jobs role's SELECT on `identity.users`, `orgs` and `org_auth_config` and drops their `jobs_all` policies, so the jobs login reads no identity table (no email, phone or contact address). It needs no `min_code_epoch`: every release since v1.1.0 reads the gauges through the functions. The downgrade gives the grants and policies back.
- `identity_0008` (chosen organisation slugs): `identity.org_slugs`, the slug each organisation chose (any but the counter's `org-<digits>`), one organisation per slug across the install. It is a global table no service role reaches, filled by two vetted writes: `identity.org_slug_claim(slug)`, the node role's claim in the new organisation's creation unit, which answers false, writing nothing, for a malformed slug, the counter's shape, or one an organisation already holds or another unit claimed (one answer, so a refusal tells nothing about another organisation); and `identity.copied_org_slug_claim(org_id, slug)`, the document copy's claim in the unit that writes the copied rows, where a slug another organisation holds fails the unit. The unique key decides a claim racing the copy; the revision claims the slugs of rows copied before it. The counter's slugs stay on the column default.
- Extra module directories: `EXTRA_MIGRATION_LOCATIONS` in `backend/python/app/edition.py` (paths relative to
  `backend/`). Empty here.

## Agent harness (`versions/harness/`)
The `harness` schema holds every agent-harness and control-plane store under `DOC_STORE=postgres` (WP-114): `harness_0002` the session journal, its stream counters and claim-checked payloads, and the deployment-wide leader leases; `0003` runs, run events, session counters, command and admission receipts, admission quotas, next runs, liveness and sandbox reaps; `0004` the budget ledger, the audit chain (records, heads, pending, anchors, checks), data keys; `0005` approval links and notices, engine sign-ins and choices, workspace heads, manifests, keys and writers, memories and schedules; `0006` the control plane (org heads, the deployment head, policy layers, approvals, bindings, installations, grants, the capability and migration ledgers, the catalog, the change outbox); `0007` session forks; `0008` erasure jobs, backfill and principal erasure. `0009` gives runs the order they were inserted in (`admission_order`, an identity column), which breaks a tie of `created_at` wherever a session's runs are read newest first, as the Mongo store breaks it by `_id`; it builds `runs_by_session` with it (`ensure_index`), which `0003` leaves to it. `0010` indexes a person's runs newest first across their conversations (`runs_by_actor_cursor`, `runs_by_actor_agent`; ADR-UI-01). `0011` the Inbox (ADR-INBOX-01): a person's settings (`inbox_preferences`), the once-only claims of finished-run notices (`run_end_notices`, pruned after 30 days) and the watch leases of open streams (`run_watchers`). The harness fields of main's own rows (message `label`, `senderId`, `runId`, ...; session `harnessVersion`, `harnessLedger`, `erasureRequestedAt`) are columns of the `conversation` branch (`conversation_0003`).
- One table shape: `org_id` leads every key; `doc jsonb` is the document as the Mongo store keeps it (dates as `{"$date": ms}`, bytes as `{"$bin": base64}`; `agent-harness/pg-documents/pg.ts`), and every field a query filters, sorts or keys on is a typed or generated column with the index of the Mongo query shape. Deployment-wide plumbing with no org (leases, liveness, sandbox reaps, the deployment head) is `internal`.
- Org RLS through the kernel registry (`kernel.apply_rls(..., 'org', p_jobs => true)`); no SECURITY DEFINER function: the cross-org reads the worker needs (the run queue, the sweeps, the due schedules) run as the jobs role, as main's outbox dispatcher does, and each run found is then moved in a unit of its own org. Every write is fenced by the store epoch (the Node unit's prologue).
- Invariants are row locks under READ COMMITTED: a stream's seq is allocated on its counter row (gap-free, commit order); a run's transition takes the run row and checks revision, fence, attempt and lease on database time; one active run per session is a unique partial index; claims use `FOR UPDATE SKIP LOCKED`.
- **Held on a move** ([ADR-DOCMIG-01](../../docs/agent-harness-v2/adr/ADR-DOCMIG-01-every-collection-is-copied-listed-or-held.md)). `docstore-migrate` copies the harness fields that are columns of main's tables (`conversation_0003`/`0004`), lists the stale plumbing as not copied (leases, heartbeats, watch and write leases, export tickets), and holds every other harness and control-plane collection: preflight is red while one holds documents (and while a `chatSessions`, `users` or `org` document holds a coding-engine field), so a move is refused instead of starting with empty harness tables. **Carried since R45-CARRY:** a carrier
  (`backend/nodejs/apps/src/scripts/docstore-migrate/carry/`) copies, follows (deletes included), verifies, rolls back and resets
  one store group as a unit, and a collection or field it carries is no longer held: the data keys and the workspaces' heads,
  manifests and session keys (`harness.data_keys`, `workspace_heads`, `workspace_manifests`, `workspace_keys`; keys stay
  wrapped), and the coding-engine fields
  (`harness.personal_choices`). `platform_data_0008` adds the key map (`platform.docstore_keymap`: which row each copied
  document became, for a table that does not keep the MongoDB `_id`), written and read by the import role only, and the import
  role's access to those harness tables. **Since R46-CARRY** the durable runs, their journal and claim-checked payloads (payload
  names are not rewritten: either document store reads either store's names), the ledgers, people's data, erasure jobs and the
  control plane are carried too; `platform_data_0009` adds the key map's deployment-wide form
  (`platform.docstore_keymap_deployment`, for rows no org owns: sandbox reaps, erasure backfill plans, the deployment head; import
  role only) and the import role's access to every carried harness table (row policy on the org-scoped ones, privileges alone on
  the three deployment-wide ones). `platform_data_0010` (R49-SMALL) adds `platform.docstore_refused`: every document the copy
  refused, by collection and id (import role only), which verify and rollback read instead of the job state's first 300.
  `finalize --yes` removes the key map and the refusals once a move is final. Only the five edition-written
  collections stay held (R45CARRY-FU-4); an edition carries the collections only it writes through
  `EDITION_DOCSTORE_COVERAGE.carriers` (`backend/nodejs/apps/src/edition.ts`).

## Graph (`versions/graph/`)
The `graph` schema (the PostgreSQL graph store, `DATA_STORE=postgres`) is created whole by its baseline revision `graph_0001`: tables, partitions, indexes, row policies and the vetted organisation and connector reads; a change after the baseline is a normal step revision (`graph_0002` adds the index on records by virtual record and content revision; `graph_0003` adds the vetted reads of the code graph's hot lookups: blocks by record or by connector and name, code files by path; `graph_0004` adds those of record by external id, user by userId, and records by virtual record id; `graph_0005` has the code graph's hot lookups find their matches by the key's index before ordering them; `graph_0006` adds the vetted reads, with their partial indexes, of a connector's records by id, organisations by name, persons by source key, users, groups and persons by email, and people by name; it creates `pg_trgm` in schema `ext` if the administrator has not; `graph_0007` adds those of named entities by key, alias and key prefix, value mentions by record and stage states by revision, with an index of the aliases; `graph_0008` adds those of groups, record groups and roles by external id and of the stage sweep's page of states and the records on their revisions, with an index of the page; `graph_0009` adds that of a connector's declared record groups, for the access check; `graph_0010` those of the stage sweeps' stale states and unheld revisions; `graph_0011` adds the two partial indexes that serve a page of a code-graph hop in cursor order; `graph_0012` adds the vetted read, with its partial index, of a connector's records whose file type was not supported; `graph_0013` adds the vetted read, with its partial indexes of records by external id and files by path, of the records and files that link a storage document; `graph_0015` adds the partial index on a record's pending virtual record, which the holder lookups match; `graph_0016` replaces the body of the unheld-revisions read so that a record that is not COMPLETED holds every revision of its virtual record; ## Running
`PG_MIGRATE_URL=postgresql+psycopg://pipeshub_migrate:...@host:5432/db python -m db.migrate` (from `backend/`).
Direct PostgreSQL address only: the runner takes a session advisory lock, then checks in pg_locks that the
session really holds it, and refuses (exit 2) when it does not, which is what happens behind a pooler.
Exit codes: 0 done, 1 a migration failed, 2 configuration, 3 lock wait timed out
(`PG_MIGRATE_LOCK_TIMEOUT_S`, default 600; a waiting run polls the lock instead of waiting in a statement, so it holds no snapshot that a running
`CREATE INDEX CONCURRENTLY` would wait for), 4 `kernel.rls_violations` not empty.

An upgrade of an installed database runs in this order: the lock, then the **online index step**, then one transaction (revisions, epochs, checks),
then the **retired-index drops**. The online step builds the `ONLINE_INDEXES` of every pending revision (a revision `<branch>_<NNNN>` is pending
while the branch's epoch is below NNNN) on its own autocommit session as the owner role: `ON ONLY` the parent, `CREATE INDEX CONCURRENTLY` per leaf
that holds rows (a plain build on an empty leaf), then `ATTACH`, one leaf at a time; writers and readers keep working. The session has no
`statement_timeout` and no `lock_timeout` for the concurrent build (its lock admits readers and writers; it waits for older transactions); the
statements that take a lock writers wait for (the `ON ONLY` parent, a plain build, `ATTACH`) give up after 2 s and are retried.
`PG_INDEX_BUILD_MEMORY_MB` sets that session's `maintenance_work_mem` (a whole number of megabytes; unset keeps the server's; the budget of the whole
build, its parallel workers included, so keep it under the server's memory and, for parallel builds, under its shared memory size). Each index is
logged when it starts and ends, and every 10 s while it builds (its phase, blocks and partitions done from `pg_stat_progress_create_index`). A table that got an index with an expression key is analyzed once its indexes are built: the planner estimates an expression from the statistics `ANALYZE` stores for each leaf's index, and there are none before it runs ([PostgreSQL: pg_statistic](https://www.postgresql.org/docs/17/catalog-pg-statistic.html)). A stopped run (killed, a lost connection) leaves an invalid index: the next run of this build drops and rebuilds it
(`kernel.rls_violations` refuses an invalid index, so no run reports success with one). If the step or the transaction fails, the indexes the step
built are dropped again, so the build the database was on still finds the surface it expects (only once the upgrade's session has ended with the epochs unchanged: an error can arrive after the server committed, when the reply to `COMMIT` is lost, and then the committed revisions keep their indexes; when that cannot be told within 60 s the indexes stay and the run says so); a run killed before that leaves them, and going back
to the earlier build then needs them dropped by hand (the earlier build names them as `50 surface: unexpected`), or roll forward. After the commit the
`ONLINE_DROPS` of every revision are dropped (below). Downgrade is development
only (`PG_MIGRATE_ALLOW_DOWNGRADE=1 python -m db.migrate downgrade <rev>`).

## Health check (`python -m db.doctor`)
`PG_MIGRATE_URL=... python -m db.doctor` (from `backend/`) checks a database without changing it: one read-only transaction, no migrate lock, so it can run beside the services and through a pooler. It reports every branch whose epoch is below this build's head (migrations pending: run `db.migrate`) or whose `min_code_epoch` is above it (this build is older than the schema), then runs the checks the migrate job runs after an upgrade: `kernel.rls_violations` (which includes invalid indexes and extensions that are not in `kernel.settings.extensions`), its warnings, the vetted function manifests against the registry, and the security surface snapshot (the two layers below). `PG_MIGRATE_SURFACE_CHECK=skip` is ignored: the doctor always compares the surface. Exit codes: 0 healthy, 1 the check itself failed, 2 configuration (no URL, cannot connect), 4 a problem was found (each one is printed).

## Moving the key-value store from Redis (`python -m app.scripts.kv_redis_to_postgres`)
Run once, from `backend/python`, **before** switching `KV_STORE_TYPE` from `redis` to `postgres`; otherwise the install starts with an empty store (config, credentials and pending-delete records stay behind in Redis). Stop the PipesHub services first. It reads the Redis settings the services use (`REDIS_*`, `REDIS_KV_PREFIX`, `REDIS_KEY_NAMESPACE`) and `PG_CORE_URL`, copies only the config key-value keys into `platform.kv_entries` exactly as stored (ciphertext, never decoded or printed) with their remaining TTL, and never writes to Redis. `--dry-run` prints key counts per top-level prefix and writes nothing. A key PostgreSQL holds with a different value, or a configuration key (a `/...` path) it holds that Redis does not, stops the run before any write (exit 1) unless `--overwrite` is given, which replaces or removes them; runtime rows in the same table are never touched; re-running after a successful copy changes nothing. Check: the JSON summary shows `different_after: 0` and `conflicts: []`; a second run reports `changed: 0`. With `PG_KV_ACCESS=enforce` it must run with the Node API's login (`PG_CORE_URL=<node login> PG_RUNTIME_SERVICE=node`): it writes every configuration key. Rollback is setting `KV_STORE_TYPE` back to `redis`, before the services have written to PostgreSQL: changes made while on `postgres` are not copied back, so after that a rollback returns to the older Redis values.

## Placement worker (`python -m db.maintain placement`)
The vector tables are partitioned by organisation. Each organisation gets a partition of its own before its first vector row; creating a partition is DDL, so the writing service files a request (`retrieval.org_leaf_request`) and waits for this worker to close it (`retrieval.org_leaf_status`). Run one worker per database wherever the PostgreSQL vector store is used (`VECTOR_DB_TYPE=pgvector`, opt-in): `PG_MIGRATE_URL=... PG_JOBS_URL=... python -m db.maintain placement --watch [SECONDS]` (both direct addresses; the migrate login creates the partitions as the owner role, the jobs login reads and closes the requests). One pass handles at most 20 requests, oldest first, and takes the migrate lock only when there is one, so an idle worker never holds up a deployment; without `--watch` it makes one pass and exits (0 done, 1 a request failed, 2 configuration, 3 lock wait timed out, 5 a request was refused). It creates the partition of every partitioned table, secures it and attaches it in one transaction per table (a run that stopped half way is finished by the next), builds the bit-HNSW index of each registered embedding space on the points partition, and closes the request. An organisation that already has rows in a shared partition is refused and its request closed with the reason in `note`; a malformed organisation id is refused the same way; any other failure is retried with a growing delay (1, 2, 4 ... 60 seconds) and given up after 8 attempts, about two minutes after the first. A new ask re-opens a failed request once it is 30 seconds old.

## kg statistics (`python -m db.maintain analyze`)
The typed graph's tables (schema `kg`, `DATA_STORE=postgres`) are planned from their statistics, and every one of their indexes leads with `org_id`: until `ANALYZE` has seen an organisation, the planner puts it at one row and a knowledge-hub browse may read every kg row of the organisation instead of a node's children. No application role may run `ANALYZE` (it needs `MAINTAIN` or ownership, [PostgreSQL: ANALYZE](https://www.postgresql.org/docs/17/sql-analyze.html)), so a connector's first load into kg (its promotion to enforce) and its count after a restore file a request (`kg.w_analyze_request`, one row per organisation in `kg.analyze_requests`, kg_0016); a later request moves its time forward, and this job closes it: it `ANALYZE (SKIP_LOCKED)`s, as the owner role under the migrate lock, the kg tables the browse reads whose statistics are older than the newest request, and deletes every request the statistics now cover (autovacuum's count too). A table analyzed in the last 10 minutes (`PG_KG_ANALYZE_EVERY_S`, seconds) waits, so a burst of first loads is one `ANALYZE` per table; a table another session holds a conflicting lock on is skipped and taken by a later pass. It takes the migrate lock only when a table is due. Run it wherever the graph is on PostgreSQL: `placement --watch` runs it on every pass, so a deployment that runs the placement worker needs nothing else; `analyze` alone makes one pass (0 done, 1 failed, 2 configuration, 3 lock wait timed out). Credentials: `PG_MIGRATE_URL` and `PG_JOBS_URL`, both direct addresses.

## Vector maintenance jobs (`python -m db.maintain`)
Nothing here runs unless it is invoked, and these jobs only matter where the pgvector store is used (`VECTOR_DB_TYPE=pgvector`, opt-in). Every job works one organisation at a time (statements carry the org as a bound value and name only that org's rows), is idempotent, and can be killed at any point: each batch is one transaction, so a rerun finds a consistent state and finishes. A pass is bounded (100 batches per org), so a job that reports more to do is simply run again. Two runs of the same job on the same org never work it twice (a per-org advisory lock; the second skips the org; a second nightly exits busy). Jobs that read or change org data use `PG_JOBS_URL` (the jobs login, direct address); jobs that change the schema (indexes, leaf options) use `PG_MIGRATE_URL`, take the same lock as the migrate job one leaf at a time, and run as the owner role.

| Command | What it does | Credential |
| --- | --- | --- |

| `recount [<org>]` | recomputes the point counts from the live points and the term frequencies from the postings; exit 6 if an org was busy. Run it once after upgrading to `retrieval_0005`: until then the lexical search of a collection written before it counts the postings of each query term (`retrieval.lexical_df_pending`). After upgrading to `retrieval_0008`, which keeps a bound on each term's weights (`wmax`), the bounds fill themselves in the background: each `fold` pass computes missing ones from the postings, up to 200 per transaction and 100 transactions (20,000 bounds) per org per pass, each batch finding its rows by the partial index `retrieval.lexical_df_unbounded` (the rows without a bound: every row at the upgrade, none once filled), so it reads its own rows and never the ones filled before them (`retrieval.lexical_bound_pending` lists the collections still to do, and the log reports the progress), and until a term has its bound the search sums every posting of it, as before. `recount` computes them all at once, except for a term that still has a delta written before the upgrade: that one is summed in full until the fold folds the delta and the fill computes its bound | jobs |

## Writing a revision
Expand then contract; never rename; backfills are jobs, not revisions. Index builds on existing tables go
through `lib/ddl.py` (`ensure_index`, `ensure_partitioned_index`), partitions through `add_partition`.
**Indexes on tables that may hold rows** are never built or dropped inside the upgrade's transaction: a plain `CREATE INDEX` keeps the table's
writers, and a `DROP INDEX` every reader, waiting until the commit (on `graph.nodes`, every organisation's). A revision lists such an index as data,
`ONLINE_INDEXES = [{"table": ..., "name": ..., "cols": ..., "where": ..., "using": ...}]` (the keyword arguments of `ensure_partitioned_index`), and
its `upgrade()` still calls `ensure_partitioned_index(op.get_bind(), **ix, blocking=True)` for each: after the online step that call finds the index
valid and issues nothing on the table; on a new install it builds it on empty leaves. An index on a column the same revision adds cannot be built
ahead (`kg_0019`, `platform_data_0005` build theirs in the transaction). `graph_0019` builds its index in the transaction; `graph_0020` lists the same index in its `ONLINE_INDEXES`, so an upgrade with both pending builds it online first. On a database several revisions behind, an index whose column, function
or operator class an earlier pending revision adds fails at its first statement, before anything is built: the step logs it and leaves it to its
revision's transaction, as before the step existed. A changed definition is a new name (`CREATE INDEX IF NOT EXISTS` does not
compare definitions; the surface check does, by hash). The old index is retired by a later revision: `ONLINE_DROPS = ["schema.index"]`, and `db.lint` requires the
revision to say `min_code_epoch` (older code plans with the index) or `older_code_compatible = "<why nothing reads it>"`; db.migrate drops it after the commit (a partitioned index cannot be dropped `CONCURRENTLY`, nor an
attached leaf index, so it is a plain `DROP INDEX`, a catalog change of a moment, under a 2 s `lock_timeout` with retries; an index of a plain table
is dropped `CONCURRENTLY`). Until it is gone the surface check accepts its line, and a drop that could not get its lock is a warning that the next
run retries, never a failed upgrade. Revisions released before the online step (up to `released_heads.json`) built theirs in the transaction and are
not changed: a database that ran them keeps what they built. `python -m db.lint` refuses, in a revision no release has shipped, an `ensure_partitioned_index(..., blocking=True)` on a table the revision does not create unless the index is one of its `ONLINE_INDEXES` or of a later revision's of its branch (that revision is pending whenever this one is, so the online step normally builds it first; when an earlier pending revision adds the indexed column, the step falls back and the revision's transaction builds it, as above; `graph_0020` lists `graph_0019`'s) or the module sets `blocking_index_ok = "<why it cannot be built ahead>"` (at least four words; `kg_0019` and `platform_data_0005` do), and, without `min_code_epoch`, SQL in `upgrade()` that is a `DROP INDEX` or is not constant text: an f-string, `+` with anything but a literal, `%`, `.format`, a call, or a name other than a module constant that nothing else in the file binds counts as a possible drop, wherever the unknown part is, and, in the `.py` and the `.sql` of a revision no release has shipped, the body of every `DO` and of every function or procedure the revision creates and runs (a `CALL`, a `SELECT`, a `PERFORM` in a `DO` body, a trigger, or from a routine that is run; names match with or without their schema) is read as code: a `DROP INDEX`, an `EXECUTE`, a dollar-quoted string or a statement that is code itself (a `DO`, a routine, a trigger, a rule, however quoted) inside it, or a body that is not one dollar-quoted string after `AS` (a quoted string, `BEGIN ATOMIC`, a C function), counts as one too (a waiver does not clear it; a routine the revision only creates is not read). It reads every revision's `.py`, with or without a `.sql`.
**Rollback safety.** After `helm rollback`, an older build accepts a newer schema whenever every `min_code_epoch` is within its code epoch, so a revision must say whether older code still works. `python -m db.lint` fails a revision that does any of the following unless its `.py` sets `min_code_epoch = N` (an integer above 0: older code must not run) or a module-level `older_code_compatible = "<why older code still works>"` (at least four words). A comment or `min_code_epoch = 0` does not count. Statements are matched after comments and whitespace are normalised, so layout does not matter; the SQL checked is the `.sql` file (statements inside `DO` bodies included, `IF ... THEN` and `PERFORM` stripped) plus, from `upgrade()` and every module function it calls (not `downgrade()`), the string constants passed to `execute`, `exec_driver_sql` (also through an alias or `getattr`), `text` and `ensure_index`, and Alembic's schema calls (`create_check_constraint`, `create_foreign_key`, `create_unique_constraint`, `create_primary_key`, `drop_constraint`, `alter_column`, `add_column`, `drop_column`, `drop_table`, `rename_table`, `create_index`, `drop_index`), which map to the matching SQL rule. An argument built at run time needs the mark or waiver. DROP / RENAME / SET SCHEMA / ALTER ... TYPE / DROP VIEW (and TYPE, SEQUENCE, DOMAIN, ROLE, OWNED, EXTENSION) / TRUNCATE / ALTER ROLE ... NOLOGIN need the epoch mark (a view dropped and re-created in the same file is exempt); a waiver does not clear them. The rest accept either, and apply to a table or function the file did not create (a `CREATE TABLE IF NOT EXISTS` of a table any module's revision creates counts as existing):
- `ADD COLUMN ... NOT NULL` without a default (`DEFAULT NULL` is none), `SET NOT NULL` or `DROP DEFAULT` (older inserts fail);
- a new CHECK, FOREIGN KEY, UNIQUE, PRIMARY KEY or EXCLUDE constraint, `NOT VALID` included (it still checks new writes), or a column added with an inline CHECK / REFERENCES; `ALTER DOMAIN`;
- tightened row-level security: `CREATE` / `ALTER` / `DROP POLICY`, `ENABLE` / `FORCE ROW LEVEL SECURITY`, or `kernel.apply_rls` (positional or `p_rel =>`);
- `CREATE OR REPLACE` / `DROP` / `ALTER` of a FUNCTION or PROCEDURE, `CREATE OR REPLACE VIEW` / `ALTER VIEW`, and `CREATE` / `DROP TRIGGER`. A vetted function is changed by re-running its generated file, so the check follows the revisions that name it in `run_vetted` (any one with the mark or waiver passes);
- a unique index, in SQL or built in the `.py` with `ensure_index` / `ensure_partitioned_index(..., unique=True)`;
- `REVOKE` from any role other than `PUBLIC`, except the two generated housekeeping forms (`REVOKE CREATE ON SCHEMA s FROM pipeshub_vetted_*` and `REVOKE pipeshub_vetted_* FROM pipeshub_owner`); a table or function privilege taken from a service, app or vetted role can break older code;
- `DROP CONSTRAINT` (a dropped unique or primary key breaks `ON CONFLICT`), `ALTER TABLE ... DETACH PARTITION`, `CREATE RULE`;
- a `DO` block with `EXECUTE` (dynamic SQL cannot be parsed).
Review item for every revision: run the previous release's code against the new schema in your head (inserts, updates, reads, function calls) and write the answer into the waiver. A development downgrade (`PG_MIGRATE_ALLOW_DOWNGRADE`) keeps the contract: below the contract revision the branch row reads, for example, epoch 1 with `min_code_epoch` 11, and every build refuses that database until it is upgraded again. Not parsed: function names passed to `run_vetted` through a variable, SQL that reaches a database through an object other than those above, and the waiver's truth.

**Released heads.** `released_heads.json` holds each branch's head epoch in the last release, and `tests/test_unit.py::test_no_released_head_is_gone` fails when a branch's head is below it (a shipped revision deleted or renumbered). Only the release process edits the file: before a release is tagged, run `python -m db.released_heads <tag>` from `backend/` on the commit you tag (`main`, or the release branch for a hotfix) and merge the result, then tag that commit (`deployment/docker-compose/RELEASE.md`). On a tag push, on a manual release run with promote, and on a manual run of a pre-release version (which publishes its version tags), the release workflow runs `python -m db.released_heads --check` and stops before any build when the file's epochs are not the tree's heads (the `release` name is not compared, so a pre-release or a hotfix that adds no migration passes; one that does runs the writer first).

CI: `python -m db.epoch_lint`, `python -m db.lint`; `python -m db.schema_requirements kernel,platform > schema_requirements.json`
writes a build artifact's requirements, checked at boot by `boot_assert.py` (Python) and `nodejs/apps/src/libs/db/schema-assert.ts` (Node).

## Org isolation (row-level security)
Every table that holds org data has `org_id text NOT NULL` as the leading key column and is registered in the same
revision that creates it:

    SELECT kernel.apply_rls('app.docs', 'org', p_jobs => true, p_vetted => true);   -- the whole tree, owner/migrate only
    -- class 'org': own org; 'lineage': also reads the orgs in app.org_lineage; 'global': no RLS and no app privileges,
    -- reached only through vetted functions

Policies read `app.org_id` through `NULLIF(current_setting('app.org_id', true), '')`, so an unset or empty value matches
nothing. Row-level security is enabled and forced on the table and on every partition. A new partition is made
with `lib.ddl.add_partition` (standalone leaf, `kernel.apply_rls_partition`, then ATTACH). A key that must be unique across
orgs is declared with `kernel.exempt_constraint` and has no app privileges: only its vetted functions touch it.
SECURITY DEFINER functions are classified with `kernel.register_function(proc, 'read'|'write'|'jobs'|'prologue', writer, scope, content_ok)`
and are written as manifest entries (next section). The bootstrap leaves the owner with ADMIN only on each vetted role.

## Vetted functions
A vetted function is a `SECURITY DEFINER` function owned by its schema's `pipeshub_vetted_<schema>` role (one role per schema, no members, no
privilege outside the schema, only on tables that opted in with `p_vetted`/`p_vetted_write`). The kernel schema has its own, created by the
bootstrap. Why: RLS hides indexes behind operators that are not leakproof; the function applies the org predicate itself, so the planner
may use the index, and everything it can touch is bounded by its owner.

Write the function as an entry in `<module>/vetted/manifest.yaml` (format and the template: `lib/vetted.py`). Every field is checked against a strict schema: identifiers match `^[a-z_][a-z0-9_]*$`, types and `returns` come from a short list, `default` and `no_org` are a number, NULL, true/false or a plain quoted string, flags are booleans, and the body may RAISE only a constant EXCEPTION with an SQLSTATE; the generator quotes identifiers as `quote_ident` does. Generate the SQL with:

    python -m db.lib.vetted render versions/<module>/vetted/manifest.yaml     # writes versions/<module>/vetted/<name>.sql
    python -m db.lib.vetted check  versions/<module>/vetted/manifest.yaml     # CI: the checked-in SQL is what the manifest says

A revision installs it with `run_vetted(__file__, "<name>")`. The generated SQL validates every argument (SQLSTATE `22023`), takes the org only
from `app.org_id` (no org: no rows), pins `search_path = pg_catalog, <schema>[, ext], pg_temp` (**pg_temp last**), creates the function as the
vetted role (the owner borrows it for that transaction: SET and CREATE on the schema, then released), revokes PUBLIC, grants EXECUTE and
registers the function. The review checklist, and where it is enforced:

| Checklist item | Enforced by |
|---|---|
| 1 read-only, STABLE, no DML, no dynamic SQL (`EXECUTE`, `format()`, `query_to_xml`), no `ON CONFLICT` in a write function, SQL or PL/pgSQL only; no side channel: `RAISE` only as a constant `EXCEPTION` with an SQLSTATE (no notice, no format argument, no DETAIL, no `ASSERT`) | checks 36, 55, 56, 57, 74; the suite fails on any notice |
| 2 path is `pg_catalog`, own schema, `ext`, `pg_temp` last | checks 16, 58; the shadowing test |
| 3 org from the GUC, never an argument; global lookups are exact-match | checks 59, 60, 61; foreign-org test |
| 4 every argument validated, `22023` | check 62; validation test |
| 5 minimal columns: no whole rows (also as `json`), no content column unless registered `content_ok` | checks 63, 64 |
| 6 hard LIMIT | check 65 |
| 7 owner, no PUBLIC, only the application (never jobs, backup, restore) | checks 15, 17, 66; privileges test |
| 8 reads only its schema's tables that opted into `vetted_read` | checks 42, 73; manifest `reads` check |
| 9 tests exist | every registered function is in a manifest and the manifest agrees with the registry (`71`, run by `db.migrate`) |
| 10 the plans: no sequential scan of an org-scoped table above 1,000 rows on any of seven calls, and the named index (whole name) on calls one and seven | plan gate (`vetted_harness.check_plans`) |
| 11 nothing that raises on row data (casts, division, date parsing, jsonb paths) | check 67 |

A manifest entry's `test:` section feeds the generated suite: `needle` (SQL that inserts the row only org B owns; `{org}` is the needle org),
`args` (sample arguments), `own_result` / `other_result` / `no_org_result` (exact rows for the owning org, another org, no org; the default
for the last two is no rows), `state` (a query whose answer must not change when another org calls a write function), `bad_args` (each must
fail with `22023`), `index` and `volume` (SQL that fills the table for the index and timing checks), `max_ms`, or `checks: [...]` to list the
only checks that apply (a helper has `privileges` and `catalog`).

The surface snapshot lists each function's owner, flags, settings and a hash of its body, so any change to a body is a reviewed diff.
Per function the manifest drives a generated suite (`tests/test_vetted.py`): no org, a foreign org, the own org, index use, validation,
privileges, catalog, timing and shadowing by a caller's temp table.

**Plan gate.** `vetted_harness.check_plans` fails on a sequential scan of an org-scoped table with more than 1,000 estimated rows (tables are analysed first) and on a missing index, matched as a whole name. `vetted_harness.plans_auto_explain` loads `auto_explain` in an administrator session (LOAD needs superuser), switches to the
service role, calls the function seven times and reads the nested plans from the notices (the plpgsql plan cache goes generic after five
calls). Where LOAD is not allowed (managed platforms), `plan_explain` switches to the vetted role and EXPLAINs the function's query with the
org set; `check_index` falls back to it by itself.

**`kernel.org_lineage(org)`** is the list the unit of work puts in `app.org_lineage`: the caller's org first, then the parents returned by
`kernel.org_parent_ids(org)` (sorted, at most 16, well-formed ids only). Asking for another org's lineage answers like having no org. By default `org_parent_ids` returns nothing, so the lineage is the org alone. No table shipped here uses the `lineage` class (`test_no_shipped_table_uses_the_lineage_class`): it is a hook for deployments that add a parent hierarchy. `org_parent_ids` is an extension point: its signature is
frozen (check 68), nobody but `org_lineage` can execute it (check 72), and an extra migration location replaces only its body (only functions named in `EXTENSION_POINTS` in `lib/vetted.py` may be extended) with a
manifest entry marked `extends: true` (same signature, class and scope) and an `allowlist.yaml` whose `surface:` lists the new function
line and whose `remove:` lists the old one. A body that reads the location's own tables first claims a new, empty schema
(`kernel.declare_extension_schema`) and then calls `kernel.grant_vetted_owner_select(table)` for tables in it (SELECT and USAGE only, nothing in
any other schema; the grant is a snapshot line the allowlist must list). The location may also write that schema through vetted functions of its
own (`kernel_0023`): the manifest names them in the schema, `python -m db.bootstrap_roles` creates the schema's vetted owner from the manifest
(`location_vetted_schemas`), and `declare_extension_schema` accepts that owner only while it is fresh (no object, privilege or policy in the database,
a member of nothing, held only by the owner role with ADMIN, no login). Its functions write only that schema (check 42); the kernel's vetted owner
keeps SELECT only. A schema the owner role does not own, one that holds an object, or an owner used anywhere before is refused as always.

**`kernel.org_writes_held(org)`** (`kernel_0020`) is the second extension point, under the same rules: called by the two write fences only (check 72), with the unit's org, after the fence holds its install-wide barrier (see `kernel_0020` above); `true` refuses the unit (`25006`). By default it returns `false`.

Two layers decide whether a database is acceptable, and both must be empty (the migrate job exits 4 otherwise, CI runs both on an empty
database, and `python -m db.doctor` runs both on a live one):

1. **The surface snapshot, deny by default** (`surface.py`, expected text in `surface.snapshot.txt` and any `surface*.txt` next to a
   module, plus an `allowlist.yaml` in each directory of `EXTRA_MIGRATION_LOCATIONS` (a `surface:` key, one `- "<line>"` item per line, merged into
   the expected state; a `remove:` key drops the base lines the location replaces; the OSS default has none), plus files named in `PG_MIGRATE_SURFACE_FILES`). One sorted line per fact about the security surface: roles and
   attributes, every membership edge with its ADMIN/INHERIT/SET options, role and database settings, ACLs on databases, schemas,
   relations, columns, functions, types, languages, large objects and foreign servers, default privileges, policies, RLS and FORCE
   flags, rules, triggers, constraints, indexes, extended statistics (`CREATE STATISTICS`, listed for a partition too: they do not recurse onto partitions, so one on a leaf is its own object), view and function definitions (hashed), SECURITY DEFINER / LEAKPROOF flags and function
   settings, operators and casts, built-in function attributes (name, arguments, language, owner, SECURITY DEFINER, LEAKPROOF, volatility, kind, settings; not the OID, body or library path, which differ between builds of one major; a hash per PostgreSQL major, `sysfuncs@17 ...`, and a line for any built-in that is SECURITY DEFINER or has settings), extensions, foreign data, publications, subscriptions and event triggers. A live line that is not
   expected, or an expected line that is not live, is a violation (rule `50`). A change to any of it shows up as a diff in the pull
   request that makes it: regenerate with `UPDATE_SURFACE=1 pytest` (or `python -m db.surface` on a migrated database) and review.
   A line written `? <line>` is optional: it may be live or not and is never reported missing, while any variant of it is still
   unexpected (the opt-in monitoring role of `kernel_0019`).
   A minor release can add a built-in, so the snapshot keeps one reviewed `sysfuncs@<major>` line per minor release in use, and a
   server passes when it matches any of them (installs on an earlier minor keep passing). To accept a new minor, run
   `PG_ADMIN_URL=<new minor> python -m db.surface --sysfuncs <stock server of a reviewed minor>`: it prints the built-ins added (`+`)
   and removed (`-`) as `name(args):language:owner is the bootstrap superuser:secdef:leakproof:volatility:kind:settings`. If none
   is SECURITY DEFINER, LEAKPROOF or has settings, add the new line and keep the old ones. The `sysfunc` lines are never relaxed. The
   CI images in `.github/workflows/db-migrations.yml` are pinned by digest, like `deployment/docker-compose/postgres/Dockerfile`: bump
   both together in a pull request that adds any new `sysfuncs` line.
   `PG_MIGRATE_SURFACE_CHECK=skip` switches the comparison off (development only). It is skipped while a restore window is open.
2. **Semantic checks** (`kernel.rls_violations`, checks 01-51), which say why: every relation outside schema `kernel` is registered
   (org, lineage, global or internal), keys and foreign keys lead with `org_id`, policies match their templates, `pg_temp` is
   last, function classes and who may execute them, membership allowlist, administrator separation, column grants, rules, views,
   foreign data, sequences, default privileges, publications and event triggers, LEAKPROOF, large objects, the consumer inbox key,
   and invalid indexes. Every role in the cluster is checked, whatever its name. Roles that own objects, the owner, the group, the
   service roles and the vetted roles never log in. Each service role has exactly one member, its own `<role>_login`, without ADMIN.
   `kernel.settings.admins` is an explicit reviewed list of human administrators: they may hold administrator roles, but may not be
   members of or hold any application role, no application role may reach them, and they may not be listed if they are ours. No role
   has BYPASSRLS, and the only superusers are the bootstrap superuser and the database owner. `kernel.settings.extensions` lists the
   extensions that may be installed; only their members are exempt from the object checks.

Privileges are attributed through the whole membership graph (inherit or SET), so a privilege parked on a helper role counts for
every role that reaches it.

Roles: `python -m db.bootstrap_roles [--vetted schema,schema]` (administrative `PG_ADMIN_URL`; idempotent, additive, no
role gets SUPERUSER, CREATEROLE or BYPASSRLS; with `PG_MONITOR_PASSWORD` it also creates the monitoring login `pipeshub_monitor`). A login that would be created needs its `PG_<ROLE>_PASSWORD` or the run stops (exit 2) before creating anything (the server receives its SCRAM verifier, computed by the client, never the password, and the session's statement log, statistics and activity reporting are switched off where the administrative login may); `PG_BOOTSTRAP_ALLOW_NO_PASSWORD=1` waives that for peer, trust or certificate authentication. On an existing database, run it again before every `db.migrate` upgrade: a new revision can need a role the old bootstrap did not create, and migrate stops at that revision. Each service has a login `pipeshub_<svc>_login`, a member of its own NOLOGIN
service role `WITH INHERIT FALSE, SET TRUE`: the login holds no privileges until the unit of work switches role. No role
bypasses RLS: `pipeshub_backup` reads all rows through a SELECT policy, `pipeshub_restore` (NOLOGIN) inserts through a
policy that admits only the org of an open restore window.

Restore: `python -m db.restore_window open --org <id> [--hours N]` (needs `PG_ADMIN_URL`, `PG_MIGRATE_URL`, `PG_BACKUP_URL`,
`PG_RESTORE_PASSWORD`) switches the application logins off and disconnects them, refuses unless that org has no rows,
and gives `pipeshub_restore` a login that expires by itself. Export the org with `export [--org <id>] --dir <d>` (only that org's rows, parents first; without `--org` it takes the only org that has rows, and refuses when there are none or several), `load [--org <id>] --dir <d>` it as `pipeshub_restore` (without `--org`, the only org in the files)
(a file holding another org's row is refused before anything is inserted: the database rejects a whole multi-row INSERT if
one row is foreign, so a mixed dump would lose rows), then
`sequences` (the migrator sets every column-owned sequence from the restored data), then `close`. Global tables are not
restorable by this role; they load through vetted import functions. `load` is one transaction for every table and takes table names only from
the registry (it refuses anything else). If `open` is interrupted, `close --abandon` brings the logins back. PgBouncer should set `server_login_retry` low so
the logins come back quickly (2 works well).

`kernel_0005` adds `platform.consumer_inbox` (primary key `(org_id, message_id)`; check 44) for consumer replay protection.
Server-side large objects have no org, so the bootstrap revokes their functions from PUBLIC (check 43). The PgBouncer reset
includes `DEALLOCATE ALL` (with `max_prepared_statements` on, PgBouncer keeps protocol-level statements working), so SQL
`PREPARE` text does not reach the next client.

On a managed platform that cannot revoke the large-object functions, set `{"managed": true}` in `platform.deployment_profile.profile`: check 43's
function rows become warnings (`kernel.rls_warnings`) and that one snapshot line is not compared.

**An administrator that is not a superuser** (a managed service's master user: `LOGIN CREATEROLE CREATEDB`, no SUPERUSER,
BYPASSRLS or REPLICATION) can run `db.bootstrap_roles` when it owns the database and the platform installs the extensions (`vector`,
`pg_trgm`) into schema `ext` owned by `pipeshub_owner`. `kernel.bootstrap_admin()` names it: the database owner when it is such a role
(all of `LOGIN`, `CREATEROLE` and `CREATEDB`; none of SUPERUSER, BYPASSRLS and REPLICATION) and not one of ours or a predefined one
(prefixes compared literally). Any other owner is not it and stays an actor: check 22 reports its BYPASSRLS, and check 41 reports
the CREATEROLE, CREATEDB or REPLICATION it holds (for example an owner with CREATEROLE but no CREATEDB, or one that cannot log in). The checks treat the administrator as they treat the bootstrap superuser:
it is not an application actor; the ADMIN-only memberships PostgreSQL 16+ gives it on every role it created, and its memberships of
roles that are not ours (a platform's own administrative role), are accepted (checks 18 and 37); its surface lines are compared under
the superuser's token, and the lines of the platform roles it holds (NOLOGIN groups with none of the attributes checks 22 and 41
are about, or predefined roles) are left to the semantic checks; check 43 reports PUBLIC's access
to the large-object functions as a warning, as on a declared managed platform. Everything else is unchanged: a role that reaches the
administrator is still an actor holding what it reaches; the administrator holding one of our roles with INHERIT or SET is a violation
(`37 bootstrap administrator holds an application role`); an actor's own grant on a large-object function is still check 43, on a
declared managed platform too; a role the administrator creates is reviewed in the surface like any other. A platform role's own
memberships of other roles are checked as any role's are. Tests: `tests/test_managed_admin.py`.

## Person-level tables and jobs functions
Some identity tables are keyed by a person, not by an org (a credential, a sign-in code). They are `global` tables with no `org_id`
(`kernel.apply_rls(rel, 'global', p_vetted_write => true)`), marked with `kernel.mark_person(rel)` (check 76: no `org_id` column).
The application holds no privilege on them; only vetted functions of scope `person` reach them (manifest keys in `lib/vetted.py`):

| Effect | Rule (generated template; checks) |
|---|---|
| `read` | Before an org is chosen (`app.org_id` empty) an exact email is answered. With an org set, only the acting person's own email (`actor` resolves it from `app.org_id` and `app.user_id`); any other email, a stranger and a missing principal get the same empty answer (78, 79). No caller-chosen limit or threshold, and a constant `LIMIT` (85). |
| `self` | The acting principal's email must equal the person's; then the per-email lock, then the membership proof (`member`) (78-81). |
| `admin` | One of a closed list (`unblock`, `role_change`, `admin_signout`, `clear_if_last`): the principal must be an admin of the org (`admin_check`), the person a live member, and an audit row is written (82, 83). |
| `preorg` | Only while no org is set; returns nothing except `consume_otp` (84). |

Every person write takes `pg_advisory_xact_lock(7350, hashtext(email))` before it reads the membership proof (80). Advisory locks are
transaction-scoped, two-integer, and the first integer is a class in `kernel.lock_keys` (93). A person write may also write other
orgs' org-scoped rows of the person (`fanout`, tables with `vetted_write`) because it holds the proof; no other function may (`db.lib.vetted.problems`).

**Jobs-only functions.** A `jobs`-class function is named `import_*` or `sweep_*`, executable by the jobs role only (31: by registry class, by the
owner of the global table it writes, and by behaviour). An import names `requires_job` kinds and refuses with `55000` unless
`platform.jobs` holds a running job of one of them (its schema's vetted owner reads that table through `kernel.grant_job_gate(schema)`). A sweep
takes no arguments and deletes by a fixed `now()` expiry predicate. Deletion is for sweeps alone: `kernel.allow_vetted_delete(rel)` opts one global
table in; no read or write function deletes (88) and no other table grants DELETE to a vetted role (89).

**Pinned writes.** A table that one service writes through vetted functions and nobody else (an access table, a change queue) needs DELETE and `ON CONFLICT`, which checks 57 and 88 refuse to every function; a vetted org-scoped `write` function may use them where it is pinned. A *pin* is a registry row `(function, table, op)` with `op` in `insert | upsert | update | delete`, made by `kernel.allow_vetted_write_op` (owner only; the generated function file calls it, from the manifest's `pins:` list). A function with a pin may touch only what it pins (105), and these shapes are all the catalog accepts (the body is read after `kernel.src_text`, so line breaks and comments do not matter; the spelling of the tokens is the one shown):

| Pin | The statement | Checks |
|---|---|---|
| `delete`, `key: [c1, c2]` (the primary key after `org_id`) | `DELETE FROM s.t t USING unnest(p_a, p_b) AS k(a, b) WHERE t.org_id = v_org AND t.c1 = k.a AND t.c2 = k.b;` (each `key` column compared with the alias column at its position, in any order of the conditions) or, with scalar arguments, `DELETE FROM s.t t WHERE t.org_id = v_org AND t.c1 = p_x;` Nothing else in the `WHERE`, no `RETURNING`. | 104 (the pin is the whole key), 106 (the statement is exactly that), 108 (every unnested argument is an array argument with `cardinality(p_a) > N` and `N <= max_items <= 5000`, so a longer array is `22023`), 109 (a scalar key is a scalar argument) |
| `delete`, `txn: col` (an `xid8` column) | `DELETE FROM s.t t WHERE t.org_id = v_org AND t.col = pg_current_xact_id();`, no arguments needed | 104, 106 |
| `upsert`, `set: [c, ...]` (`[]` = `DO NOTHING`) | `INSERT INTO s.t (org_id, ...) SELECT v_org, k.x, ... FROM unnest(p_a, ...) AS k(x, ...) ON CONFLICT (<the primary key>) DO UPDATE SET c = excluded.c, ...` or `VALUES (v_org, p_x, ...)`; no join, no sub-select, no `WHERE`; `RETURNING` only key columns. | 107, 108 |
| `insert`, `update` | as before, but the function may touch only what it pins | 105 |

The org is always `v_org` (from `app.org_id` by the generated template, never an argument: checks 59, 60). On a table that requires the per-org policy (`kernel_0017`) the vetted role's row policy is the org predicate, so even a function that escaped the shapes below reads and writes only the org in `app.org_id`; the shapes, the generated foreign-org and no-org tests and `custom_plan` (the plan gate runs on every delete and upsert) are the first line, the policy the second. `app.org_id` is set by the calling service (by design): a role that can run the function can choose the org it runs for, which is the same trust as the row policy of every other role. The policy keys on that setting and a routine body can change a setting, so **the text rules 130 and 131, 133 (no routine of the reach carries an `app.*` setting of its own), 134 (no dynamic SQL there), 135 (no routine there in a language the checks do not read) and 132 (a pinned function calls pinned functions and vetted kernel routines only), are what keep a routine from changing `app.org_id`**; the policy stops every cross-org route the catalog reads, not those (tests pin both facts). A table with a pin for an operation has no direct privilege for it anywhere else, on the table, any partition or any column, for any role an application login can reach or PUBLIC (110); no other vetted role has one (115); no definer function without a pin writes it (114); the pinned function is executable by its `writer` and its owner only (113). A pinned function reads `app.org_id` once (the template's declaration), calls no `set_config`, `SET LOCAL` or `RESET`, and uses `v_org` only as `org_id = v_org`, `VALUES (v_org, ...`, `SELECT v_org, ...` and `v_org IS NULL`: never assigned, selected into, redeclared or looped over (116). Each statement of a pinned function has exactly one DML keyword and none behind a `WITH` (105); a plain insert is one `VALUES (v_org, <arguments or constants>)` row or `SELECT v_org, ... FROM unnest(...)`, and a plain update sets arguments or constants (never `org_id`) with `WHERE <alias>.org_id = v_org [AND <alias>.col = <argument or constant>]...`, no `OR`, sub-select or `FROM` (117). The cap of an unnested array is an `IF cardinality(arg) > N THEN RAISE EXCEPTION` before the first DML (108). A pinned function contains no `MERGE` and no `ONLY` (105), and a function with no pin that writes a pinned table by `MERGE`, `UPDATE ONLY` or `DELETE FROM ONLY` is named by 114 like any other write. The next rules read the routines a vetted role can run: the routines a vetted role owns, the routines the server itself runs for a pinned table (its triggers, column defaults and generation expressions, CHECK constraints and index expressions, the support functions of the operator classes its indexes use, and the functions that take its row type, which `(t).f` calls) and, while a pin exists, the install's operators, casts, domain CHECKs and operator-class support functions, and every routine any of these call by name, however deep, including the transition, final, combine, serial and moving-aggregate functions of an aggregate they name. An install's own helpers that nothing of that is connected to are not read, so they cannot fail an upgrade. A routine of that reach in a language the checks do not read (C, an untrusted language; not an extension's) is named by 135, and a name built at run time by 134. What remains out of reach is a routine nothing in that reach names or the server runs for a pinned table, and a binding of the org that a routine cannot change, which would need a key shared by the services and the database and is not built. No such definer function has a CR, FF, VT, `$` or non-ASCII character outside a string (111) or a SQL-standard body (`BEGIN ATOMIC`, `RETURN <expression>`) in any SQL or PL/pgSQL routine of that reach (112); no such routine starts a statement with `DO`, `SET`, `RESET`, `PREPARE`, `LOAD`, `LISTEN`, `NOTIFY`, `DISCARD`, `COPY`, `LOCK` or a DDL / `GRANT` verb (130: their text is a string or changes the org, the search path or the role) and none calls `set_config` for anything but `lock_timeout` (131); a pinned function calls only pinned functions and vetted kernel routines (132: another routine would run its statements outside the shapes), no routine of that reach carries an `app.*` setting in its configuration (133: `SET app.org_id = ...` on a routine would change the org it runs for), and none builds SQL dynamically (134: rule 56's list, `EXECUTE`, `format()`, `query_to_xml` and the like, applied to invoker routines too); no other function names a pinned function (120); no view (121), inheritance child (122) or cascading foreign key (123) touches a pinned relation; the writer of a pinned function is registered in `kernel.pin_writers` (125). One vetted role still owns every function of a schema, so per-function isolation inside a schema rests on 114, 120 and the row policy; a dedicated role per writer is the stronger option and is not built. The pins themselves are lines of the security surface (`pin <function> <table> <op> key=.. set=.. txn=.. max=..`), so a new or changed pin is a reviewed diff in the snapshot (an extra location lists its own in `allowlist.yaml`). A pinned function names `callers:` (source paths below `backend/`); `db.lint` fails on any other file that mentions it, which is the "only the stamping module" boundary: the database enforces "the connectors service", the lint "the module". `restore` keeps its INSERT on every org table (a restore window of one org), as for every table.

The revision that installs pinned writers on a table that applications wrote directly before (the shadow-mode fallback) must revoke that grant in the same revision and set `min_code_epoch` (the lint requires it for a REVOKE; code built before it must not run: `boot_assert`, and an older build's migrate Job refuses to open the data). Check 110 turns a forgotten revoke into exit 4, which rolls the whole upgrade back. `kernel_0016` refuses its own downgrade while any pin exists, `kernel_0017` while a table still requires the per-org policy.

**External-issuer dedupe.** A write function may answer "already processed" (`ON CONFLICT DO NOTHING`, returns boolean) only for a global table without
`org_id` whose key is exempted as `external_issuer`; the manifest names its `callers` and `python -m db.lint` fails on any other source path calling it (90).

**Fence.** A `prologue` function (`kernel.assert_profile_epoch`) is `VOLATILE`, `SECURITY DEFINER` and asserts `READ COMMITTED`. It takes the shared
transaction-scoped barrier lock (class in `kernel.lock_keys`) held to commit and refuses with `25006` when a switch holds it exclusively; the switch
takes the same key exclusively in the transaction that changes the epoch. The logins hold `USAGE` and `EXECUTE` only; no application role reads the table the fence reads (32).
Both runtimes reference the fence's output column in the prologue's outer `SELECT`, and read units are `READ ONLY`.

**Shared sequences.** A sequence may feed an internal surrogate. A text column whose default calls `nextval()` shows the value, so it needs a
reviewed `kernel.waive_sequence(...)` row from a migration (91, 92). A caller-supplied unique value (an org slug) is an exempted `public_by_design` key; its vetted write
answers the same for a taken and a malformed value and has no `ON CONFLICT` (57).

## Tests
`cd backend/db && pytest`. Integration tests start throwaway clusters from `MIGRATE_TEST_PG_BINS` (comma-separated
PostgreSQL `bin` dirs; skipped when unset and no `initdb` on PATH). Needs `pip install --require-hashes --no-deps -r requirements-test.lock`.
The servers need pgvector and PostgreSQL's contrib modules, `auto_explain` among them (some tests read the plans of the statements
inside a vetted function): the `postgresql-contrib` package of a distribution, or `make -C contrib install` in a source build.

## If a runner dies
The lock belongs to the runner's session and is released when PostgreSQL notices the client is gone (TCP
keepalives, about a minute at worst; at once on a process kill). The migration session sets
`client_connection_check_interval=5s`, so a statement still running for a dead runner is cancelled within
seconds, and `idle_in_transaction_session_timeout=10min` ends an abandoned open transaction; `statement_timeout`
is 15 min. Each revision is one transaction, so nothing is half applied: run the job again. If a re-run reports
lock timeouts for longer than that, find the old backend (`SELECT pid, state, query FROM pg_stat_activity
WHERE usename = 'pipeshub_migrate'`) and `pg_terminate_backend` it.

The org isolation tests run through a real PgBouncer (transaction pooling, a pool of two server connections, the kernel reset
settings): fault injection per registered table (LIST/HASH and time-RANGE trees) and 3,000+ pooled transactions with no
cross-org row.

CI: `.github/workflows/db-migrations.yml` (lints, an empty database migrated to heads with the catalog check, and the tests on PostgreSQL 17 and 18 service containers,
`MIGRATE_TEST_PG_EXTERNAL=host:port`; `MIGRATE_TEST_PGBOUNCER=<binary>` enables the real-pooler test).
